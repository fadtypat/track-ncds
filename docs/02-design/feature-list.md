เอกสารนี้จัดกลุ่ม FR/NFR ทั้งหมดจาก [[backlog]] ให้เป็น "ฟีเจอร์" ที่มีความหมายต่อผู้ใช้งานจริง
สำหรับทีมออกแบบ/พัฒนา อ้างอิงรายละเอียดเต็มจาก
[[20260917-01-patient-ncd-history-lab-complication-risk]] (spec ฉบับแรกของโปรเจกต์),

ที่ครอบคลุมข้อมูลผู้ป่วยในขอบเขตเดียวกัน) และ
[[20260922-01-operational-quality-nfr]] (spec เพิ่มเติมด้านคุณภาพเชิงปฏิบัติการ — Performance,
Availability, Clinical Safety Validation, Session Timeout, Accessibility, Security Rules
Verification, Browser/Device Compatibility, Interoperability — ครอบคลุมทั้งระบบเช่นเดียวกับ PDPA)
[[20260923-01-user-authentication-email-password]] (spec เพิ่มเติมด้านการยืนยันตัวตนก่อนเข้าสู่ระบบ
— เข้าสู่ระบบ, สมัครบัญชีด้วยตนเอง, ยืนยันอีเมล, ลืมรหัสผ่าน) และ
[[20260924-01-admin-role-account-management]] (spec เพิ่มเติมกำหนดบทบาท admin ใหม่ — อนุมัติบัญชี,
เปลี่ยน role, ระงับ/เปิดใช้งานบัญชี, จัดการ PatientAssignment และดูประวัติผู้ป่วยทุกรายแบบ read-only;

พยาบาล)

## 1. ดูประวัติการวินิจฉัยและผลตรวจ lab ของผู้ป่วย NCD

แพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD เปิดดูประวัติการวินิจฉัยโรค NCD (เบาหวาน E10–E14, ความดันโลหิตสูง
I10–I14, ถุงลมโป่งพอง J44) ของผู้ป่วยรายบุคคล เรียงตามช่วงเวลา พร้อมดูค่าผลตรวจ lab มาตรฐานที่
เกี่ยวข้อง (เช่น HbA1c, eGFR, LDL, ค่าความดันโลหิต) แบบย้อนหลังเป็นช่วงเวลาเพื่อติดตามแนวโน้ม
ข้อมูลทั้งหมดอ้างอิงจากแหล่งข้อมูล HOSxP (หรือข้อมูล mockup ระหว่างพัฒนา) และจำกัดการเข้าถึงเฉพาะ
บทบาทที่มีสิทธิ์เท่านั้น

- รหัส FR/NFR ที่เกี่ยวข้อง:
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-01]],
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-02]],
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-01]],
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-02]]
- บทบาทผู้ใช้: แพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD
- ระดับความสำคัญ (MoSCoW): Must have

หมายเหตุ: การเข้าถึงประวัติของผู้ป่วยรายบุคคลในฟีเจอร์นี้มีขั้นตอนค้นหา/เลือกผู้ป่วยเป็น
precondition เสมอ ดูฟีเจอร์ที่ 3 ([[#3. ค้นหา/เลือกผู้ป่วยในความดูแล]])

## 2. วิเคราะห์ แจ้งเตือน และยืนยัน/แก้ไขผลประเมินความเสี่ยงโรคแทรกซ้อน

ระบบประมวลผลค่า lab ของผู้ป่วยเทียบกับ threshold มาตรฐาน (แบบ rule-based ไม่ใช้ AI/Machine
Learning ใน MVP) เพื่อประเมินความเสี่ยงการเกิดโรคแทรกซ้อนที่อยู่ในขอบเขต (ไตวายเรื้อรัง N18.3–N18.9,
โรคหัวใจ I20–I25, โรคหลอดเลือดสมอง I60–I69) แล้วแสดงผลเป็น flag/สัญญาณเตือนที่มองเห็นได้ชัดเจน
บนหน้าจอของแพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD ต่อผู้ป่วยรายบุคคล เพื่อสนับสนุนการตัดสินใจทางคลินิก
เพิ่มเติมจากนี้ แพทย์/พยาบาลผู้ดูแลผู้ป่วยรายนั้น (เฉพาะผู้ป่วยที่อยู่ในความดูแลของตนตาม NFR-02)
ยืนยันหรือแก้ไข (override) ผลการประเมินความเสี่ยงที่ระบบประมวลผลอัตโนมัติได้ เช่น กรณีเห็นว่าผล flag
อัตโนมัติไม่สอดคล้องกับการประเมินทางคลินิกจริง สิทธิ์นี้ครอบคลุมเฉพาะผลการวิเคราะห์ความเสี่ยงเท่านั้น
ไม่ครอบคลุมการแก้ไขประวัติวินิจฉัย (FR-01) หรือผลตรวจ lab (FR-02) ซึ่งยังคงเป็นข้อมูลอ่านอย่างเดียว
และการแก้ไข/ยืนยันทุกครั้งต้องบันทึก audit log ตาม NFR-06 ไม่ใช่สิทธิ์ของ Admin (ดูฟีเจอร์ที่ 7)

- รหัส FR/NFR ที่เกี่ยวข้อง:
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-03]],
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-04]],
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-16]],
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-01]],
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-02]]
- บทบาทผู้ใช้: แพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD
- ระดับความสำคัญ (MoSCoW): Must have

## 3. ค้นหา/เลือกผู้ป่วยในความดูแล

แพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD ค้นหาผู้ป่วยเฉพาะรายด้วยเลขประจำตัวผู้ป่วย (HN) รูปแบบตัวเลขล้วน
7 หลักเท่านั้น (ไม่รองรับการค้นหาด้วยชื่ออีกต่อไป) และ/หรือเรียกดูรายชื่อผู้ป่วย NCD ทั้งหมดที่อยู่ใน
ความดูแลของตนเอง (assignment ระดับรายผู้ป่วย ไม่ใช่การมองเห็นตามแผนก/หน่วยงานที่สังกัด — ไม่บังคับ
ต้องค้นหาก่อนเสมอ) เพื่อเลือกผู้ป่วยรายบุคคลก่อนเข้าดูประวัติการวินิจฉัย (ฟีเจอร์ที่ 1) และผลวิเคราะห์
ความเสี่ยงโรคแทรกซ้อน (ฟีเจอร์ที่ 2) เป็นขั้นตอนแรกสุดของ journey ก่อนเข้าถึงข้อมูลผู้ป่วยรายบุคคลใดๆ
ทั้งหมด ระบบต้องไม่แสดงผู้ป่วยที่ไม่ได้อยู่ในความดูแลของผู้ใช้งานคนนั้น การตรวจสอบว่ากรอก HN ไม่ครบ
7 หลัก หรือค้นหาด้วย HN ที่ครบ 7 หลักแล้วแต่ไม่พบผู้ป่วยที่ตรงกัน เกิดขึ้น**หลังผู้ใช้กดค้นหาแล้วเท่านั้น**
(ไม่ใช่แบบ real-time ระหว่างพิมพ์) โดยระบบต้องแจ้งเตือนผู้ใช้งานและให้กรอกค้นหาใหม่ได้ทันที โดยไม่บล็อก
การเรียกดูรายชื่อทั้งหมด

- รหัส FR/NFR ที่เกี่ยวข้อง:
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-05]],
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-06]],
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-02]]
- บทบาทผู้ใช้: แพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD
- ระดับความสำคัญ (MoSCoW): Must have

## 4. คุ้มครองข้อมูลส่วนบุคคลของผู้ป่วยตาม PDPA

ระบบต้องประมวลผลข้อมูลส่วนบุคคล/ข้อมูลสุขภาพของผู้ป่วยที่ใช้ในฟีเจอร์ที่ 1-3 (ประวัติวินิจฉัย, ผลตรวจ
lab, ผลวิเคราะห์ความเสี่ยง, รายชื่อผู้ป่วย) ให้สอดคล้องกับพระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ.
2562 (PDPA) ครอบคลุม: จำกัดการประมวลผลเฉพาะเท่าที่จำเป็นตามวัตถุประสงค์การดูแลรักษา (lawful basis),
เข้ารหัสข้อมูลทั้งขณะจัดเก็บและส่งผ่านเครือข่าย, จำกัดระยะเวลาเก็บรักษาและรองรับการลบข้อมูล, บันทึก
ร่องรอยการเข้าถึงข้อมูล (audit log), รองรับคำขอใช้สิทธิของเจ้าของข้อมูล (เข้าถึง/สำเนา/แก้ไข/ลบ/คัดค้าน)
และสนับสนุนข้อมูลสำหรับกระบวนการแจ้งเหตุละเมิดข้อมูลส่วนบุคคล เป็นข้อกำหนดเชิง compliance ที่ครอบคลุม
ทั้งระบบ ไม่ผูกกับฟีเจอร์ใดฟีเจอร์หนึ่งโดยเฉพาะ (ดู [[20260921-01-pdpa-data-protection-compliance]])

- รหัส FR/NFR ที่เกี่ยวข้อง:

  [[20260921-01-pdpa-data-protection-compliance#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-04]],
  [[20260921-01-pdpa-data-protection-compliance#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-05]],

- บทบาทผู้ใช้: แพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD (ในฐานะผู้ประมวลผลข้อมูล — เอกสาร PDPA ไม่ได้เพิ่มบทบาท
  ใหม่)

  Must have แม้ NFR-05/NFR-07/NFR-08 จะเป็นระดับกลาง/Should have ก็ตาม)

หมายเหตุการจัดกลุ่ม (ต้องให้ผู้ใช้ยืนยัน): ฟีเจอร์นี้รวม NFR-03–NFR-08 ไว้เป็นฟีเจอร์เดียวแทนการกระจาย
เข้าไปในฟีเจอร์ที่ 1-3 เพราะ spec ต้นทาง ([[20260921-01-pdpa-data-protection-compliance]]) แยกเป็น
เอกสารข้ามฟีเจอร์เองโดยตั้งใจให้ครอบคลุมทั้งระบบ ไม่ผูกกับฟีเจอร์ใดฟีเจอร์หนึ่ง — การจัดกลุ่มนี้เป็น

ว่าเห็นด้วยกับการรวมเป็นฟีเจอร์เดียว หรือต้องการให้กระจาย NFR-03/NFR-04/NFR-06 (พื้นฐาน) เข้าไปในฟีเจอร์
ที่ 1-3 แทน (คล้ายกับที่ NFR-01/NFR-02 ถูกใส่ไว้ในทุกฟีเจอร์อยู่แล้ว)

## 5. รับประกันคุณภาพเชิงปฏิบัติการของระบบ (Performance, Availability, Clinical Safety, Session Security, Accessibility, Compatibility, Interoperability)

ระบบต้องรักษามาตรฐานคุณภาพเชิงปฏิบัติการที่ครอบคลุมทุกฟีเจอร์ (ฟีเจอร์ที่ 1-4 ข้างต้น) ไม่ผูกกับฟีเจอร์
ใดฟีเจอร์หนึ่งโดยเฉพาะ ได้แก่: หน้าจอค้นหา/ประวัติวินิจฉัย/ผลตรวจ lab/ผลวิเคราะห์ความเสี่ยงต้องตอบสนอง
ภายในน้อยกว่า 2 วินาที (Performance), อ้างอิง SLA มาตรฐานของ Firebase/Google Cloud เป็นเป้าหมาย
uptime (Availability), การจับคู่โรคหลัก→โรคแทรกซ้อนและ threshold ค่า lab ที่ใช้ใน Risk Rule Engine
ต้องผ่านการยืนยันจากแพทย์ผู้เชี่ยวชาญก่อน deploy ทุกครั้งเสมอเป็นข้อกำหนดถาวร (Clinical Safety
Validation), ระบบต้อง auto-logout เมื่อไม่มีการใช้งานเกิน 30 นาที (Session Timeout), ห้ามใช้สีเป็น
สัญญาณเดียวในการสื่อความหมาย ต้องมีข้อความกำกับคู่กับสีเสมอโดยเฉพาะการแสดง flag ความเสี่ยง
(Accessibility), Firestore Security Rules ที่ควบคุมสิทธิ์ต้องมี automated test ผ่าน Firebase
Emulator Suite ครอบคลุมทุกกรณีสิทธิ์ก่อนใช้กับข้อมูลผู้ป่วยจริงเสมอ (Security Rules Verification),
รองรับ browser หลักเวอร์ชันล่าสุด (Chrome/Edge/Firefox) บน desktop/tablet (Browser/Device
Compatibility) และบันทึกไว้เป็นประเด็นรอตัดสินใจสำหรับการพิจารณามาตรฐาน HL7/FHIR เมื่อเชื่อมต่อ HOSxP
จริงในอนาคต (Interoperability — future, ยังไม่ใช่ข้อกำหนดบังคับของ MVP)

- รหัส FR/NFR ที่เกี่ยวข้อง:
  [[20260922-01-operational-quality-nfr#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-09]],
  [[20260922-01-operational-quality-nfr#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-10]],
  [[20260922-01-operational-quality-nfr#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-11]],
  [[20260922-01-operational-quality-nfr#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-12]],
  [[20260922-01-operational-quality-nfr#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-13]],
  [[20260922-01-operational-quality-nfr#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-14]],
  [[20260922-01-operational-quality-nfr#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-15]],
  [[20260922-01-operational-quality-nfr#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-16]]
  (Won't have — out of scope เฟสนี้ทั้งหมด ยืนยันโดยผู้ใช้แล้ว ดูหมายเหตุด้านล่าง)
- บทบาทผู้ใช้: แพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD (spec นี้ไม่ได้เพิ่มบทบาทใหม่ เพิ่มเงื่อนไขเชิงคุณภาพที่
  ครอบคลุมการใช้งานของบทบาทที่มีอยู่แล้วเท่านั้น)
- ระดับความสำคัญ (MoSCoW): Must have (NFR-09/NFR-11/NFR-12/NFR-14 อยู่ในระดับสูง จึงทำให้ทั้งฟีเจอร์
  เป็น Must have แม้ NFR-10/NFR-13/NFR-15 จะเป็นระดับกลาง/Should have ก็ตาม — NFR-16 ถูกกำหนดเป็น
  Won't have แยกต่างหากเป็นรายรหัส ไม่นับรวมในการคำนวณระดับของทั้งฟีเจอร์)

หมายเหตุการจัดกลุ่ม (ตามแบบฟีเจอร์ที่ 4/PDPA): ฟีเจอร์นี้รวม NFR-09–NFR-16 ไว้เป็นฟีเจอร์เดียวแทนการ
กระจายเข้าไปในฟีเจอร์ที่ 1-4 เพราะ spec ต้นทาง ([[20260922-01-operational-quality-nfr]]) ระบุไว้
ชัดเจนว่าเป็นข้อกำหนดเชิง cross-cutting ที่ครอบคลุมทั้งระบบด้วยเหตุผลเดียวกับที่ PDPA เคยแยกเป็นเอกสาร
ของตัวเองมาก่อน (เทียบเท่าฟีเจอร์ที่ 4) — สอดคล้องกับ pattern เดิมของเอกสารนี้

หมายเหตุ (NFR-16 — ยืนยันโดยผู้ใช้แล้ว): NFR-16 (Interoperability — future) จัดเป็นระดับ "ต่ำ" ใน
[[backlog]] ซึ่งตามกฎ mapping ตายตัวของเอกสารนี้จะ map เป็น Could have โดยอัตโนมัติ แต่เนื้อหาใน
[[20260922-01-operational-quality-nfr#นอกขอบเขต (Out of scope) ของเอกสารนี้|หัวข้อนอกขอบเขต]]
ของ spec ต้นทางระบุไว้ชัดเจนว่า "ยังคงนอกขอบเขต MVP" และ "บันทึกไว้เป็นประเด็นรอตัดสินใจ ยังไม่ใช่
ข้อกำหนดบังคับของระบบในขณะนี้" จึงถามผู้ใช้ว่าควรกำหนดเป็น Could have ตามกฎ หรือ Won't have (เลื่อน
ออกจากขอบเขตเฟสนี้ทั้งหมด) — **ผู้ใช้ยืนยันแล้วว่าให้กำหนด NFR-16 เป็น Won't have** ตรงกับเนื้อหา
"นอกขอบเขต" ของ spec ต้นทาง การกำหนด Won't have นี้เป็นระดับของรหัส NFR-16 เพียงรหัสเดียว ไม่กระทบ
ระดับ Must have ของทั้งฟีเจอร์ที่ 5 ซึ่งยังคงเป็น Must have จากรหัสระดับสูงอื่น (NFR-09/NFR-11/
NFR-12/NFR-14) ที่อยู่ในฟีเจอร์เดียวกัน

## 6. สมัครบัญชี เข้าสู่ระบบ และจัดการรหัสผ่านด้วยอีเมล (Authentication)

ผู้ใช้งาน (แพทย์/พยาบาล) สมัครบัญชีใหม่ได้เองด้วยอีเมล/รหัสผ่าน (self sign-up) ผ่าน Firebase
Authentication โดยบัญชีที่สมัครใหม่จะมี `isActive = false` และยังไม่มี role กำหนด จนกว่า **Admin**
จะอนุมัติผ่านหน้าจอในระบบ (FR-11 — แทนที่กลไกเดิมที่เคยระบุว่าดำเนินการผ่าน Firebase Console/
Firestore โดยตรง ดูฟีเจอร์ที่ 7) หลังสมัคร ระบบจะส่งอีเมลยืนยันตัวตน (email verification) ที่ผู้ใช้ต้อง
ยืนยันให้เสร็จก่อนเข้าใช้งานฟีเจอร์อื่นของระบบได้ ผู้ใช้ที่มีบัญชีอยู่แล้วเข้าสู่ระบบด้วยอีเมล/รหัสผ่าน
และสามารถขอรีเซ็ตรหัสผ่านทางอีเมลได้เมื่อลืมรหัสผ่าน ทุกขั้นตอน (เข้าสู่ระบบผิดพลาด, สมัครด้วยอีเมล
ซ้ำ, ขอรีเซ็ตรหัสผ่าน) ต้องไม่เปิดเผยว่าอีเมลใดมีบัญชีอยู่ในระบบหรือไม่ (account enumeration
prevention) และรหัสผ่านที่ตั้ง/รีเซ็ตต้องเป็นไปตามนโยบายความซับซ้อนขั้นต่ำเสมอ ฟีเจอร์นี้เป็น
precondition ก่อนฟีเจอร์ที่ 1-5 ทั้งหมด (ต้องเข้าสู่ระบบและยืนยันอีเมลสำเร็จก่อน จึงจะเริ่ม journey
ค้นหา/ดูข้อมูลผู้ป่วยได้ — ดู [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-02]]
ที่ยังคงควบคุมสิทธิ์เข้าถึงข้อมูลผู้ป่วยแยกต่างหากหลังเข้าสู่ระบบสำเร็จแล้ว)

- บทบาทผู้ใช้: แพทย์/พยาบาลผู้สมัครบัญชี/เข้าสู่ระบบ (Admin เป็นผู้อนุมัติบัญชี/กำหนด role ผ่านหน้าจอ

## 7. จัดการบัญชีผู้ใช้งาน สิทธิ์ และการมอบหมายผู้ป่วย (Admin)

**Admin** เป็นบทบาทใหม่ในระบบ (role ที่ 3 ควบคู่แพทย์/พยาบาล) มีหน้าจอในระบบสำหรับดำเนินการทั้งหมด
ต่อไปนี้: อนุมัติบัญชีผู้ใช้งานใหม่ที่สมัครเอง (กำหนด role แพทย์/พยาบาล พร้อมเปิดใช้งาน
`isActive = true`) แทนที่กลไกเดิมที่เคยดำเนินการผ่าน Firebase Console/Firestore โดยตรง, เปลี่ยน role
ของผู้ใช้งานที่เคยอนุมัติแล้ว, ระงับ (`isActive = false`) หรือเปิดใช้งาน (`isActive = true`) บัญชี
ภายหลัง (ผู้ใช้งานที่ถูกระงับต้องไม่สามารถเข้าถึงข้อมูลผู้ป่วยใดๆ ได้ทันที), มอบหมาย/ยกเลิกการมอบหมาย
ผู้ป่วยให้แพทย์/พยาบาล (จัดการ `patientAssignments` ซึ่งเป็นเงื่อนไข "อยู่ในความดูแล" ที่ควบคุมการ
มองเห็นผู้ป่วยของแพทย์/พยาบาลตามฟีเจอร์ที่ 3) และดูประวัติการวินิจฉัย ผลตรวจ lab และผลวิเคราะห์
ความเสี่ยงโรคแทรกซ้อนของผู้ป่วย**ทุกราย**ในระบบแบบอ่านอย่างเดียว โดยไม่ต้องมี PatientAssignment
เป็นของตนเอง (ต่างจากแพทย์/พยาบาลที่จำกัดเฉพาะผู้ป่วยที่ได้รับมอบหมายตาม NFR-02) ทุกครั้งที่ Admin
เข้าถึงข้อมูลผู้ป่วยรายบุคคลต้องบันทึก audit log แบบ fail-safe ก่อนเสมอ (บันทึก log ก่อนคืนข้อมูล
หากบันทึกไม่สำเร็จต้องปฏิเสธการเข้าถึง) Admin ไม่มีสิทธิ์แก้ไขข้อมูลทางคลินิกใดๆ (ประวัติวินิจฉัย,
ผล lab, ผลวิเคราะห์ความเสี่ยง) สิทธิ์แก้ไข/ยืนยันผลวิเคราะห์ความเสี่ยงยังคงเป็นของแพทย์/พยาบาลตาม
ฟีเจอร์ที่ 2 (FR-16) เท่านั้น การสร้างบัญชี Admin คนแรก (bootstrap) ยังคงดำเนินการผ่าน Firebase
Console/Firestore โดยตรง อยู่นอกขอบเขตของฟีเจอร์นี้

- รหัส FR/NFR ที่เกี่ยวข้อง:
  [[20260924-01-admin-role-account-management#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-11]],
  [[20260924-01-admin-role-account-management#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-12]],
