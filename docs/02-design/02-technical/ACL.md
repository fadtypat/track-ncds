## บทบาท

ผู้ใช้ 2 กลุ่ม เก็บเป็น 3 ค่า `role` ใน `users/{uid}` (Firestore เป็น source of truth เดียว ไม่ใช้
Custom Claims — [[technology-stack]] decision area 7/18)

| กลุ่ม | `role` | ได้มาอย่างไร |
| --- | --- | --- |
| ผู้ใช้งานทางคลินิก | `"แพทย์"`, `"พยาบาล"` | Admin อนุมัติบัญชีที่สมัครเอง (FR-11) หรือเปลี่ยน role (FR-12) |
| ผู้ดูแลระบบ | `"admin"` | Admin คนอื่นเปลี่ยน role (FR-12); Admin คนแรกตั้งผ่าน Firebase Console/Firestore โดยตรง |
| (ไม่ใช่บทบาท) ผู้สมัคร/บัญชีรออนุมัติ | ไม่มีค่า, `isActive=false` | สมัครเอง (FR-08) — สร้างโดย Cloud Function `signUpUser` |

## เงื่อนไขพื้นฐานก่อนใช้สิทธิ์ใดๆ ของบทบาท

ทุก operation ยกเว้น Operation 7–9 ต้องผ่านครบทุกข้อ (Operation ร่วม Access Control ใน [[api-spec]]):

1. มี Firebase ID token ที่ถูกต้อง
2. `email_verified == true` ใน token (FR-09, decision area 19)
3. `users/{uid}.role` เป็นหนึ่งในบทบาทที่ operation นั้นอนุญาต
4. `users/{uid}.isActive == true` (NFR-02)

ไม่ผ่านข้อใดข้อหนึ่ง = ปฏิเสธ (fail-closed) — บัญชีรออนุมัติ/ถูกระงับจึงถูกปฏิเสธทุก operation โดยอัตโนมัติ

## กรณีทดสอบบังคับ (NFR-14)

Security Rules และ shared helper ต้องมี automated test ครอบคลุมอย่างน้อย:

1. ผู้ใช้ไม่มี PatientAssignment ใดเลย
2. ผู้ใช้มี PatientAssignment บางราย — ต้องไม่เห็นผู้ป่วยรายอื่น
3. บัญชีถูกระงับ (`isActive=false`)
4. บัญชียังไม่ยืนยันอีเมล (`email_verified=false`) แม้ role/isActive/assignment ถูกต้อง
5. บัญชีรออนุมัติ (ไม่มี role)
6. Admin อ่าน Op.1/2/3 ของผู้ป่วยที่ไม่ได้มอบหมายได้ และมี audit log `isAdminAccess=true`
7. Admin เรียก Op.16 หรือเขียนข้อมูลทางคลินิก — ถูกปฏิเสธ
8. Admin แก้ role/isActive ของตนเอง — ถูกปฏิเสธ
9. แพทย์/พยาบาลเรียก Op.10–15 — ถูกปฏิเสธ

## ประเด็นรอตัดสินใจ

- (2026-09-25) Op.4 และ Op.16 ยังระบุว่า "ต้องมี PatientAssignment" — หลังเลิกใช้การมอบหมาย ควรเปิดให้ทุกรายเหมือน Op.0–3 หรือไม่

- Admin ควรสืบค้น audit trail (Op.5) ได้หรือไม่ (จาก [[api-spec#ประเด็นรอตัดสินใจ|api-spec]])
- ควรจำกัดสิทธิ์ Op.4/Op.5 ของแพทย์/พยาบาลเพิ่มเติมหรือไม่ (เช่น เฉพาะเจ้าหน้าที่ PDPA)
- FR-16 override ซ้ำได้กี่ครั้ง และใครดูประวัติการ override ได้
