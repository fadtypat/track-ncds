# คุณภาพเชิงปฏิบัติการของระบบ (Operational Quality — Performance, Availability, Clinical Safety, Security, Usability, Compatibility, Interoperability)

## บทนำ

เอกสารนี้กำหนดกลุ่มความต้องการที่ไม่ใช่เชิงฟังก์ชัน (NFR) ด้าน **คุณภาพเชิงปฏิบัติการ
(operational quality)** ของระบบ ซึ่งก่อนหน้านี้ยังไม่เคยถูกระบุไว้ที่ใดในโปรเจกต์เลย —
[[20260917-01-patient-ncd-history-lab-complication-risk]] มีเฉพาะ NFR-01 (แหล่งข้อมูล/Integration)
และ NFR-02 (Security / Access Control ระดับ role + patient) ส่วน
[[20260921-01-pdpa-data-protection-compliance]] มีเฉพาะ NFR-03–NFR-08 ด้าน PDPA/compliance เท่านั้น
ยังไม่มี NFR ด้าน performance, availability, clinical safety, session security, usability/
accessibility, browser compatibility หรือ interoperability เลยแม้แต่ข้อเดียว — ช่องว่างนี้ถูกพบระหว่าง
การวิเคราะห์ช่องว่าง NFR ร่วมกับผู้ใช้หลายรอบ และผู้ใช้ยืนยันเนื้อหา/ระดับความสำคัญของทั้ง 8 รายการ
ด้านล่างแล้วทุกข้อ

เอกสารนี้แยกออกจาก [[20260917-01-patient-ncd-history-lab-complication-risk]] และ
[[20260921-01-pdpa-data-protection-compliance]] ด้วยเหตุผลเดียวกับที่ PDPA เคยแยกเป็นเอกสารของตัวเอง
(ดูหัวข้อ "สมมติฐาน" ของ [[20260921-01-pdpa-data-protection-compliance]]) คือ **operational quality
เป็นข้อกำหนดเชิง cross-cutting ที่ครอบคลุมทั้งระบบ ไม่ผูกกับฟีเจอร์ใดฟีเจอร์หนึ่งโดยเฉพาะ**
(ครอบคลุมทั้ง FR-01–FR-06 ของเอกสารต้นทาง และเชื่อมโยงกับ NFR-02/NFR-06 ของ PDPA ด้วย) การแยกเอกสาร
ทำให้ฟีเจอร์อื่นที่จะเพิ่มเข้ามาในอนาคตสามารถอ้างอิงข้อกำหนดชุดนี้ร่วมกันได้โดยไม่ต้องแก้ไขเอกสารเดิม
ทั้งสองฉบับซ้ำ

## ขอบเขต

### ข้อมูล/ฟีเจอร์ที่อยู่ในขอบเขตของเอกสารนี้

- หน้าจอค้นหา/แสดงรายชื่อผู้ป่วย, ประวัติการวินิจฉัย, ผลตรวจ lab และผลวิเคราะห์ความเสี่ยงโรคแทรกซ้อน
  (อ้างอิง FR-01–FR-06 ของ [[20260917-01-patient-ncd-history-lab-complication-risk]])
- Risk Rule Engine ที่ใช้จับคู่โรคหลัก→โรคแทรกซ้อนและ threshold ค่า lab (อ้างอิง FR-03)
- กลไกควบคุมสิทธิ์ 2 ระดับ (role-level + patient-level) ที่ [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-02]] กำหนดไว้แล้ว —
  เอกสารนี้เพิ่มมิติ "เวลาที่เข้าถึงได้" (session timeout) และ "การยืนยันด้วย automated test" ซึ่งเป็น
  คนละมิติจาก "ใครเข้าถึงได้" ที่ NFR-02 กำหนดไว้เดิม
- แนวทาง hosting/deployment ที่ [[technology-stack]] ตัดสินใจไว้แล้ว
  (Firebase-native stack) ใช้เป็นบริบทประกอบเหตุผลของ NFR ด้าน availability/security rules
  verification/browser compatibility ในเอกสารนี้

### บทบาทที่เกี่ยวข้อง

แพทย์และพยาบาลผู้ดูแลผู้ป่วย NCD (บทบาทเดียวกับที่กำหนดไว้แล้วใน
[[20260917-01-patient-ncd-history-lab-complication-risk#บทบาทผู้ใช้ในขอบเขตนี้|บทบาทผู้ใช้ในขอบเขตนี้]])
เอกสารนี้ไม่ได้เพิ่มบทบาทใหม่ แต่เพิ่มเงื่อนไขเชิงคุณภาพที่ครอบคลุมการใช้งานของบทบาทที่มีอยู่แล้ว

### นอกขอบเขต (Out of scope) ของเอกสารนี้

- การตั้งค่า SLA ตัวเลขเพิ่มเติมนอกเหนือจากมาตรฐานของ Firebase/Google Cloud (ดู NFR-10) —
  ไม่กำหนด SLA ที่เข้มงวดกว่าที่ผู้ให้บริการ platform รับประกันไว้
- การเชื่อมต่อจริงกับ HOSxP และมาตรฐาน HL7/FHIR (ดู NFR-16) — ยังคงนอกขอบเขต MVP เช่นเดียวกับที่
  [[20260917-01-patient-ncd-history-lab-complication-risk#นอกขอบเขต (Out of scope) ของเอกสารนี้|
  หัวข้อนอกขอบเขตของเอกสารต้นทาง]] ระบุไว้แล้ว บันทึกไว้ในเอกสารนี้เพียงเป็นประเด็นรอตัดสินใจ
  ไม่ใช่ NFR บังคับ
- รายละเอียดเชิงเทคนิคของการทดสอบ performance/load (เครื่องมือ, environment, threshold การรับ/ไม่รับ
  ผลทดสอบ) — เป็นหน้าที่ของ `docs/03-testing/01-test-plan/test-plan.md` ที่จะออกแบบต่อจาก NFR-09
  ในเอกสารนี้ ([[test-plan]] เคยบันทึกไว้แล้วว่า "ไม่มี NFR
  ด้าน performance ระบุไว้ใน backlog ณ ปัจจุบัน" — เอกสารนี้ปิดช่องว่างนั้น)
- ขั้นตอนการยืนยันทางคลินิกของแพทย์ผู้เชี่ยวชาญ (แบบฟอร์ม, workflow การอนุมัติ, ผู้มีอำนาจลงนาม) —
  NFR-11 กำหนดเพียงว่า "ต้องมีการยืนยันก่อน deploy เสมอ" ส่วนกระบวนการจริงเป็นรายละเอียดเชิงองค์กร/
  operational ที่ควรกำหนดต่อในระดับ detailed-design หรือกระบวนการขององค์กร ไม่ใช่หน้าที่ของเอกสารนี้

## ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)

| รหัส | ด้าน | ความต้องการ |
| --- | --- | --- |
| NFR-09 | Performance | หน้าจอค้นหา/แสดงรายชื่อผู้ป่วย, ประวัติการวินิจฉัย, ผลตรวจ lab และผลวิเคราะห์ความเสี่ยงโรคแทรกซ้อน (อ้างอิง FR-01–FR-06 ของ [[20260917-01-patient-ncd-history-lab-complication-risk]]) ต้องตอบสนอง (แสดงผลข้อมูลครบถ้วนบนหน้าจอ) ภายใน **น้อยกว่า 2 วินาที** นับจากผู้ใช้งานสั่งการ (ค้นหา/เปิดดู/เลือกผู้ป่วย) จนถึงข้อมูลปรากฏครบ |
| NFR-10 | Availability | ระบบอ้างอิง SLA มาตรฐานของ Firebase/Google Cloud (ตามที่ [[technology-stack]] ตัดสินใจเลือกเป็น hosting platform หลัก) เป็นเป้าหมาย uptime ของระบบ **ไม่ตั้ง SLA เพิ่มเติมที่เข้มงวดกว่ามาตรฐานของผู้ให้บริการเอง** |
| NFR-11 | Clinical Safety Validation | การจับคู่โรคหลัก→โรคแทรกซ้อน (ตามหัวข้อสมมติฐานของ [[20260917-01-patient-ncd-history-lab-complication-risk#สมมติฐาน (Assumptions) — โปรดตรวจทานอีกครั้ง\|สมมติฐาน]]) และค่า threshold ผลตรวจ lab ที่ใช้ใน Risk Rule Engine (อ้างอิง FR-03) **ทุกครั้งที่มีการเพิ่มหรือแก้ไข ต้องผ่านการยืนยันจากแพทย์ผู้เชี่ยวชาญก่อน deploy ใช้งานจริงเสมอ** ข้อกำหนดนี้เป็น**ข้อกำหนดถาวร** (บังคับใช้กับทุกครั้งที่มีการเปลี่ยนแปลง rule ในอนาคต) ไม่ใช่ gate ที่ตรวจสอบเพียงครั้งเดียวตอนเริ่มโครงการ |
| NFR-12 | Session Timeout | ระบบต้อง auto-logout ผู้ใช้งานโดยอัตโนมัติเมื่อไม่มีการใช้งาน (inactivity) เกิน **30 นาที** ข้อกำหนดนี้เชื่อมโยงกับ [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-02]] เรื่อง access control แต่เป็นคนละมิติกัน — NFR-02 ควบคุม "ใครเข้าถึงได้" ส่วน NFR-12 ควบคุม "เข้าถึงได้ในช่วงเวลาใด" |
| NFR-13 | Accessibility | ระบบต้อง**ไม่ใช้สีเป็นสัญญาณเดียว**ในการสื่อความหมายบนหน้าจอ ต้องมีข้อความกำกับคู่กับสีเสมอ โดยเฉพาะการแสดง flag ความเสี่ยงโรคแทรกซ้อน (อ้างอิง FR-04) ที่ต้องมีข้อความระบุระดับความเสี่ยงกำกับ ไม่ใช่ใช้สีเพียงอย่างเดียวให้ผู้ใช้ตีความเอง |
| NFR-14 | Security Rules Verification | Firestore Security Rules ที่ควบคุมสิทธิ์ 2 ระดับ (role-level + patient-level ตาม [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-02]] และตามที่ [[technology-stack#ความเสี่ยงที่ต้องพิจารณาเพิ่มเติม (สำคัญ — ผู้ใช้รับทราบและยืนยันให้ดำเนินการต่อแล้ว)\|technology-stack ระบุความเสี่ยงไว้แล้ว]]) ต้องมี **automated test ผ่าน Firebase Emulator Suite ครอบคลุมทุกกรณีสิทธิ์** ก่อนนำไปใช้กับข้อมูลผู้ป่วยจริงเสมอ |
| NFR-15 | Browser/Device Compatibility | ระบบต้องรองรับ browser หลักเวอร์ชันล่าสุด (**Chrome, Edge, Firefox**) บนอุปกรณ์ **desktop และ tablet** ที่คลินิก/โรงพยาบาลส่งเสริมสุขภาพตำบล (รพ.สต.) ใช้งานจริง |
| NFR-16 | Interoperability (future) | เมื่อมีการเชื่อมต่อกับระบบ HOSxP จริงในอนาคต (ปัจจุบันอยู่นอกขอบเขต MVP ตาม [[20260917-01-patient-ncd-history-lab-complication-risk#นอกขอบเขต (Out of scope) ของเอกสารนี้\|หัวข้อนอกขอบเขตของเอกสารต้นทาง]]) ให้พิจารณามาตรฐานการแลกเปลี่ยนข้อมูลสุขภาพ เช่น HL7/FHIR ประกอบการออกแบบ — บันทึกไว้เป็น**ประเด็นรอตัดสินใจ** ยังไม่ใช่ข้อกำหนดบังคับของระบบในขณะนี้ |

ระดับความสำคัญ (สูง/กลาง/ต่ำ ใช้จัดกลุ่มใน [[backlog]] ตามรูปแบบเดิมของโปรเจกต์ — ตาราง NFR ด้านบน
ไม่มีคอลัมน์นี้โดยตรง สอดคล้องกับรูปแบบที่ใช้ใน [[20260917-01-patient-ncd-history-lab-complication-risk]]
และ [[20260921-01-pdpa-data-protection-compliance]] — ผู้ใช้ยืนยันเนื้อหาและระดับความสำคัญของทุกข้อ
แล้วระหว่างการวิเคราะห์ช่องว่าง NFR หลายรอบ ก่อนส่งต่อให้เขียนเป็นเอกสารนี้):

- **NFR-09 (Performance) = สูง** — ต้องมีใน MVP เพราะกระทบประสบการณ์การตัดสินใจทางคลินิกโดยตรงของ
  แพทย์/พยาบาลในทุกฟีเจอร์หลัก (FR-01–FR-06)
- **NFR-10 (Availability) = กลาง** — อ้างอิง SLA มาตรฐานของ platform ที่เลือกไว้แล้วโดยไม่ต้องตั้งค่า/
  ดำเนินการเพิ่มเติมใน MVP แรก
- **NFR-11 (Clinical Safety Validation) = สูง** — ผู้ใช้ระบุว่าเป็นระดับความสำคัญสูงสุดในบรรดา NFR
  ทั้งชุดนี้ (เนื่องจากกระทบความปลอดภัยทางคลินิกของผู้ป่วยโดยตรงหากค่า threshold/การจับคู่โรคผิดพลาด)
  ตามมาตราส่วน สูง/กลาง/ต่ำ ของโปรเจกต์ จัดอยู่ในกลุ่ม **สูง** และควรได้รับการปฏิบัติตามเป็นลำดับแรก
  ในกลุ่มสูงเมื่อวางแผน release/test เนื่องจากเป็นข้อกำหนดถาวร (permanent gate) ไม่ใช่ตรวจครั้งเดียว
- **NFR-12 (Session Timeout) = สูง** — ต้องมีใน MVP เพราะเป็นกลไกความปลอดภัยพื้นฐานที่ป้องกันการเข้าถึง
  ข้อมูลผู้ป่วยโดยไม่ได้รับอนุญาตเมื่อผู้ใช้ละทิ้งอุปกรณ์ เชื่อมโยงโดยตรงกับ NFR-02 ที่เป็นระดับสูงอยู่แล้ว
- **NFR-13 (Accessibility) = กลาง** — สำคัญต่อความถูกต้องในการสื่อสารผลความเสี่ยง แต่ไม่ใช่กลไกความ
  ปลอดภัย/ป้องกันข้อมูลรั่วไหลโดยตรงเหมือนกลุ่มสูงข้างต้น
- **NFR-14 (Security Rules Verification) = สูง** — ต้องมีใน MVP ก่อนใช้กับข้อมูลผู้ป่วยจริงเสมอ
  เพราะ [[technology-stack#ความเสี่ยงที่ต้องพิจารณาเพิ่มเติม (สำคัญ — ผู้ใช้รับทราบและยืนยันให้ดำเนินการต่อแล้ว)\|technology-stack]] ระบุไว้แล้วว่า Security Rules ที่ตั้งค่า
  ผิดพลาดเสี่ยงทำให้ข้อมูลผู้ป่วยรั่วไหลได้ง่าย
- **NFR-15 (Browser/Device Compatibility) = กลาง** — ผู้ใช้ระบุเป็นช่วง "ต่ำ-กลาง" จัดอยู่ในกลุ่ม
  **กลาง** ตามมาตราส่วน 3 ระดับของโปรเจกต์ เพราะจำเป็นต่อการใช้งานจริงในหน้างาน แต่ไม่ใช่ความเสี่ยงเชิง
  ความปลอดภัย/คลินิกโดยตรงเท่ากลุ่มสูงข้างต้น
- **NFR-16 (Interoperability — future) = ต่ำ** — อยู่นอกขอบเขต MVP ปัจจุบันทั้งหมด บันทึกไว้เป็นประเด็น
  รอตัดสินใจสำหรับอนาคตเท่านั้น

## เอกสารที่เกี่ยวข้อง

- [[20260917-01-patient-ncd-history-lab-complication-risk]] — เอกสาร spec ต้นทางที่นิยาม FR-01–FR-06
  และ NFR-01/NFR-02 ที่ NFR-09, NFR-11, NFR-12, NFR-13, NFR-14 ในเอกสารนี้อ้างอิง/เชื่อมโยงถึง
- [[20260921-01-pdpa-data-protection-compliance]] — เอกสาร spec ด้าน PDPA ที่ใช้รูปแบบการแยกเอกสาร
  แบบ cross-cutting เดียวกันกับเอกสารนี้
- [[technology-stack]] — แหล่งอ้างอิงบริบท Firebase-native stack ที่ใช้
  ประกอบเหตุผลของ NFR-10, NFR-14, NFR-15 และเป็นที่มาของความเสี่ยง Security Rules ที่ NFR-14 ตอบสนอง
- [[test-plan]] — เคยบันทึกไว้ว่าไม่มี NFR ด้าน performance ในขอบเขตการ
  ทดสอบ ณ ขณะนั้น เอกสารนี้ปิดช่องว่างดังกล่าวด้วย NFR-09
- [[backlog]] — สรุปรวม FR/NFR ทั้งหมดของโปรเจกต์
