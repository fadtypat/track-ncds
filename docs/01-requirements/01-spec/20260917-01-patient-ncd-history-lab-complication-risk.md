# ประวัติโรค NCD ผลตรวจ Lab และการวิเคราะห์ความเสี่ยงโรคแทรกซ้อน

## บทนำ

เอกสารนี้กำหนดความต้องการของฟีเจอร์ที่ให้แพทย์/พยาบาลผู้ดูแลผู้ป่วยโรคไม่ติดต่อเรื้อรัง (NCDs)
สามารถดูประวัติการวินิจฉัยโรค NCD, ดูผลตรวจ lab ที่เกี่ยวข้องย้อนหลัง และให้ระบบช่วยวิเคราะห์
ความเสี่ยงการเกิดโรคแทรกซ้อนแบบ rule-based ตาม threshold ค่า lab มาตรฐาน เพื่อสนับสนุนการตัดสินใจ
ทางคลินิกของผู้ดูแลผู้ป่วย เป็นเอกสาร spec ฉบับแรกของโปรเจกต์นี้ จึงเริ่มรหัส FR/NFR ที่ 01

## ขอบเขต

### กลุ่มโรคหลัก (NCDs) ที่ระบบดูแล

| กลุ่มโรค | รหัส ICD-10 |
| --- | --- |
| เบาหวาน (Diabetes Mellitus) | E10–E14 |
| ความดันโลหิตสูง (Hypertension) | I10–I14 |
| ถุงลมโป่งพอง (Emphysema/COPD) | J44 |

### โรคแทรกซ้อนที่ระบบต้อง flag ความเสี่ยง

| โรคแทรกซ้อน | รหัส ICD-10 |
| --- | --- |
| ไตวายเรื้อรัง (Chronic Kidney Disease) | N18.3–N18.9 |
| โรคหัวใจ (Heart Disease) | I20–I25 |
| โรคหลอดเลือดสมอง (Stroke) | I60–I69 |

### บทบาทผู้ใช้ในขอบเขตนี้

เฉพาะ **แพทย์และพยาบาลผู้ดูแลผู้ป่วย NCD** เท่านั้นที่เป็นผู้ใช้งานฟีเจอร์นี้ (ไม่ใช่เจ้าหน้าที่คลินิก
ทุกกลุ่ม) ขอบเขตบทบาทนี้ใช้เป็นฐานของ NFR-02 ด้าน access control ด้านล่าง

### นอกขอบเขต (Out of scope) ของเอกสารนี้

- การเชื่อมต่อจริงกับระบบ HOSxP (field mapping, protocol, connection จริง) — ยังไม่ตัดสินใจ
  เพราะ `technology-stack.md` ยังไม่ถูกกำหนด (ดู NFR-01) ระบุไว้เพียงระดับหมายเหตุ
- การวิเคราะห์ความเสี่ยงด้วย AI/Machine Learning model — ขอบเขต MVP ใช้ rule-based threshold
  ตามค่า lab มาตรฐานเท่านั้น (ดู FR-03)

## สมมติฐาน (Assumptions) — โปรดตรวจทานอีกครั้ง

ผู้ใช้ให้รหัส ICD-10 มาโดยตรง แต่การจับคู่ "โรคหลัก → โรคแทรกซ้อนที่ต้องเฝ้าระวัง" ด้านล่าง
เป็นการตีความของผู้จัดทำเอกสารจากข้อมูลที่ได้รับ **ต้องให้ผู้ใช้/แพทย์ผู้เชี่ยวชาญยืนยันอีกครั้ง**
ก่อนนำไปออกแบบ rule engine เชิงเทคนิคต่อ (เช่นใน `db-spec.md`, `detailed-design/`):

| โรคหลัก (ต้นเหตุ) | โรคแทรกซ้อนที่สมมติว่าเกี่ยวข้อง |
| --- | --- |
| เบาหวาน (E10–E14) | ไตวายเรื้อรัง, โรคหัวใจ, โรคหลอดเลือดสมอง |
| ความดันโลหิตสูง (I10–I14) | ไตวายเรื้อรัง, โรคหัวใจ, โรคหลอดเลือดสมอง |
| ถุงลมโป่งพอง (J44) | โรคหัวใจ (cor pulmonale) — ยังไม่ยืนยันความเกี่ยวข้องกับไตวายเรื้อรัง/หลอดเลือดสมอง |

หมายเหตุ: threshold ค่า lab มาตรฐาน (เช่น HbA1c, eGFR, LDL, BP) ที่จะใช้ตัดสิน rule ยังไม่ได้ระบุ
ค่าตัวเลขจริงในเอกสารนี้ เพราะเป็นรายละเอียดระดับออกแบบเชิงเทคนิค (rule engine) ที่ควรกำหนดต่อใน
`docs/02-design/02-technical/detailed-design/` โดยอ้างอิงกลับมาที่ FR-03 ของเอกสารนี้

หมายเหตุเพิ่มเติมสำหรับ FR-05 (เพิ่มภายหลังจากช่องว่างที่พบระหว่างออกแบบ `api-spec.md`/`db-spec.md`):
คำว่า "อยู่ในความดูแล" ของแพทย์/พยาบาลผู้ใช้งาน ในเอกสารนี้ตีความว่าหมายถึง **assignment ระดับ
รายผู้ป่วย** (ผู้ป่วยแต่ละรายถูกมอบหมายให้อยู่ในความดูแลของแพทย์/พยาบาลคนใดคนหนึ่งหรือหลายคนโดยตรง
ในระบบ) ไม่ใช่การมองเห็นผู้ป่วยทั้งหมดตามแผนก/หน่วยงานที่สังกัด — ประเด็นนี้ยังเป็นการตีความของ
ผู้จัดทำเอกสาร **ต้องให้ผู้ใช้ยืนยันอีกครั้ง** ก่อนนำไปออกแบบ schema การ assign ผู้ป่วยจริงต่อใน
`db-spec.md`

หมายเหตุเพิ่มเติมสำหรับ FR-16 (เพิ่ม 2026-09-24 จาก requirement ดิบเพิ่มเติม "แพทย์/พยาบาล
ดูประวัติการรัษา แก้ไข การวิเคราะห์โรคได้" — **ยืนยันแล้วโดยผู้ใช้ผ่าน NEEDS_USER_INPUT เมื่อ
2026-09-24**): "แก้ไข" ตีความและยืนยันแล้วว่าหมายถึง**เฉพาะการยืนยัน/แก้ไขผลการประเมินความเสี่ยง
โรคแทรกซ้อน (FR-03/FR-04) เท่านั้น** ไม่ใช่การแก้ไขข้อมูลประวัติการวินิจฉัย (FR-01) หรือผลตรวจ lab
(FR-02) ซึ่งยังคงเป็นข้อมูลอ่านอย่างเดียวจาก HOSxP/mockup ตาม NFR-01 เช่นเดิม (การแก้ไขข้อมูลต้นทาง
เหล่านี้จะขัดแย้งกับ NFR-01 โดยตรง) ส่วน "การวิเคราะห์โรคได้" ยืนยันแล้วว่าหมายถึงการใช้งาน
FR-03/FR-04 ที่มีอยู่แล้ว ไม่ใช่ฟีเจอร์วิเคราะห์โรคใหม่

ส่วนเกณฑ์การค้นหา (**ยืนยันแล้ว 2026-09-21 ผ่าน AskUserQuestion** — แทนที่การตีความเดิมด้านล่าง):
ระบบ**บังคับให้ค้นหาผู้ป่วยเฉพาะรายด้วยเลขประจำตัวผู้ป่วย (HN) เท่านั้น** ไม่รองรับการพิมพ์ค้นหาด้วย
ชื่อผู้ป่วยอีกต่อไป ส่วนการเรียกดูรายชื่อผู้ป่วยทั้งหมดที่อยู่ในความดูแลแบบไม่ต้องพิมพ์ค้นหายังคงใช้งาน
ได้ตามเดิม (ดูรายละเอียดเงื่อนไขการค้นหาด้วย HN ที่ FR-06)

หมายเหตุอัปเดต 2026-09-25 สำหรับ FR-05/NFR-02/FR-16 (**แทนที่การตีความ "อยู่ในความดูแลระดับรายผู้ป่วย"
(PatientAssignment) ที่ระบุไว้ด้านบนทั้งหมด — ยืนยันแล้วโดยผู้ใช้**): จาก requirement ดิบเพิ่มเติม
"ไม่ต้องให้ admin จัดการการมอบหมายผู้ป่วย ให้แพทย์/พยาบาล/admin สามารถดูผู้ป่วยได้ทุกคนหลังจาก login"
ระบบ**ยกเลิกกลไก PatientAssignment (การมอบหมายผู้ป่วยรายบุคคล) ทั้งหมด** แพทย์/พยาบาล/admin ทุกคนที่
ผ่านเงื่อนไขพื้นฐาน (token ถูกต้อง, `email_verified = true`, role ที่ระบบอนุญาต, `isActive = true`)
เห็นผู้ป่วย**ทุกราย**ในระบบเหมือนกันหลังเข้าสู่ระบบ ไม่มีการจำกัดเฉพาะผู้ป่วยที่ "อยู่ในความดูแล" อีก
ต่อไป FR-05, NFR-02 และ FR-16 ด้านล่างถูกแก้ไขให้สะท้อนการเปลี่ยนแปลงนี้แล้ว (ข้อความเดิมก่อนแก้ไขอยู่
ใน git history) การเปลี่ยนแปลงนี้ยังส่งผลให้ FR-14 (Admin จัดการ PatientAssignment) ใน
[[20260924-01-admin-role-account-management]] ถูกยกเลิก และ NFR-19 (ข้อยกเว้นสำหรับบทบาท admin)
ในเอกสารเดียวกันไม่ใช่ "ข้อยกเว้น" อีกต่อไป (ดูรายละเอียดที่เอกสารนั้น) สิทธิ์ล่าสุดของทุก operation
ยึดตาม [[ACL]] เป็นแหล่งความจริงหลัก

หมายเหตุเพิ่มเติมสำหรับ FR-06 (เพิ่ม 2026-09-21 จาก requirement ดิบที่เจาะจงเงื่อนไขการค้นหาด้วย HN
— **อัปเดต 2026-09-21 ยืนยันแล้วโดยผู้ใช้ผ่าน AskUserQuestion**, แทนที่สมมติฐานเบื้องต้น 3 ข้อเดิม):

1. **ความสัมพันธ์กับการค้นหาด้วยชื่อใน FR-05 (ยืนยันแล้ว)** — ผู้ใช้ยืนยันว่า**บังคับค้นหาด้วย HN
   เท่านั้น** ไม่ใช้การค้นหาด้วยชื่ออีกต่อไป (ยกเลิกการตีความเดิมที่ว่าให้ใช้งานคู่ขนานกับการค้นหา
   ด้วยชื่อได้) FR-05 จึงถูกแก้ไขให้ตัดช่องทางค้นหาด้วยชื่อออก คงไว้เฉพาะการเรียกดูรายชื่อทั้งหมดที่
   อยู่ในความดูแล (ไม่ต้องพิมพ์ค้นหา) และการค้นหาเฉพาะรายด้วย HN (FR-06)
2. **ลักษณะการ validation (แก้ไข 2026-09-26 — ดูหมายเหตุ FR-06/FR-17 ด้านล่าง แทนที่ข้อความเดิม)** —
   เดิมผู้ใช้เคยยืนยันว่าการตรวจสอบ "ไม่ครบ 7 หลัก" เกิดขึ้นหลังกดค้นหาเท่านั้น แต่จาก requirement ดิบ
   เพิ่มเติมเรื่อง AI ช่วยอธิบายผลการค้นหา (FR-17) ผู้ใช้ยืนยันว่าต้องการให้**การตรวจสอบรูปแบบ HN/การ
   ค้นหาผู้ป่วย**ทำงานทั้งตอน "หยุดพิมพ์" (debounce) และตอน "กดค้นหา" จึงแก้ไขให้การตรวจสอบรูปแบบ HN
   และการค้นหาจริงเกิดขึ้นได้ 2 จังหวะ: (ก) เมื่อผู้ใช้หยุดพิมพ์ชั่วขณะ (debounce) และ (ข) เมื่อผู้ใช้
   กดปุ่มค้นหา ไม่ใช่หลังกดค้นหาเพียงจังหวะเดียวอีกต่อไป **(แก้ไขเพิ่มเติม 2026-09-26 รอบสอง — ยืนยัน
   แล้วโดยผู้ใช้ระหว่าง `/build-tech-stack` แทนที่ข้อความเดิมที่ผูก AI ไว้กับ 2 จังหวะนี้ด้วย)**: การ
   เรียกบริการ AI ภายนอกตาม FR-17 **ไม่ได้ทำงานทั้ง 2 จังหวะตามนี้** แต่ทำงาน**เฉพาะตอนผู้ใช้กดปุ่ม
   ค้นหาเท่านั้น** เพื่อประหยัด quota ของบริการ AI ดูรายละเอียดที่หมายเหตุ FR-17 ข้อ 3 ด้านล่าง
3. **รูปแบบ HN (ยืนยันแล้ว)** — ผู้ใช้ยืนยันตรงตามการตีความเดิมว่าเป็นตัวเลขล้วน (numeric) 7 หลัก
   ไม่รวมตัวอักษร

หมายเหตุเพิ่มเติมสำหรับ FR-17 (เพิ่ม 2026-09-26 จาก requirement ดิบเพิ่มเติม "ผมอยากให้ AI ช่วย
track-ncds ในหน้าค้นหาด้วยเลข HN พิมพ์ในช่องค้นหา พอหยุดพิมพ์ หรือกดค้นหา ให้ AI เอาคำตอบมาแสดง" —
ทุกข้อยืนยันแล้วโดยผู้ใช้ผ่านการสนทนาจริง ไม่ต้องถามซ้ำ):

1. **ขอบเขตหน้าที่ของ AI (ยืนยันแล้ว)** — AI ทำหน้าที่เพียง "อธิบายผลการค้นหาเป็นภาษาคน" 3 กรณี
   (พบผู้ป่วย / ไม่พบผู้ป่วย / กรอก HN ไม่ครบ 7 หลัก) เท่านั้น **ไม่ใช่แชตตอบคำถามอิสระ** และ
   **ไม่ใช่การแนะนำขั้นตอนทางคลินิก** (ไม่เกี่ยวข้องกับ FR-03/FR-04/FR-16 เรื่องการวิเคราะห์/ยืนยัน
   ความเสี่ยงโรคแทรกซ้อน)
2. **ข้อมูลที่ส่งให้บริการ AI (ยืนยันแล้ว)** — ห้ามส่งชื่อผู้ป่วยหรือข้อมูลระบุตัวตนใดๆ ให้บริการ AI
   ส่งได้เฉพาะเลข HN ที่ผู้ใช้พิมพ์ และผลการค้นหาแบบไม่ระบุตัวตน (สถานะพบ/ไม่พบ/HN ไม่ครบหลัก, จำนวน
   ที่พบ) รายละเอียดข้อจำกัดด้าน PDPA ดู NFR-21 ใน [[20260921-01-pdpa-data-protection-compliance]]
3. **จังหวะการทำงาน (แก้ไข 2026-09-26 รอบสอง — ยืนยันแล้วโดยผู้ใช้ระหว่าง `/build-tech-stack`, แทนที่
   ข้อความเดิมที่ระบุว่า AI ทำงานทั้ง 2 จังหวะ)** — AI ทำงาน**เฉพาะตอนผู้ใช้กดปุ่มค้นหาเท่านั้น**
   ไม่เรียก AI ตอนหยุดพิมพ์ชั่วขณะ (debounce) อีกต่อไป เหตุผล: ประหยัด quota ของบริการ AI ส่วนการ
   ตรวจสอบรูปแบบ HN และการค้นหาผู้ป่วยตาม FR-06 ยังคงทำงานทั้ง 2 จังหวะ (หยุดพิมพ์และกดค้นหา) ตามเดิม
   ไม่เปลี่ยนแปลง มีเพียงการเรียก AI เท่านั้นที่ถูกจำกัดให้ทำงานจังหวะเดียว (ดูหมายเหตุ FR-06 ข้อ 2
   ด้านบนที่แก้ไขสอดคล้องกันแล้ว)
4. **สภาพแวดล้อมที่ใช้งาน (ยืนยันแล้ว)** — ใช้บนเว็บจริง (production) ไม่ใช่แค่เครื่องนักพัฒนา
5. **ชื่อเทคโนโลยี AI (ยืนยันแล้ว)** — เอกสารนี้จงใจไม่ระบุชื่อ/ผู้ให้บริการ AI ที่เลือกใช้จริง
   (เป็นการตัดสินใจเชิงเทคโนโลยีที่จะบันทึกใน [[technology-stack]] แยกต่างหากผ่าน `/build-tech-stack`)
   ในเอกสารนี้กล่าวถึงเพียงระดับ logical ว่าเป็น "บริการ AI ภายนอก" (external AI service)
6. **ความทนทานต่อความล้มเหลว (ยืนยันแล้ว)** — หากบริการ AI ใช้งานไม่ได้/ล้มเหลว การค้นหาปกติ (FR-05/
   FR-06) ต้องยังคงใช้งานได้ตามปกติ ไม่ถูกบล็อกจากความล้มเหลวของ AI

หมายเหตุเพิ่มเติมสำหรับ FR-18 (เพิ่ม 2026-09-27 จาก requirement ดิบ "ผมอยากได้ปุ่ม ให้ AI ช่วยสรุป
จำนวน visit ที่ตรวจ lab hba1c ในปีงบประมาณ" — ทุกข้อยืนยันแล้วโดยผู้ใช้ผ่าน NEEDS_USER_INPUT เมื่อ
2026-09-27):

1. **นิยามปีงบประมาณ (ยืนยันแล้ว)** — หมายถึงปีงบประมาณราชการไทย 1 ตุลาคม–30 กันยายน (เช่น ปีงบประมาณ
   2569 = 1 ตุลาคม 2568–30 กันยายน 2569)
2. **ตำแหน่งปุ่ม/หน่วยของการสรุป (ยืนยันแล้ว)** — สรุปเป็นรายผู้ป่วยรายบุคคล ปุ่มอยู่บนการ์ดผู้ป่วยแต่ละ
   รายในหน้ารายชื่อผู้ป่วยตาม FR-05
3. **ระดับความสำคัญ (ยืนยันแล้ว)** — **กลาง** เพราะเป็นฟีเจอร์เสริมสนับสนุนการติดตาม ไม่ใช่ MVP หลักอย่าง
   FR-01/FR-02 สอดคล้องกับระดับที่ใช้กับ FR-17 ซึ่งเป็นฟีเจอร์ AI เสริมลักษณะเดียวกัน
4. **ขอบเขตงานที่คำนวณด้วยระบบ vs AI (ยืนยันแล้ว)** — ขั้นที่ 1 (หาวันที่ตรวจ HbA1c ในปีงบประมาณ) และ
   ขั้นที่ 2 (สรุปจำนวน visit และระยะห่างเป็นจำนวนวันระหว่างการตรวจแต่ละครั้ง) เป็นการคำนวณของระบบเอง
   (ไม่ใช่ AI) มีเพียงขั้นที่ 3 (เขียนสรุปเป็นภาษาคนจากตัวเลขที่คำนวณแล้ว) เท่านั้นที่ใช้บริการ AI ภายนอก
5. **สิทธิ์กดปุ่ม/เขียนผลลงฐาน (ยืนยันแล้ว — แตกต่างจาก FR-16)** — เปิดให้**แพทย์/พยาบาล/admin ทุกคน**
   กดได้ (ไม่จำกัดเฉพาะแพทย์/พยาบาลเหมือน FR-16) เพราะผู้ใช้ยืนยันว่าผลสรุปนี้เป็นเพียง**การคำนวณสถิติ**
   (จำนวนครั้งตรวจ/ระยะห่างวัน) ไม่ใช่การวินิจฉัยหรือการตัดสินใจทางคลินิก จึงไม่เข้าข่ายข้อจำกัดของ FR-16
   (override ผลวิเคราะห์ความเสี่ยง) — admin ยังคงเป็น read-only สำหรับข้อมูลทางคลินิกอื่นทั้งหมดตาม FR-15
   เหมือนเดิม ไม่เปลี่ยนแปลง
6. **กรณีไม่มีผลตรวจ HbA1c ในปีงบประมาณที่เลือก (ยืนยันแล้ว)** — ปุ่มยังกดได้ตามปกติ ระบบบันทึกผลสรุปว่า
   จำนวน visit = 0 ("ไม่มีข้อมูล") ลงฐานข้อมูลไว้เป็นหลักฐานว่าเคยตรวจสอบแล้ว ไม่ใช่ปิดปุ่ม/ซ่อนปุ่ม
7. **กรณีตรวจ HbA1c เพียงครั้งเดียวในปีงบประมาณ (ยืนยันแล้ว)** — ระบบสรุปจำนวน visit = 1 โดยไม่มีค่า
   ระยะห่างระหว่างการตรวจ (ไม่มีคู่เปรียบเทียบ) และ AI ต้องเขียนสรุปว่ายังไม่มีข้อมูลเพียงพอสำหรับประเมิน
   ความสม่ำเสมอ
8. **การเขียนผลลงฐาน/การเขียนทับ (ยืนยันแล้ว)** — ผลสรุปเก็บแยกรายผู้ป่วยต่อปีงบประมาณ ประกอบด้วยตัวเลข
   ที่คำนวณแล้ว (จำนวน visit, ระยะห่างเป็นวันแต่ละคู่), ข้อความที่ AI เขียน, ชื่อ/รุ่นโมเดล AI ที่ใช้ และ
   เวลาที่สร้างผลสรุป กดปุ่มซ้ำ = **เขียนทับผลเดิมของผู้ป่วย/ปีงบประมาณเดียวกัน ไม่เก็บประวัติ (ไม่มี
   version history)**
9. **ข้อมูลที่ส่งให้บริการ AI ภายนอก (ยืนยันแล้ว)** — จำกัดเฉพาะ**ตัวเลขสรุปที่คำนวณแล้วเท่านั้น**
   (จำนวนครั้งที่ตรวจ, ระยะห่างเป็นจำนวนวันระหว่างการตรวจแต่ละครั้ง) **ห้ามส่ง HN, ชื่อผู้ป่วย, วันที่ตรวจ
   จริง หรือค่าผล HbA1c ใดๆ ให้บริการ AI เด็ดขาด** ขยายจากหลักการเดียวกับ FR-17 แต่เป็นชุดข้อมูลคนละแบบ
   รายละเอียดข้อจำกัดด้าน PDPA ดู NFR-21 (ขยายเพิ่ม 2026-09-27) ใน
   [[20260921-01-pdpa-data-protection-compliance]]
10. **ป้ายกำกับข้อความ AI และความทนทานต่อความล้มเหลว (ยืนยันแล้ว — เช่นเดียวกับ FR-17)** — ข้อความสรุปที่
    AI เขียนต้องมีป้ายกำกับชัดเจนว่าเป็น**ข้อมูลประกอบ ไม่ใช่คำแนะนำทางการแพทย์** หากบริการ AI ใช้งานไม่ได้/
    ล้มเหลว ระบบยังคงคำนวณและบันทึกตัวเลขสรุปจากขั้นที่ 1–2 ลงฐานข้อมูลได้ตามปกติ เพียงไม่มีข้อความสรุป
    ภาษาคนจาก AI เท่านั้น ไม่บล็อกการบันทึกตัวเลขที่คำนวณได้แล้ว
11. **การบันทึก audit log (ยืนยันแล้ว)** — การกดปุ่มนี้ถือเป็นการเข้าถึงข้อมูลผลตรวจ lab รายบุคคลของ
    ผู้ป่วย ต้องบันทึก audit log ตาม NFR-06 เช่นเดียวกับการเข้าถึงข้อมูลผู้ป่วยรายบุคคลอื่นๆ ในเอกสารนี้
    (สำหรับ admin ยังคงต้องเป็น audit log แบบ fail-safe ตาม NFR-20 เพิ่มเติมด้วย)
12. **ชื่อเทคโนโลยี AI (ยืนยันแล้ว — เช่นเดียวกับ FR-17)** — เอกสารนี้จงใจไม่ระบุชื่อ/ผู้ให้บริการ AI ที่
    เลือกใช้จริง กล่าวถึงเพียงระดับ logical ว่าเป็น "บริการ AI ภายนอก" (การตัดสินใจเชิงเทคโนโลยีบันทึกแยก
    ใน [[technology-stack]])

## ความต้องการเชิงฟังก์ชัน (Functional Requirements)

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
| --- | --- | --- | --- |
| FR-01 | แสดงประวัติการวินิจฉัยโรค NCD ของผู้ป่วย | แพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD ดูประวัติการวินิจฉัยของผู้ป่วยรายบุคคล ครอบคลุมกลุ่มโรคหลัก เบาหวาน (E10–E14), ความดันโลหิตสูง (I10–I14), ถุงลมโป่งพอง (J44) เรียงตามช่วงเวลา | สูง |
| FR-02 | แสดงผลตรวจ lab ที่เกี่ยวข้องกับโรค NCD ย้อนหลัง | แสดงค่าผลตรวจ lab มาตรฐานที่เกี่ยวข้องกับกลุ่มโรคหลักและโรคแทรกซ้อนในขอบเขต (เช่น HbA1c, eGFR, LDL, ค่าความดันโลหิต ฯลฯ) แบบย้อนหลังเป็นช่วงเวลา เพื่อให้แพทย์/พยาบาลติดตามแนวโน้ม | สูง |
| FR-03 | วิเคราะห์ความเสี่ยงโรคแทรกซ้อนแบบ rule-based ตาม threshold ค่า lab | ระบบประมวลผลค่า lab ของผู้ป่วยเทียบกับ threshold มาตรฐานที่เกี่ยวข้องกับโรคแทรกซ้อนในขอบเขต (ไตวายเรื้อรัง, โรคหัวใจ, โรคหลอดเลือดสมอง) เพื่อประเมินระดับความเสี่ยง โดยไม่ใช้ AI/Machine Learning model ใน MVP | สูง |
| FR-04 | แสดง/แจ้งผลการประเมินความเสี่ยงโรคแทรกซ้อนแก่ผู้ดูแล | แสดงผลลัพธ์จาก FR-03 เป็น flag/สัญญาณเตือนที่มองเห็นได้ชัดเจนบนหน้าจอของแพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD ต่อผู้ป่วยรายบุคคล | สูง |
| FR-05 | ค้นหา/แสดงรายชื่อผู้ป่วย NCD ทุกรายในระบบ | แพทย์/พยาบาล/admin ผู้ใช้งาน (ทุกคนที่ผ่านเงื่อนไขพื้นฐานตาม NFR-02) เรียกดูรายชื่อผู้ป่วย NCD **ทุกรายในระบบ** (**เปลี่ยนแปลง 2026-09-25 ยืนยันแล้วโดยผู้ใช้** — ยกเลิกกลไก PatientAssignment เดิมที่เคยจำกัดเฉพาะผู้ป่วยที่ "อยู่ในความดูแล" ดูหมายเหตุอัปเดตด้านบน) และ/หรือค้นหาผู้ป่วยเฉพาะรายด้วยเลขประจำตัวผู้ป่วย (HN) เท่านั้น (ไม่รองรับการค้นหาด้วยชื่อ — ยืนยันแล้ว ดูหมายเหตุ FR-06) เพื่อเลือกผู้ป่วยรายบุคคลก่อนเข้าดูประวัติการวินิจฉัย (FR-01), ผลตรวจ lab (FR-02) และผลวิเคราะห์ความเสี่ยงโรคแทรกซ้อน (FR-03/FR-04) เป็นขั้นตอนแรกสุดของ journey ก่อนเข้าถึงข้อมูลผู้ป่วยรายบุคคลใดๆ ทั้งหมด (admin เข้าถึงได้แบบอ่านอย่างเดียวเท่านั้น ดู [[20260924-01-admin-role-account-management#ความต้องการเชิงฟังก์ชัน (Functional Requirements)\|FR-15]]) เงื่อนไขการค้นหาด้วย HN โดยเฉพาะดูรายละเอียดเพิ่มเติมที่ FR-06 | สูง |
| FR-06 | ค้นหาผู้ป่วยด้วยเลข HN แบบ 7 หลัก พร้อม validation | แพทย์/พยาบาลผู้ใช้งานค้นหาผู้ป่วย (ภายใต้ FR-05) ด้วยเลขประจำตัวผู้ป่วย (HN) รูปแบบตัวเลขล้วน 7 หลักตามที่ระบบกำหนดไว้ตายตัว (ยืนยันแล้ว) เป็นช่องทางค้นหาเดียวที่ใช้งานได้ในระบบ (ไม่มีการค้นหาด้วยชื่ออีกต่อไป — ดูหมายเหตุ assumption ด้านบน) การตรวจสอบว่ากรอก HN ไม่ครบ 7 หลัก และการค้นหาจริงเกิดขึ้นได้ 2 จังหวะ **(แก้ไข 2026-09-26 ยืนยันแล้วโดยผู้ใช้ — แทนที่ข้อความเดิมที่ระบุว่าเกิดขึ้นหลังกดค้นหาเพียงจังหวะเดียว เพื่อรองรับ FR-17)**: (ก) เมื่อผู้ใช้หยุดพิมพ์ชั่วขณะ (debounce) และ (ข) เมื่อผู้ใช้กดปุ่มค้นหา หากกรอก HN ไม่ครบ 7 หลัก หรือค้นหาด้วย HN ที่ครบ 7 หลักแล้วแต่ไม่พบผู้ป่วยที่ตรงกัน ระบบต้องแจ้งผู้ใช้งานและให้กรอกค้นหาใหม่ได้ทันที โดยไม่บล็อกการเรียกดูรายชื่อทั้งหมดตาม FR-05 | สูง |
| FR-16 | ยืนยัน/แก้ไขผลการประเมินความเสี่ยงโรคแทรกซ้อน (Override Risk Assessment) | แพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD (ผู้ป่วย**ทุกราย**ในระบบตาม NFR-02 ที่แก้ไข 2026-09-25 — ไม่จำกัดเฉพาะผู้ป่วยที่เคย "อยู่ในความดูแล" อีกต่อไป, ยืนยันแล้วโดยผู้ใช้ผ่าน NEEDS_USER_INPUT เมื่อ 2026-09-25) ยืนยันหรือแก้ไขผลลัพธ์การประเมินความเสี่ยงโรคแทรกซ้อนที่ระบบประมวลผลอัตโนมัติตาม FR-03/FR-04 ได้ (เช่น กรณีเห็นว่าผล flag อัตโนมัติไม่สอดคล้องกับการประเมินทางคลินิกจริง) สิทธิ์นี้ครอบคลุม**เฉพาะผลการวิเคราะห์ความเสี่ยง (ComplicationRiskAssessment/RiskFinding)** เท่านั้น **ไม่ครอบคลุมการแก้ไขข้อมูลประวัติการวินิจฉัย (FR-01) หรือผลตรวจ lab (FR-02) ที่ยังคงเป็นข้อมูลอ่านอย่างเดียวจากแหล่งข้อมูล HOSxP/mockup ตาม NFR-01** การแก้ไข/ยืนยันทุกครั้งต้องบันทึกร่องรอยตาม NFR-06 (audit log) เพิ่มเติมจากการเข้าถึงแบบดูอย่างเดียว เพิ่มเข้ามาเมื่อ 2026-09-24 จาก requirement ดิบเพิ่มเติม (ดูหัวข้อสมมติฐาน) — ไม่ใช่สิทธิ์ของ admin (ดู [[20260924-01-admin-role-account-management#นอกขอบเขต (Out of scope) ของเอกสารนี้\|นอกขอบเขตของ admin]]) | สูง |
| FR-17 | AI ช่วยอธิบายผลการค้นหาผู้ป่วยด้วย HN เป็นภาษาคน | เพิ่ม 2026-09-26 จาก requirement ดิบ "ผมอยากให้ AI ช่วย track-ncds ในหน้าค้นหาด้วยเลข HN พิมพ์ในช่องค้นหา พอหยุดพิมพ์ หรือกดค้นหา ให้ AI เอาคำตอบมาแสดง" (ยืนยันขอบเขตแล้วโดยผู้ใช้ — ดูหมายเหตุ FR-17 ในหัวข้อสมมติฐาน) **(แก้ไข 2026-09-26 รอบสอง — ยืนยันแล้วโดยผู้ใช้ระหว่าง `/build-tech-stack`, แทนที่ข้อความเดิมที่ระบุว่าทำงานทั้ง 2 จังหวะ)** เมื่อผู้ใช้ค้นหาด้วย HN ตาม FR-06 ระบบเรียกบริการ AI ภายนอก**เฉพาะตอนผู้ใช้กดปุ่มค้นหาเท่านั้น** (ไม่เรียกตอนหยุดพิมพ์/debounce เพื่อประหยัด quota ของบริการ AI — การตรวจสอบรูปแบบ HN และการค้นหาผู้ป่วยตาม FR-06 เองยังคงทำงานทั้ง 2 จังหวะตามเดิม ไม่เปลี่ยนแปลง) ให้**อธิบายผลการค้นหาเป็นภาษาคน**ประกอบผลลัพธ์ที่ระบบแสดงอยู่แล้ว ครอบคลุม 3 กรณี: พบผู้ป่วยที่ตรงกัน, ไม่พบผู้ป่วยที่ตรงกัน, และกรอก HN ไม่ครบ 7 หลัก AI ทำหน้าที่เพียงอธิบายผลลัพธ์เท่านั้น **ไม่ใช่แชตตอบคำถามอิสระและไม่ใช่การแนะนำขั้นตอนทางคลินิก** (ไม่เกี่ยวข้องกับ FR-03/FR-04/FR-16) ข้อความที่ AI สร้างต้องมีป้ายกำกับชัดเจนว่าเป็น**ข้อมูลประกอบ ไม่ใช่คำแนะนำทางการแพทย์** ข้อมูลที่ส่งให้บริการ AI จำกัดเฉพาะเลข HN ที่พิมพ์และผลการค้นหาแบบไม่ระบุตัวตน ห้ามส่งชื่อผู้ป่วยหรือข้อมูลระบุตัวตนใดๆ (รายละเอียดข้อจำกัดด้าน PDPA ดู [[20260921-01-pdpa-data-protection-compliance#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-21]]) หากบริการ AI ใช้งานไม่ได้/ล้มเหลว การค้นหาปกติตาม FR-05/FR-06 ต้องยังคงใช้งานได้ตามปกติ ไม่ถูกบล็อกจากความล้มเหลวของ AI ใช้งานบนเว็บจริง (production) ไม่ใช่เฉพาะเครื่องนักพัฒนา เอกสารนี้ระบุเพียงระดับ logical ว่าเป็น "บริการ AI ภายนอก" ไม่ระบุชื่อเทคโนโลยีที่เลือกใช้จริง (บันทึกแยกใน [[technology-stack]]) | กลาง |
| FR-18 | AI สรุปจำนวนครั้งตรวจ HbA1c และระยะห่างระหว่างการตรวจในปีงบประมาณ (รายผู้ป่วย) | เพิ่ม 2026-09-27 จาก requirement ดิบ "ผมอยากได้ปุ่ม ให้ AI ช่วยสรุป จำนวน visit ที่ตรวจ lab hba1c ในปีงบประมาณ" (ทุกข้อยืนยันแล้วโดยผู้ใช้ผ่าน NEEDS_USER_INPUT — ดูหมายเหตุ FR-18 ในหัวข้อสมมติฐาน) มีปุ่มบนการ์ดผู้ป่วยแต่ละรายในหน้ารายชื่อผู้ป่วยตาม FR-05 ให้**แพทย์/พยาบาล/admin ทุกคน** (ต่างจาก FR-16 ที่จำกัดเฉพาะแพทย์/พยาบาล เพราะผลสรุปนี้เป็นการคำนวณสถิติ ไม่ใช่การวินิจฉัย/ตัดสินใจทางคลินิก — ยืนยันแล้วโดยผู้ใช้) กดเพื่อให้ระบบทำงาน 3 ขั้นตอน: **ขั้นที่ 1** ระบบ (ไม่ใช่ AI) หาวันที่ตรวจ HbA1c ทั้งหมดของผู้ป่วยจากผลตรวจ lab ตาม FR-02 ที่อยู่ในปีงบประมาณราชการไทย (1 ตุลาคม–30 กันยายน) ที่เลือก **ขั้นที่ 2** ระบบคำนวณจำนวน visit ที่ตรวจและระยะห่างเป็นจำนวนวันระหว่างการตรวจแต่ละครั้ง **ขั้นที่ 3** ระบบส่ง**เฉพาะตัวเลขสรุปที่คำนวณแล้ว** (จำนวนครั้ง, ระยะห่างเป็นวัน) ให้บริการ AI ภายนอกเขียนสรุปเป็นภาษาคน แล้ว**เขียนผลสรุปกลับลงฐานข้อมูล** (บันทึกตัวเลขที่คำนวณ + ข้อความที่ AI เขียน + โมเดล AI ที่ใช้ + เวลาที่สร้าง) แยกเก็บรายผู้ป่วยต่อปีงบประมาณ กดปุ่มซ้ำ = เขียนทับผลเดิมของผู้ป่วย/ปีงบประมาณเดียวกัน ไม่เก็บประวัติ กรณีไม่มีผลตรวจ HbA1c เลยในปีงบที่เลือก ปุ่มยังกดได้ตามปกติ ระบบบันทึกผลสรุปว่าจำนวน visit = 0 ("ไม่มีข้อมูล") ลงฐานเป็นหลักฐานว่าตรวจสอบแล้ว กรณีตรวจเพียงครั้งเดียว ระบบสรุปจำนวน visit = 1 โดยไม่มีค่าระยะห่าง และ AI ต้องระบุว่ายังไม่มีข้อมูลเพียงพอสำหรับประเมินความสม่ำเสมอ ข้อความที่ AI สร้างต้องมีป้ายกำกับชัดเจนว่าเป็น**ข้อมูลประกอบ ไม่ใช่คำแนะนำทางการแพทย์** เช่นเดียวกับ FR-17 หากบริการ AI ใช้งานไม่ได้/ล้มเหลว ระบบยังคงคำนวณและบันทึกตัวเลขสรุปจากขั้นที่ 1–2 ลงฐานข้อมูลได้ตามปกติ เพียงไม่มีข้อความสรุปภาษาคนจาก AI เท่านั้น การกดปุ่มนี้ถือเป็นการเข้าถึงข้อมูลผลตรวจ lab รายบุคคลของผู้ป่วย ต้องบันทึก audit log ตาม NFR-06 (และ NFR-20 เพิ่มเติมสำหรับ admin) เช่นเดียวกับการเข้าถึงข้อมูลผู้ป่วยรายบุคคลอื่นๆ admin ยังคงเป็น read-only สำหรับข้อมูลทางคลินิกอื่นทั้งหมดตาม FR-15 เหมือนเดิม ข้อมูลที่ส่งให้บริการ AI ภายนอกจำกัดเฉพาะตัวเลขสรุป (จำนวนครั้ง, ระยะห่างเป็นวัน) เท่านั้น **ห้ามส่ง HN/ชื่อผู้ป่วย/วันที่ตรวจ/ค่าผล HbA1c ใดๆ ให้บริการ AI เด็ดขาด** (รายละเอียดข้อจำกัดด้าน PDPA ดู [[20260921-01-pdpa-data-protection-compliance#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-21]] ที่ขยายเพิ่ม 2026-09-27) ใช้งานบนเว็บจริง (production) เอกสารนี้ระบุเพียงระดับ logical ว่าเป็น "บริการ AI ภายนอก" ไม่ระบุชื่อเทคโนโลยีที่เลือกใช้จริง (บันทึกแยกใน [[technology-stack]]) | กลาง |

## ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)

| รหัส | ด้าน | ความต้องการ |
| --- | --- | --- |
| NFR-01 | แหล่งข้อมูล/Integration | แหล่งข้อมูลจริงของประวัติวินิจฉัยและผลตรวจ lab คือระบบ HOSxP แต่ในช่วงพัฒนา/ทดสอบให้ใช้ข้อมูล mockup จำลองแทนไปก่อน ยังไม่กำหนด field mapping หรือวิธีเชื่อมต่อจริง เพราะ `technology-stack.md` ยังไม่ถูกตัดสินใจ |
| NFR-02 | Security / Access Control | เฉพาะผู้ใช้ที่มีบทบาทแพทย์, พยาบาล หรือ admin เท่านั้นที่เข้าถึงประวัติ, ผลตรวจ lab และผลวิเคราะห์ความเสี่ยงของผู้ป่วยได้ ต้องผ่านเงื่อนไขพื้นฐานเสมอ (token ถูกต้อง, `email_verified = true`, role ที่ระบบอนุญาต, `isActive = true`) **(แก้ไข 2026-09-25 ยืนยันแล้วโดยผู้ใช้ — ยกเลิกข้อความเดิม)**: ไม่มีการจำกัดเพิ่มเติมในระดับรายผู้ป่วยตาม assignment "อยู่ในความดูแล" อีกต่อไป (ยกเลิกกลไก PatientAssignment ทั้งหมด ดูหมายเหตุอัปเดตด้านบน) แพทย์/พยาบาล/admin ทุกคนที่ผ่านเงื่อนไขพื้นฐานเห็นผู้ป่วยทุกรายในระบบเหมือนกัน (ข้อความเดิมก่อนแก้ไขอยู่ใน git history) admin ยังคงเข้าถึงได้เฉพาะแบบอ่านอย่างเดียวเท่านั้นตาม [[20260924-01-admin-role-account-management#ความต้องการเชิงฟังก์ชัน (Functional Requirements)\|FR-15]] (ไม่มีสิทธิ์แก้ไข/override ตาม FR-16) ข้อยกเว้นเดิมที่เคยระบุไว้เฉพาะ admin ([[20260924-01-admin-role-account-management#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-19]]) จึงไม่ใช่ "ข้อยกเว้น" อีกต่อไป เพราะกลายเป็นกฎทั่วไปที่ใช้กับทุกบทบาทแล้ว (ดูหมายเหตุที่เอกสารนั้น) |

ระดับความสำคัญ (สูง/กลาง/ต่ำ ใช้จัดกลุ่มใน [[backlog]] ตามรูปแบบเดิมของโปรเจกต์ — ตาราง NFR ด้านบน
ไม่มีคอลัมน์นี้โดยตรง สอดคล้องกับรูปแบบที่ใช้ใน [[20260921-01-pdpa-data-protection-compliance]]):
NFR-01, NFR-02 = **สูง** (ต้องมีใน MVP — NFR-01 เป็นแหล่งข้อมูลพื้นฐานที่ FR-01/FR-02 ซึ่งเป็น MVP
ต้องพึ่งพาโดยตรง หากไม่มีข้อมูลประวัติวินิจฉัย/ผลตรวจ lab ตาม NFR-01 ฟีเจอร์หลักของ MVP จะทำงานไม่ได้
เลย ส่วน NFR-02 เป็นการควบคุมสิทธิ์เข้าถึงข้อมูลผู้ป่วยที่ FR-05 ซึ่งเป็น MVP ต้องพึ่งพาโดยตรงเช่นกัน
— ยืนยันโดยผู้ใช้ผ่าน AskUserQuestion เมื่อ 2026-09-22)

  กำหนดข้อจำกัดด้านการจำกัดข้อมูลที่ส่งให้บริการ AI ภายนอกที่ FR-17 และ FR-18 ในเอกสารนี้ใช้งาน
- [[20260924-01-admin-role-account-management]] — บทบาท admin (ใหม่) ที่เคยจัดการ PatientAssignment
  (FR-14 ยกเลิกแล้วตั้งแต่ 2026-09-25) เห็นผู้ป่วยทุกรายแบบอ่านอย่างเดียวตาม FR-15 (ไม่ใช่ข้อยกเว้นจาก
  NFR-02 อีกต่อไป — ดูหมายเหตุ NFR-19) และไม่มีสิทธิ์แก้ไขผลวิเคราะห์ความเสี่ยงตาม FR-16

  ตั้งแต่ 2026-09-25)
