# เข้าสู่ระบบและจัดการบัญชีผู้ใช้ด้วยอีเมล/รหัสผ่าน (Firebase Authentication)

## บทนำ

เอกสารนี้กำหนดความต้องการของการยืนยันตัวตนผู้ใช้งาน (แพทย์/พยาบาลผู้ดูแลผู้ป่วย NCD) ด้วยอีเมลและ
รหัสผ่านผ่าน **Firebase Authentication** ตามที่ [[technology-stack#7. Authentication/Authorization — Firebase Authentication + Custom Claims|technology-stack]]
ตัดสินใจไว้แล้ว ครอบคลุมการสมัครบัญชีด้วยตนเอง (self sign-up), การเข้าสู่ระบบ, การยืนยันอีเมล และ
การขอรีเซ็ตรหัสผ่านเมื่อลืมรหัสผ่าน เป็นเอกสาร spec ที่แยกใหม่เพราะเป็นฟีเจอร์คนละเรื่องกับ
[[20260917-01-patient-ncd-history-lab-complication-risk]] (ประวัติ NCD/lab/ความเสี่ยง),
[[20260921-01-pdpa-data-protection-compliance]] (PDPA) และ
[[20260922-01-operational-quality-nfr]] (คุณภาพเชิงปฏิบัติการ) — เอกสารนี้ยังคง**อ้างอิงและไม่ทับซ้อน**
กับ NFR-02 (Security / Access Control) และ NFR-12 (Session Timeout) ที่มีอยู่แล้ว เนื่องจากข้อกำหนด
ทั้งสองข้อนั้นควบคุม "ใครเข้าถึงได้เมื่อไหร่หลังล็อกอินสำเร็จแล้ว" ในขณะที่เอกสารนี้ควบคุม
"กระบวนการยืนยันตัวตนก่อนเข้าสู่ระบบ" ซึ่งเป็นคนละขั้นตอน

เอกสารนี้เป็นฉบับที่ 4 ของโปรเจกต์ จึงเริ่มรหัสที่ **FR-07** และ **NFR-17** ต่อจากรหัสสูงสุดที่มีอยู่
ในโปรเจกต์ ([[20260917-01-patient-ncd-history-lab-complication-risk]] มี FR-01–FR-06, NFR-01–NFR-02;
[[20260921-01-pdpa-data-protection-compliance]] มี NFR-03–NFR-08;
[[20260922-01-operational-quality-nfr]] มี NFR-09–NFR-16)

## ขอบเขต

### สิ่งที่อยู่ในขอบเขตของเอกสารนี้

- การสมัครบัญชีผู้ใช้งานด้วยตนเอง (self sign-up) ด้วยอีเมล/รหัสผ่าน
- การเข้าสู่ระบบ (login) ด้วยอีเมล/รหัสผ่านที่สมัครไว้
- การยืนยันความเป็นเจ้าของอีเมล (email verification) ก่อนเข้าใช้งานฟีเจอร์อื่นของระบบ
- การขอรีเซ็ตรหัสผ่านทางอีเมลเมื่อลืมรหัสผ่าน (forgot password / password reset)
- นโยบายความซับซ้อนของรหัสผ่านขั้นต่ำ และการป้องกันการสอดแนมว่าอีเมลใดมีบัญชีอยู่ในระบบหรือไม่
  (account enumeration)

### บทบาทที่เกี่ยวข้อง

แพทย์และพยาบาล (บทบาทเดียวกับที่กำหนดไว้แล้วใน
[[20260917-01-patient-ncd-history-lab-complication-risk#บทบาทผู้ใช้ในขอบเขตนี้|บทบาทผู้ใช้ในขอบเขตนี้]])
เป็นผู้สมัครบัญชี/เข้าสู่ระบบตามเอกสารนี้ เอกสารนี้ไม่ได้เพิ่มบทบาทผู้ใช้งานปลายทางใหม่ แต่มี**ผู้ดูแล
ระบบ (system administrator)** เข้ามาเกี่ยวข้องในขั้นตอนอนุมัติบัญชีตาม FR-08 — ผู้ดูแลระบบในที่นี้
หมายถึงผู้ที่มีสิทธิ์เข้าถึง Firebase Console/Firestore โดยตรงในการดำเนินการ ไม่ใช่บทบาท (role) ใหม่
ในระบบที่ต้องมี UI หรือ Custom Claims ของตัวเอง (ยืนยันแล้วโดยผู้ใช้ — ดูหัวข้อสมมติฐาน)

> **อัปเดต 2026-09-24 — ข้อสรุปนี้ถูกแทนที่บางส่วนแล้ว:** ผู้ใช้ยืนยันเปลี่ยนทิศทางผ่าน
> NEEDS_USER_INPUT ให้เพิ่มบทบาท **admin** เป็น role ใหม่ในระบบ (มี UI ของตัวเองสำหรับอนุมัติบัญชี/
> เปลี่ยน role/ระงับบัญชี/จัดการ PatientAssignment/ดูข้อมูลผู้ป่วยทุกราย) แทนที่แนวคิด "ผู้ดูแลระบบ
> ผ่าน Firebase Console เท่านั้น" ข้างต้น รายละเอียดทั้งหมดอยู่ที่
> [[20260924-01-admin-role-account-management]] — FR-07/FR-09/FR-10 ของเอกสารนี้ไม่เปลี่ยนแปลง

### นอกขอบเขต (Out of scope) ของเอกสารนี้

- **หน้าจอ/ฟีเจอร์อนุมัติบัญชีภายในระบบ** — *(ล้าสมัยบางส่วนแล้ว ณ 2026-09-24)* เดิมกำหนดว่าการอนุมัติ
  บัญชีใหม่ (กำหนด role + เปิดใช้งาน `isActive`) ในขอบเขต MVP ดำเนินการโดยผู้ดูแลระบบผ่าน Firebase
  Console/แก้ไขข้อมูลใน Firestore โดยตรง ไม่มีหน้าจออนุมัติในระบบ (ยืนยันแล้วโดยผู้ใช้เมื่อ 2026-09-23)
  — **ผู้ใช้ยืนยันเปลี่ยนทิศทางนี้แล้วเมื่อ 2026-09-24** ให้มีหน้าจออนุมัติในระบบสำหรับบทบาท admin
  ใหม่แทน ดู [[20260924-01-admin-role-account-management#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-11]]
- **การเข้าสู่ระบบผ่านผู้ให้บริการอื่น (SSO/Google/SAML)** — [[technology-stack#7. Authentication/Authorization — Firebase Authentication + Custom Claims|technology-stack]]
  ระบุไว้แล้วว่า SSO/การเชื่อมต่อระบบยืนยันตัวตนของโรงพยาบาลเป็นแนวทางที่พิจารณาในอนาคต ไม่ใช่ขอบเขต MVP
- **การจัดการ session timeout ระหว่างใช้งาน** — กำหนดไว้แล้วที่
  [[20260922-01-operational-quality-nfr#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)|NFR-12]]
  เอกสารนี้ไม่ทับซ้อน ครอบคลุมเฉพาะขั้นตอนก่อนเข้าสู่ระบบสำเร็จเท่านั้น
- **การกำหนด/แก้ไขบทบาท (role) ของผู้ใช้งานหลังอนุมัติครั้งแรก** (เช่น เปลี่ยนจากพยาบาลเป็นแพทย์,
  ระงับบัญชีภายหลัง) — *(ล้าสมัยบางส่วนแล้ว ณ 2026-09-24)* เดิมระบุว่าดำเนินการผ่าน Firebase
  Console/Firestore โดยผู้ดูแลระบบเช่นเดียวกับ FR-08 ในเบื้องต้น — **ปัจจุบันดำเนินการผ่านหน้าจอในระบบ
  โดย admin แล้ว** ดู [[20260924-01-admin-role-account-management#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-12 (เปลี่ยน role), FR-13 (ระงับ/เปิดใช้งานบัญชี)]]

## สมมติฐาน (Assumptions) — โปรดตรวจทานอีกครั้ง

ประเด็นต่อไปนี้ **ผู้ใช้ยืนยันแล้วผ่าน NEEDS_USER_INPUT เมื่อ 2026-09-23** ระหว่างการจัดทำเอกสารนี้
(แทนที่การตีความเบื้องต้นของผู้จัดทำเอกสารทั้งหมด):

1. **ขั้นตอนการทำงาน (ยืนยันแล้ว)** — ทำเอกสาร requirement ให้ครบก่อนเริ่มเขียนโค้ดใดๆ
2. **การสมัครบัญชี (ยืนยันแล้ว)** — ผู้ใช้งานสมัครบัญชีเองได้ (self sign-up) ไม่ใช่การสร้างบัญชีให้
   โดยผู้ดูแลระบบล่วงหน้าเพียงอย่างเดียว
3. **การอนุมัติบัญชีหลังสมัคร (ยืนยันแล้ว — เพื่อไม่ให้ขัดกับ [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-02]])**
   บัญชีที่สมัครใหม่**ต้องยังไม่มี role และ `isActive = false` โดยดีฟอลต์** จนกว่าจะได้รับการอนุมัติ
   ก่อนอนุมัติ ผู้ใช้ที่สมัครเสร็จแล้วจะเข้าสู่ระบบได้ (ผ่าน FR-07) แต่ต้องไม่สามารถเข้าถึงข้อมูลผู้ป่วย
   ใดๆ ได้เลย เพราะไม่ผ่านเงื่อนไข NFR-02 (role + isActive) *(อัปเดต 2026-09-24: ช่องทางการอนุมัติ
   เปลี่ยนจาก "ผ่าน Firebase Console/Firestore โดยผู้ดูแลระบบ" เป็น "ผ่านหน้าจอในระบบโดยบทบาท admin"
   แล้ว — ดู [[20260924-01-admin-role-account-management]])*
4. **การยืนยันอีเมล (ยืนยันแล้ว)** — ต้องยืนยันความเป็นเจ้าของอีเมล (email verification) ก่อนเข้าใช้
   งานฟีเจอร์ใดๆ ของระบบ (แม้จะผ่านการอนุมัติบัญชีตามข้อ 3 แล้วก็ตาม ต้องยืนยันอีเมลด้วยเสมอ)
5. **นโยบายรหัสผ่าน (ยืนยันแล้ว)** — รหัสผ่านต้องมีความยาวขั้นต่ำ **8 ตัวอักษร และต้องมีทั้งตัวอักษร
   และตัวเลขอย่างน้อยอย่างละ 1 ตัว**
6. **การป้องกัน Account Enumeration (ยืนยันแล้ว)** — ข้อความแจ้งเตือนของระบบต้อง**ไม่เปิดเผยว่าอีเมล
   ใดมีบัญชีอยู่ในระบบแล้วหรือไม่** ไม่ว่าจะเป็นตอนเข้าสู่ระบบผิดพลาด (ใช้ข้อความรวมว่า
   "อีเมลหรือรหัสผ่านไม่ถูกต้อง" แทนการแยกแจ้งว่าอีเมลไม่พบ), ตอนสมัครด้วยอีเมลที่มีอยู่แล้ว
   (ใช้ข้อความทั่วไปที่ไม่ยืนยัน/ปฏิเสธการมีอยู่ของอีเมลนั้นตรงๆ) และตอนขอรีเซ็ตรหัสผ่าน
   (แจ้งข้อความเดียวกันว่า "หากอีเมลนี้มีอยู่ในระบบ จะได้รับลิงก์รีเซ็ตรหัสผ่านทางอีเมล"
   ไม่ว่าอีเมลนั้นจะมีอยู่จริงหรือไม่)

## ความต้องการเชิงฟังก์ชัน (Functional Requirements)

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
| --- | --- | --- | --- |
| FR-07 | เข้าสู่ระบบด้วยอีเมลและรหัสผ่าน | ผู้ใช้งาน (แพทย์/พยาบาล) เข้าสู่ระบบด้วยอีเมลและรหัสผ่านที่สมัครไว้ผ่าน Firebase Authentication เมื่อเข้าสู่ระบบสำเร็จแล้ว การเข้าถึงข้อมูลผู้ป่วยยังคงต้องผ่านเงื่อนไข role/isActive/patient assignment ตาม [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-02]] และเงื่อนไขยืนยันอีเมล (FR-09) แยกต่างหาก กรณีอีเมล/รหัสผ่านไม่ถูกต้องต้องแจ้งข้อความเดียวกันโดยไม่เปิดเผยว่าอีเมลมีอยู่ในระบบหรือไม่ (ดูหัวข้อสมมติฐาน) | สูง |
| FR-08 | สมัครบัญชีผู้ใช้งานด้วยตนเอง (Self Sign-up) | ผู้ใช้งานสมัครบัญชีใหม่ได้เองด้วยอีเมลและรหัสผ่านที่เป็นไปตามนโยบายรหัสผ่านขั้นต่ำ (ดู NFR-17) โดยบัญชีที่สร้างใหม่ต้องมี `isActive = false` และยังไม่มี role กำหนดจนกว่าผู้ดูแลระบบจะอนุมัติผ่าน Firebase Console/Firestore ด้วยตนเอง (ไม่มีหน้าจออนุมัติในระบบสำหรับ MVP — ดูหัวข้อนอกขอบเขต) กรณีสมัครด้วยอีเมลที่มีบัญชีอยู่แล้ว ต้องแจ้งข้อความทั่วไปที่ไม่ยืนยัน/ปฏิเสธการมีอยู่ของอีเมลนั้นตรงๆ (ดูหัวข้อสมมติฐาน) | สูง |
| FR-09 | ยืนยันอีเมลก่อนเข้าใช้งาน (Email Verification) | หลังสมัครบัญชีสำเร็จ ระบบต้องส่งอีเมลยืนยันตัวตน (verification link) ไปยังอีเมลที่ใช้สมัคร และผู้ใช้งานต้องยืนยันอีเมลให้เสร็จสิ้นก่อนจึงจะเข้าใช้งานฟีเจอร์อื่นของระบบได้ (แม้จะผ่านการอนุมัติบัญชีตาม FR-08 แล้วก็ตาม ต้องยืนยันอีเมลด้วยเสมอ) | สูง |
| FR-10 | ขอรีเซ็ตรหัสผ่านทางอีเมล (Forgot Password) | ผู้ใช้งานที่ลืมรหัสผ่านสามารถกรอกอีเมลเพื่อขอรับลิงก์รีเซ็ตรหัสผ่านทางอีเมลได้ ไม่ว่าอีเมลที่กรอกจะมีบัญชีอยู่ในระบบจริงหรือไม่ ระบบต้องแจ้งข้อความเดียวกันเสมอว่า "หากอีเมลนี้มีอยู่ในระบบ จะได้รับลิงก์รีเซ็ตรหัสผ่านทางอีเมล" เพื่อไม่เปิดเผยว่าอีเมลใดมีบัญชีอยู่ในระบบหรือไม่ (ดูหัวข้อสมมติฐาน) รหัสผ่านใหม่ที่ตั้งต้องเป็นไปตามนโยบายรหัสผ่านขั้นต่ำเช่นเดียวกับ FR-08 (ดู NFR-17) | สูง |

## ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)

| รหัส | ด้าน | ความต้องการ |
| --- | --- | --- |
| NFR-17 | Security / Password Policy | รหัสผ่านที่ใช้สมัครบัญชี (FR-08) หรือตั้งใหม่ผ่านการรีเซ็ต (FR-10) ต้องมีความยาวขั้นต่ำ **8 ตัวอักษร และมีทั้งตัวอักษรและตัวเลขอย่างน้อยอย่างละ 1 ตัว** ระบบต้องปฏิเสธและแจ้งเตือนหากรหัสผ่านที่กรอกไม่เป็นไปตามเงื่อนไขนี้ |
| NFR-18 | Security / Account Enumeration Prevention | ข้อความแจ้งเตือนที่เกี่ยวข้องกับการเข้าสู่ระบบ (FR-07), การสมัครบัญชี (FR-08) และการขอรีเซ็ตรหัสผ่าน (FR-10) ต้อง**ไม่เปิดเผยว่าอีเมลใดมีบัญชีอยู่ในระบบแล้วหรือไม่** ไม่ว่าจะเป็นกรณีเข้าสู่ระบบผิดพลาด สมัครด้วยอีเมลซ้ำ หรือขอรีเซ็ตรหัสผ่านด้วยอีเมลที่ไม่มีในระบบ (ดูรายละเอียดข้อความในหัวข้อสมมติฐาน) |

ระดับความสำคัญ (สูง/กลาง/ต่ำ ใช้จัดกลุ่มใน [[backlog]] ตามรูปแบบเดิมของโปรเจกต์ — ตาราง NFR ด้านบน
