# บทบาทผู้ดูแลระบบ (Admin) และการจัดการบัญชี/สิทธิ์ผู้ใช้งาน

## บทนำ

เอกสารนี้กำหนดความต้องการของ**บทบาทผู้ดูแลระบบ (admin)** ซึ่งเป็น role ใหม่ในระบบ (role ที่ 3
ควบคู่กับ **แพทย์**และ**พยาบาล**ที่มีอยู่แล้วตาม
[[20260917-01-patient-ncd-history-lab-complication-risk#บทบาทผู้ใช้ในขอบเขตนี้|บทบาทผู้ใช้ในขอบเขตนี้]])
พร้อมหน้าจอในระบบสำหรับ admin ในการอนุมัติบัญชีผู้ใช้งานใหม่, กำหนด/เปลี่ยนบทบาท, ระงับ/เปิดใช้งาน
บัญชี, จัดการการมอบหมายผู้ป่วย (PatientAssignment) และดูประวัติการรักษาของผู้ป่วยทุกรายในระบบ

**เอกสารนี้แทนที่การตัดสินใจบางส่วนของ**
[[20260923-01-user-authentication-email-password]] **โดยตรง** — เอกสารนั้นเคยระบุไว้ (ยืนยันแล้วเมื่อ
2026-09-23) ว่า "ไม่มีบทบาท admin ในระบบ ไม่มีหน้าจออนุมัติบัญชีในระบบ ดำเนินการทุกอย่างผ่าน Firebase
Console/Firestore โดยตรงในเบื้องต้น" ผู้ใช้ได้ยืนยันเปลี่ยนทิศทางนี้ผ่าน NEEDS_USER_INPUT เมื่อ
2026-09-24 (ดูหัวข้อสมมติฐาน) การอนุมัติบัญชีใหม่ (เดิมคือ FR-08), การเปลี่ยน role และการระงับบัญชี
(เดิมระบุไว้เป็นนอกขอบเขตของเอกสาร auth) **ย้ายมาดำเนินการผ่านหน้าจอในระบบตามเอกสารนี้แทน** ส่วน
FR-07/FR-09/FR-10 (login, email verification, forgot password) ของเอกสาร auth เดิมยังคงใช้งานตามเดิม
ไม่เปลี่ยนแปลง

ระบบไม่ใช้ Firebase Custom Claims เก็บบทบาท/สถานะบัญชีอีกต่อไป (ตาม
[[technology-stack#18. การ Sync role/isActive ระหว่าง Firestore กับ Custom Claims (ฟีเจอร์ที่ 6) — ไม่ Sync, Firestore เป็น Source of Truth เดียว|technology-stack decision area 18]])
`role`/`isActive` ของผู้ใช้ทุกคน (รวมถึง admin) เก็บที่ `users/{uid}` ใน Cloud Firestore เป็น source of
truth เดียว ดำเนินการอ่าน/แก้ไขผ่าน Cloud Functions ที่ตรวจสิทธิ์ผู้เรียก (ต้องเป็น admin ที่
`isActive = true`) ก่อนเสมอ

เอกสารนี้เป็นฉบับที่ 5 ของโปรเจกต์ จึงเริ่มรหัสที่ **FR-11** และ **NFR-19** ต่อจากรหัสสูงสุดที่มีอยู่
ในโปรเจกต์ (FR สูงสุดเดิม FR-10 จาก [[20260923-01-user-authentication-email-password]], NFR สูงสุด
เดิม NFR-18 จากเอกสารเดียวกัน)

## ขอบเขต

### สิ่งที่อยู่ในขอบเขตของเอกสารนี้

- บทบาท **admin** เป็น role ใหม่ในระบบ (role ที่ 3 ควบคู่แพทย์/พยาบาล ไม่ได้แทนที่ role เดิม)
- หน้าจอในระบบสำหรับ admin ครอบคลุม:
  - อนุมัติบัญชีผู้ใช้งานใหม่ที่สมัครเอง (กำหนด role แพทย์/พยาบาล + เปิดใช้งาน `isActive = true`)
  - เปลี่ยนบทบาท (role) ของผู้ใช้งานที่เคยอนุมัติแล้ว
  - ระงับ (`isActive = false`) และเปิดใช้งาน (`isActive = true`) บัญชีผู้ใช้งานภายหลัง
  - ~~มอบหมาย/ยกเลิกการมอบหมายผู้ป่วยให้แพทย์/พยาบาล (จัดการ `patientAssignments`)~~ — **ยกเลิก
    2026-09-25** ระบบไม่มีกลไก PatientAssignment อีกต่อไป (ดูหมายเหตุข้อ 7 ในหัวข้อสมมติฐาน)
  - ดูประวัติการวินิจฉัย, ผลตรวจ lab และผลวิเคราะห์ความเสี่ยงโรคแทรกซ้อนของผู้ป่วย**ทุกราย**ในระบบ
    โดยไม่ต้องมี PatientAssignment เป็นของตนเอง (ต่างจากแพทย์/พยาบาลที่จำกัดเฉพาะผู้ป่วยที่ได้รับ
    มอบหมายตาม NFR-02)
- การบันทึก audit log แบบ fail-safe ทุกครั้งที่ admin เข้าถึงข้อมูลผู้ป่วยรายบุคคล (ขยายจาก NFR-06)

### บทบาทที่เกี่ยวข้อง

- **Admin** — บทบาทใหม่ตามเอกสารนี้ มี `role = "admin"` ใน `users/{uid}` เข้าสู่ระบบด้วยกลไกเดียวกับ
  แพทย์/พยาบาลตาม [[20260923-01-user-authentication-email-password#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-07]]
  (Firebase Authentication อีเมล/รหัสผ่าน) แต่มีสิทธิ์ที่ต่างออกไปตามเอกสารนี้
- **แพทย์/พยาบาล** — role เดิมตาม
  [[20260917-01-patient-ncd-history-lab-complication-risk#บทบาทผู้ใช้ในขอบเขตนี้|บทบาทผู้ใช้ในขอบเขตนี้]]
  เป็นผู้ถูกจัดการ (อนุมัติ/เปลี่ยน role/ระงับ/มอบหมายผู้ป่วย) โดย admin ตามเอกสารนี้ ไม่มีการเปลี่ยนแปลง
  สิทธิ์การเข้าถึงข้อมูลผู้ป่วยของแพทย์/พยาบาลเอง (ยังคงจำกัดเฉพาะผู้ป่วยที่ได้รับมอบหมายตาม NFR-02
  เหมือนเดิม)

โครงสร้าง role ในระบบหลังเอกสารนี้จึงมี **3 role ย่อยในระบบ** (แพทย์ / พยาบาล / admin) ที่จัดกลุ่มเป็น
**2 กลุ่มเชิงหน้าที่**: "ผู้ใช้งานทางคลินิก" (แพทย์ + พยาบาล) และ "ผู้ดูแลระบบ" (admin) — ยืนยันแล้ว
โดยผู้ใช้ (ดูหัวข้อสมมติฐาน)

### นอกขอบเขต (Out of scope) ของเอกสารนี้

- **การสร้างบัญชี admin คนแรก (bootstrap)** — ยังคงดำเนินการผ่าน Firebase Console/Firestore โดยตรง
  โดยผู้ที่มีสิทธิ์เข้าถึง infrastructure เท่านั้น (ยืนยันแล้วโดยผู้ใช้) ไม่มี FR ในระบบสำหรับสร้าง
  admin คนแรกโดยอัตโนมัติ เพราะเป็น edge case ที่เกิดครั้งเดียวตอน deploy
- **การแก้ไขข้อมูลทางคลินิกโดย admin** (ประวัติวินิจฉัย, ผล lab, ผลวิเคราะห์ความเสี่ยง) — admin มีสิทธิ์
  เพียง **ดู (read-only)** ข้อมูลทางคลินิกของผู้ป่วยทุกรายเท่านั้น (FR-15) ไม่มีสิทธิ์แก้ไขข้อมูลเหล่านี้
  สิทธิ์แก้ไข/ยืนยันผลวิเคราะห์ความเสี่ยงเป็นของแพทย์/พยาบาลตาม
  [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการเชิงฟังก์ชัน (Functional Requirements)|FR-16]]
  เท่านั้น ไม่ใช่ admin
- **การเข้าสู่ระบบ/ยืนยันอีเมล/รีเซ็ตรหัสผ่านของ admin** — ใช้กลไกเดียวกับแพทย์/พยาบาลทุกประการตาม
  [[20260923-01-user-authentication-email-password]] (FR-07/FR-09/FR-10) เอกสารนี้ไม่ได้เพิ่มกลไก
  ยืนยันตัวตนใหม่สำหรับ admin โดยเฉพาะ
- **การกำหนดสิทธิ์ระดับละเอียดกว่า role เดียว (fine-grained permission/multiple admin levels)** —
  ขอบเขต MVP มี admin เพียงระดับเดียวที่มีสิทธิ์เท่ากันทั้งหมดตาม FR-11–FR-15 ยังไม่แบ่งระดับสิทธิ์ย่อย
  ของ admin เอง

## สมมติฐาน (Assumptions) — โปรดตรวจทานอีกครั้ง

ประเด็นต่อไปนี้ **ผู้ใช้ยืนยันแล้วผ่าน NEEDS_USER_INPUT เมื่อ 2026-09-24** (แทนที่การตีความเบื้องต้น
ของผู้จัดทำเอกสารทั้งหมด และแทนที่ข้อสรุปบางส่วนใน
[[20260923-01-user-authentication-email-password]] ที่เคยยืนยันไว้เมื่อ 2026-09-23):

1. **แนวทางเอกสาร (ยืนยันแล้ว)** — สร้างเป็นเอกสาร spec ใหม่แยกต่างหาก (ไฟล์นี้) แทนที่จะเพิ่มต่อท้าย
   ในเอกสาร auth เดิมทั้งหมด หรือย้ายของเก่าไป archived เพราะ FR-07/FR-09/FR-10 เดิมยังใช้งานได้
   ไม่ล้าสมัย มีเพียงส่วนอนุมัติบัญชี/บริหารจัดการสิทธิ์ (FR-08 เดิม และหัวข้อนอกขอบเขตของเอกสารนั้น)
   ที่ถูกแทนที่
2. **นิยามบทบาท (ยืนยันแล้ว)** — "2 บทบาท" ในความต้องการดิบหมายถึง 2 กลุ่มเชิงหน้าที่ (ผู้ใช้งาน
   ทางคลินิก = แพทย์+พยาบาล / ผู้ดูแลระบบ = admin) ไม่ใช่การลดจำนวน role ย่อยในระบบ ระบบยังคงมี 3 role
   ย่อย (แพทย์/พยาบาล/admin) เหมือนเดิม
3. **ขอบเขตสิทธิ์ "แก้ไขสิทธิ์อื่น" ของ admin (ยืนยันแล้ว)** — ครอบคลุมครบวงจร: อนุมัติบัญชีใหม่
   (กำหนด role + isActive), เปลี่ยน role ภายหลัง, ระงับ/เปิดใช้งานบัญชี, และจัดการ PatientAssignment
   (FR-11–FR-14)
4. **ขอบเขต "ดูประวัติการรักษา" ของ admin (ยืนยันแล้ว)** — admin ดูได้**ทุกผู้ป่วย**โดยไม่ต้องมี
   PatientAssignment เป็นของตนเอง (ต่างจากแพทย์/พยาบาล) แต่ต้องบันทึก audit log แบบ fail-safe ทุกครั้ง
   ที่เข้าถึงข้อมูลผู้ป่วยรายบุคคล (FR-15, NFR-20) เพื่อควบคุมความเสี่ยงด้าน PDPA จากการเข้าถึงแบบไม่
   จำกัดขอบเขต
5. **ช่องทางดำเนินการ (ยืนยันแล้ว)** — มีหน้าจอจัดการผู้ใช้งาน/สิทธิ์ในระบบสำหรับ admin โดยเฉพาะ
   (ไม่ใช่ผ่าน Firebase Console/Firestore ตรงอีกต่อไปสำหรับงาน routine เหล่านี้) เนื่องจาก admin เป็น
   role ที่ login เข้าระบบได้เองแล้ว
6. **การสร้าง admin คนแรก (ยืนยันแล้ว)** — สร้าง/กำหนดผ่าน Firebase Console/Firestore โดยตรง (ดู
   หัวข้อนอกขอบเขต) ไม่มี workflow ในระบบสำหรับ bootstrap admin คนแรก

**อัปเดต 2026-09-25 (ยืนยันแล้วโดยผู้ใช้ผ่าน requirement ดิบเพิ่มเติม "ไม่ต้องให้ admin จัดการการ
มอบหมายผู้ป่วย ให้แพทย์/พยาบาล/admin สามารถดูผู้ป่วยได้ทุกคนหลังจาก login" — แทนที่สมมติฐานข้อ 3/4
ด้านบนบางส่วน):**

7. **ยกเลิกกลไก PatientAssignment ทั้งหมด** — ระบบไม่มีการมอบหมายผู้ป่วยรายบุคคลให้แพทย์/พยาบาลอีก
   ต่อไป แพทย์/พยาบาล/admin ทุกคนที่ผ่านเงื่อนไขพื้นฐาน (role/isActive/email_verified) เห็นผู้ป่วย
   ทุกรายในระบบเหมือนกันหลังเข้าสู่ระบบ ตาม
   [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการเชิงฟังก์ชัน (Functional Requirements)\|FR-05]]
   ที่แก้ไขแล้ว **FR-14 (จัดการ PatientAssignment) จึงถูกยกเลิก** เพราะไม่มี assignment ให้จัดการอีก
   ต่อไป — ดูรายละเอียดที่ FR-14 ด้านล่าง
8. **FR-15 ไม่ใช่ "ข้อยกเว้น" อีกต่อไป** — เดิม FR-15/NFR-19 ระบุว่า admin เห็นผู้ป่วยทุกรายได้โดยไม่
   ต้องมี PatientAssignment เป็น**ข้อยกเว้น**จาก NFR-02 (ที่เคยจำกัดแพทย์/พยาบาลเฉพาะผู้ป่วยที่ได้รับ
   มอบหมาย) แต่หลังยกเลิก PatientAssignment ทั้งระบบ แพทย์/พยาบาลก็เห็นผู้ป่วยทุกรายเช่นเดียวกับ admin
   แล้ว สิ่งที่ยังคงเป็นลักษณะเฉพาะของ admin คือสิทธิ์**อ่านอย่างเดียว (read-only)** เท่านั้น (ไม่มี
   สิทธิ์ override ผลวิเคราะห์ความเสี่ยงตาม FR-16 ซึ่งเป็นสิทธิ์ของแพทย์/พยาบาล) และการบันทึก audit log
   แบบ fail-safe ตาม NFR-20 ที่ยังคงบังคับใช้เหมือนเดิม
9. **Op.4 (คำขอใช้สิทธิ PDPA ตาม NFR-07) และ Op.16 (override ผลวิเคราะห์ความเสี่ยงตาม FR-16) เปิดให้
   ทุกราย** — ผู้ใช้ยืนยันแล้วว่าการยกเลิก PatientAssignment ให้ครอบคลุมทั้งสอง operation นี้ด้วย
   (ไม่ใช่แค่การดูข้อมูลผ่าน Op.0–3) แพทย์/พยาบาลทุกคน override ผลวิเคราะห์ความเสี่ยงและดำเนินการ
   คำขอ PDPA ของผู้ป่วยทุกรายในระบบได้ ไม่จำกัดเฉพาะผู้ป่วยที่เคย "อยู่ในความดูแล" อีกต่อไป (admin ยัง
   ไม่มีสิทธิ์ override ตามเดิม ดูข้อ 8) ดูรายละเอียดที่ FR-16 ของ
   [[20260917-01-patient-ncd-history-lab-complication-risk|เอกสาร NCD history]] และ NFR-07 ของ
   [[20260921-01-pdpa-data-protection-compliance|เอกสาร PDPA]]
10. **แหล่งความจริงหลักของสิทธิ์** — รายละเอียดสิทธิ์ต่อ operation ล่าสุดทั้งหมด (รวมถึงประเด็นที่ยัง
    รอตัดสินใจอื่นๆ เช่น Op.5 สืบค้น audit trail ของ admin) ยึดตาม [[ACL]] เป็นหลัก

| FR-13 | ระงับ/เปิดใช้งานบัญชีผู้ใช้งาน | Admin ระงับการใช้งาน (`isActive = false`) หรือเปิดใช้งานกลับ (`isActive = true`) บัญชีแพทย์/พยาบาลผ่านหน้าจอในระบบ ผู้ใช้งานที่ถูกระงับต้องไม่สามารถเข้าถึงข้อมูลผู้ป่วยใดๆ ได้ทันที (เชื่อมโยงกับเงื่อนไข isActive ใน [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-02]]) | สูง |
| ~~FR-14~~ | ~~จัดการการมอบหมายผู้ป่วย (Patient Assignment)~~ | **ยกเลิก 2026-09-25 (ยืนยันแล้วโดยผู้ใช้):** ระบบไม่มีกลไก PatientAssignment อีกต่อไป แพทย์/พยาบาล/admin ทุกคนเห็นผู้ป่วยทุกรายอยู่แล้วตาม [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการเชิงฟังก์ชัน (Functional Requirements)\|FR-05]] ที่แก้ไขแล้ว จึงไม่จำเป็นต้องมีหน้าจอมอบหมายผู้ป่วยอีกต่อไป (ข้อความเดิมก่อนยกเลิกอยู่ใน git history ดูเหตุผลเพิ่มเติมที่ [[ACL]]) | ~~สูง~~ |
| FR-15 | ดูประวัติการรักษาของผู้ป่วยทุกรายในระบบ (Admin) | Admin ดูประวัติการวินิจฉัยโรค NCD (FR-01), ผลตรวจ lab (FR-02) และผลวิเคราะห์ความเสี่ยงโรคแทรกซ้อน (FR-03/FR-04) ของผู้ป่วย**ทุกราย**ในระบบแบบอ่านอย่างเดียว (read-only) เท่านั้น ทุกครั้งที่เข้าถึงข้อมูลผู้ป่วยรายบุคคลต้องบันทึก audit log แบบ fail-safe ก่อนเสมอตาม NFR-20 **(อัปเดต 2026-09-25: การเห็นผู้ป่วยทุกรายไม่ใช่ข้อยกเว้นเฉพาะ admin อีกต่อไป เพราะแพทย์/พยาบาลก็เห็นผู้ป่วยทุกรายเช่นกันหลังยกเลิก PatientAssignment — ดูหมายเหตุข้อ 8 ในหัวข้อสมมติฐาน — สิ่งที่ยังคงเป็นลักษณะเฉพาะของ admin คือสิทธิ์อ่านอย่างเดียวเท่านั้น ไม่มีสิทธิ์ override ตาม FR-16)** | สูง |

## ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)

| รหัส | ด้าน | ความต้องการ |
| --- | --- | --- |
| NFR-19 | Security / Access Control (เดิมคือข้อยกเว้นสำหรับบทบาท Admin — **ไม่ใช่ข้อยกเว้นอีกต่อไปตั้งแต่ 2026-09-25**) | **อัปเดต 2026-09-25 (ยืนยันแล้วโดยผู้ใช้):** ข้อความเดิมด้านล่างนี้เคยเป็น "ข้อยกเว้น" ของบทบาท admin จากเงื่อนไข PatientAssignment ของ NFR-02 — แต่หลังระบบยกเลิกกลไก PatientAssignment ทั้งหมด (แพทย์/พยาบาล/admin ทุกคนเห็นผู้ป่วยทุกรายเหมือนกันแล้วตาม [[20260917-01-patient-ncd-history-lab-complication-risk#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-02]] ที่แก้ไข) ข้อกำหนดนี้จึง**ไม่ใช่ข้อยกเว้นเฉพาะ admin อีกต่อไป** สิ่งที่ยังคงเป็นลักษณะเฉพาะของ admin คือสิทธิ์**อ่านอย่างเดียว** (ไม่มีสิทธิ์ override ตาม FR-16) ตามที่ระบุใน FR-15 ข้อความเดิม (ก่อนแก้ไข): ผู้ใช้ที่มี `role = "admin"` และ `isActive = true` เข้าถึงข้อมูลผู้ป่วยทุกรายได้ (FR-15) โดยไม่ต้องผ่านเงื่อนไข PatientAssignment ระดับรายผู้ป่วย เงื่อนไข role/isActive ยังต้องผ่านครบเช่นเดียวกับผู้ใช้งานอื่นทุกคน |
| NFR-20 | PDPA / บันทึกการเข้าถึงข้อมูล (Audit Log สำหรับ Admin) | ทุกครั้งที่ admin เข้าถึง/ดูข้อมูลผู้ป่วยรายบุคคลตาม FR-15 ระบบต้องบันทึก audit log แบบ fail-safe ก่อนเสมอ (บันทึก log ก่อนคืนข้อมูล หากบันทึกไม่สำเร็จต้องปฏิเสธการเข้าถึง) ระบุผู้เข้าถึง (admin คนใด), ผู้ป่วยรายใด และเวลาที่เข้าถึง ขยายเพิ่มเติมจาก [[20260921-01-pdpa-data-protection-compliance#ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)\|NFR-06]] **(หมายเหตุ 2026-09-25: เหตุผลเดิมที่ว่า admin เสี่ยงสูงกว่าเพราะไม่จำกัดตาม PatientAssignment ไม่ใช่จุดต่างอีกต่อไป เนื่องจากแพทย์/พยาบาลก็เห็นผู้ป่วยทุกรายเช่นกันหลังยกเลิก PatientAssignment แต่ข้อกำหนดการบังคับใช้ audit log แบบ fail-safe เฉพาะสำหรับ admin ตามข้อนี้ยังคงมีผลบังคับใช้ตามเดิม ยังไม่ได้ขยายไปถึงแพทย์/พยาบาล — ผู้ใช้ยืนยันเฉพาะเรื่อง FR-16/NFR-07 เท่านั้นในการเปลี่ยนแปลงครั้งนี้)** |

ระดับความสำคัญ (สูง/กลาง/ต่ำ ใช้จัดกลุ่มใน [[backlog]] ตามรูปแบบเดิมของโปรเจกต์ — ตาราง NFR ด้านบน
ไม่มีคอลัมน์นี้โดยตรง สอดคล้องกับรูปแบบที่ใช้ใน [[20260923-01-user-authentication-email-password]]):
NFR-19, NFR-20 = **สูง** (ต้องมีใน MVP เพราะเป็นเงื่อนไขความปลอดภัย/PDPA พื้นฐานที่ FR-15 ซึ่งเป็น MVP
ต้องพึ่งพาโดยตรง — ยืนยันโดยผู้ใช้ผ่าน NEEDS_USER_INPUT เมื่อ 2026-09-24)

  สิทธิ์ของ admin)
