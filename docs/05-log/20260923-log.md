## capture-requirement: เข้าสู่ระบบ/สมัครบัญชี/ลืมรหัสผ่านด้วยอีเมล-รหัสผ่าน (Firebase Authentication)

**Requirement ดิบจากผู้ใช้**

"ผมอยากได้ระบบล็อกอินด้วยอีเมลกับรหัสผ่านของ Firebase"

**การตัดสินใจ: สร้างเอกสารใหม่ vs แก้เอกสารเดิม**

เลือกสร้างเอกสาร spec ใหม่แยกต่างหาก เพราะเป็นฟีเจอร์ authentication ที่ยังไม่เคยถูกกำหนดไว้ในเอกสาร
ใดของโปรเจกต์เลย (ตรวจแล้วว่า
[[20260917-01-patient-ncd-history-lab-complication-risk]], [[20260921-01-pdpa-data-protection-compliance]]
และ [[20260922-01-operational-quality-nfr]] ไม่มีเนื้อหาเรื่องนี้) และเป็น cross-cutting feature
คนละเรื่องกับทั้ง 3 ฉบับ ไม่ใช่การต่อท้ายหรือแทนที่เอกสารใดเอกสารหนึ่ง

**คำถามที่ถามผู้ใช้ผ่าน NEEDS_USER_INPUT และคำตอบที่ได้**

รอบแรก (ก่อนเริ่มงาน โดย orchestrator เป็นผู้ถาม):

1. เริ่มจากเอกสาร requirement ก่อนเขียนโค้ดหรือไม่ → **ทำเอกสารก่อน**
2. ผู้ใช้สมัครบัญชีเองได้หรือไม่ (self sign-up) → **สมัครเองได้**
3. ต้องมีฟังก์ชันลืมรหัสผ่าน/รีเซ็ตรหัสผ่านทางอีเมลใน MVP หรือไม่ → **มี**

รอบสอง (หลังพบว่า self sign-up ขัดกับ NFR-02):

4. การอนุมัติบัญชีหลังสมัคร → **บัญชีใหม่เริ่มต้นไม่มี role และ `isActive=false` ต้องรอผู้ดูแลระบบ
   กำหนด role + เปิดใช้งานภายหลังผ่าน Firebase Console/Firestore (ไม่มีหน้าจออนุมัติในระบบสำหรับ MVP)**
5. การยืนยันอีเมล → **ต้องยืนยันอีเมลก่อนเข้าใช้งาน**
6. นโยบายรหัสผ่าน → **ขั้นต่ำ 8 ตัวอักษร ต้องมีทั้งตัวอักษรและตัวเลข**
7. การป้องกัน Account Enumeration → **ใช้ข้อความ generic ไม่เปิดเผยว่าอีเมลมีในระบบหรือไม่ ทั้งตอน
   login ผิดพลาด, สมัครด้วยอีเมลซ้ำ และลืมรหัสผ่าน**

**เอกสารที่สร้าง/แก้ไข**

- สร้างใหม่: [[20260923-01-user-authentication-email-password]] — เพิ่มรหัส **FR-07, FR-08, FR-09,
  FR-10** (ทั้งหมดระดับสูง) และ **NFR-17 (Password Policy), NFR-18 (Account Enumeration Prevention)**
  (ทั้งสองระดับสูง)
- แก้ไข: [[backlog]] — เพิ่มแถว FR-07–FR-10 ในตาราง "สูง (MVP)" และแถว NFR-17–NFR-18 ในตาราง
  "Non-Functional Requirements" ทั้งหมดสถานะ `Backlog`

**สถานะการอัปเดต backlog.md** — อัปเดตเสร็จสมบูรณ์ ไม่มีรายการเดิมถูกลบ/แก้ไข

Service เป็นตัวกลาง, การสร้าง `users/{uid}` อัตโนมัติ, role เป็น optional จนกว่าจะอนุมัติ) ถูกยืนยัน
จากผู้ใช้ไว้ครบแล้วในรอบ `sync-architecture` ก่อนหน้า ระดับ operation/entity ในรอบนี้เป็นการแปลง
รายละเอียดที่ตัดสินใจแล้วให้เป็น contract ที่ตรงกัน ไม่พบจุดใหม่ที่ต้องเลือก trade-off เพิ่มเติม

**การแก้ไข `docs/02-design/02-technical/db-spec.md`**

- อัปเดตหมายเหตุต้นเอกสารและ "ภาพรวม Entity" ให้ entity ผู้ใช้ (User) อ้างอิง FR-07–FR-10, NFR-17,
  NFR-18 เพิ่มเติม (ไม่มี entity ใหม่ถูกเพิ่ม)
- หัวข้อ "ผู้ใช้ (User)": เปลี่ยน `บทบาท` จาก "จำเป็น" เป็น "ไม่บังคับ" (ค่าว่างจนกว่าจะอนุมัติ), เพิ่ม
  attribute เชิง logical ใหม่ 3 ตัว (`อีเมล`, `รหัสผ่านที่จัดเก็บ`, `สถานะการยืนยันอีเมล`) พร้อมหมายเหตุ
  ชัดเจนว่าจัดเก็บจริงโดย Firebase Authentication ไม่ใช่ Firestore document `users/{uid}` (จึงไม่มี
  field mapping ใน Firestore Technical Binding สำหรับ 3 attribute นี้) และปรับคำอธิบาย
  `สถานะการใช้งานบัญชี`/field mapping `role` ให้ตรงกับ default `isActive=false`/ไม่มี role ตอนสมัคร
- อัปเดต ER Diagram (mermaid) ของ USER ให้มี attribute ใหม่ครบ
- อัปเดตตาราง Security Rules Verification (NFR-14) เพิ่ม test case ใหม่สำหรับบัญชีที่ยังไม่อนุมัติ
- เพิ่มรายการใน "ประเด็นรอตัดสินใจ" (sync role/isActive กับ Custom Claims, Auth Blocking Functions)
  และเพิ่ม [[20260923-01-user-authentication-email-password]] ในเอกสารที่เกี่ยวข้อง

**การแก้ไข `docs/02-design/02-technical/api-spec.md`**

- อัปเดตหมายเหตุต้นเอกสารและหัวข้อ "บทบาทผู้เรียกใช้ (Roles)" เพิ่มบทบาท "ผู้สมัครบัญชี" และระบุ
  "ผู้ดูแลระบบ" เป็นผู้ดำเนินการนอกระบบ (ไม่เรียก operation ใด)
- เพิ่มหมายเหตุในกฎ role-level ของ Operation ร่วม "ตรวจสอบสิทธิ์การเข้าถึงข้อมูลผู้ป่วย" อธิบายว่าบัญชี
  ที่ยังไม่อนุมัติไม่ผ่านการตรวจสอบนี้โดยอัตโนมัติ (ไม่ต้องเพิ่มเงื่อนไขใหม่)

  `emailVerified` ซ้ำ (พึ่งพา Client เท่านั้น ตาม architecture)
- เพิ่ม **Operation 7** (เข้าสู่ระบบ — FR-07, ไม่ผ่าน Backend Service), **Operation 8** (สมัครบัญชี —
  FR-08/FR-09, NFR-17, NFR-18, ผ่าน Backend Service) และ **Operation 9** (ขอรีเซ็ตรหัสผ่าน — FR-10,

**ผลการตรวจสอบ**

- **NFR-01 ถึง NFR-16 (18 รายการ − 2 ใหม่ = 16 รายการเดิม):** สถานะ **รองรับแล้ว (Addressed)** ทั้งหมด
  ไม่มีการถดถอย — NFR-01–08 ตรวจซ้ำแล้วตรงกับรอบที่หกเดิม; NFR-09–16 ตรวจครั้งแรกในรอบนี้ พบว่าออกแบบ

  password policy ฝั่งเซิร์ฟเวอร์จริง (regex ในโค้ด Cloud Function หรือ Identity Platform password
  policy) (2) NFR-18 กลไก suppress error code/ทำเวลาตอบสนองให้ generic เพื่อป้องกัน timing
  side-channel ทั้งสองจุดนี้ถูกเอกสารต้นทาง (architecture, api-spec) ระบุไว้เองแล้วในหัวข้อ "ประเด็นรอ
