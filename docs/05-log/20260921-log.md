1. การแยกเป็นเอกสารใหม่แทนการรวมกับเอกสารเดิม
2. ขอบเขตหัวข้อ PDPA ที่เลือกครอบคลุม (lawful basis, encryption, retention, audit log, data subject
   rights, breach notification support) — อาจมีหัวข้ออื่นที่ผู้ใช้ต้องการเพิ่ม/ตัดออก เช่น การโอนข้อมูล
   ไปต่างประเทศ หรือโครงสร้าง DPO ขององค์กร
3. ระดับความสำคัญ (สูง/กลาง) ของแต่ละ NFR เป็นดุลพินิจของ BA ยังไม่ได้ยืนยันกับผู้ใช้
4. การไม่เพิ่มรหัส FR ใหม่ (ตีความว่าความต้องการดิบเป็นเงื่อนไข/ข้อจำกัดเชิง NFR เป็นหลัก ไม่ใช่ฟีเจอร์
   ใหม่ที่ผู้ใช้มองเห็นได้)
5. การกำหนดฐานทางกฎหมาย (lawful basis) ที่ชัดเจนของ NFR-03 ต้องให้ฝ่ายกฎหมาย/DPO ของหน่วยงานยืนยัน

**สถานะก่อนเริ่มงาน (gate check)**

  อ้างอิง [[20260921-01-pdpa-data-protection-compliance]] ซึ่ง NFR-03/04/06 = สูง, NFR-05/07/08 = กลาง

  NFR-02 (3 ฟีเจอร์, 1 journey) เท่านั้น — **ไม่ up to date** กับ backlog ล่าสุด เพราะ NFR-03–NFR-08
  ยังไม่ถูกกล่าวถึงในทั้งสองไฟล์เลย ตารางสรุป MoSCoW เดิมก็มีแค่ 3 แถว ไม่ครบ
- mermaid diagram เดิมใน journey ตรงกับรายการขั้นตอนแบบข้อความอยู่แล้ว (ก่อนแก้ไขในรอบนี้)

**ปัญหาที่พบระหว่างทำงาน: ไม่มีเครื่องมือ AskUserQuestion**

Sub-agent นี้ไม่มี AskUserQuestion ในชุดเครื่องมือที่ได้รับ (เรียกใช้แล้วขึ้น error "ไม่มีใน
subagent") แม้ prompt งานจะระบุว่าเป็น session สนทนากับผู้ใช้จริงและควรถามเมื่อกำกวมก็ตาม จึงตัดสินใจ
แทนโดยยึดเหตุผลจาก spec ต้นทาง แล้วบันทึกเป็นจุดที่ต้องให้ผู้ใช้ยืนยันไว้อย่างชัดเจนแทน (รูปแบบเดียวกับ
ที่ agent อื่นเคยทำไว้ในงาน capture-requirement ก่อนหน้านี้ในวันเดียวกัน — ดู entry ด้านบน)

**จุดที่กำกวมและตัดสินใจแทน (ต้องให้ผู้ใช้ยืนยัน)**

1. **การจัดกลุ่ม NFR-03–NFR-08 เป็นฟีเจอร์**: เลือกสร้างฟีเจอร์ใหม่ 1 ฟีเจอร์ (#4 "คุ้มครองข้อมูล
   ส่วนบุคคลของผู้ป่วยตาม PDPA") รวมทั้ง 6 รหัส แทนการกระจายเข้าไปในฟีเจอร์ 1-3 เดิม (ทางเลือกอื่นที่
   พิจารณา: กระจาย NFR-03/04/06 เข้าฟีเจอร์เดิมทั้ง 3 อัน + ตั้งฟีเจอร์ใหม่เฉพาะ NFR-05/07/08, หรือ
   กระจายทั้ง 6 รหัสเข้าฟีเจอร์เดิมทั้งหมดโดยไม่ตั้งฟีเจอร์ใหม่เลย) เหตุผลที่เลือกแนวทางนี้: spec ต้นทาง
   ([[20260921-01-pdpa-data-protection-compliance]]) แยกเป็นเอกสารข้ามฟีเจอร์เองโดยตั้งใจให้ครอบคลุม
   ทั้งระบบ ไม่ผูกกับฟีเจอร์ใดฟีเจอร์หนึ่ง — บันทึกหมายเหตุไว้ในหัวข้อฟีเจอร์ที่ 4 ของ
   [[feature-list]] แล้วว่าต้องให้ผู้ใช้ยืนยันอีกครั้ง
2. **การออกแบบ journey ใหม่สำหรับ NFR-06/07/08**: สร้าง journey ที่สองแยกต่างหาก (ไม่ใช่แทรกใน
   journey เดิม) เพราะเป็นสถานการณ์ที่ถูก trigger จากเหตุการณ์ภายนอก (คำขอใช้สิทธิของผู้ป่วย/ข้อสงสัย
   ข้อมูลรั่วไหล) ไม่ใช่ routine การดูแลผู้ป่วยแบบ journey แรก — จุดนี้ค่อนข้างชัดเจนตามเกณฑ์ที่กำหนดไว้
   (สถานการณ์ใหม่จริง) จึงไม่ได้ถือเป็นความกำกวมที่ต้องถาม
3. **บทบาทผู้ใช้ใน journey ที่สอง**: ใช้คำว่า "เจ้าหน้าที่ที่มีสิทธิ์" ตามถ้อยคำที่ NFR-07 ใช้ตรงๆ
   ("เจ้าหน้าที่ที่มีสิทธิ์สามารถค้นหาและสกัดข้อมูล...") แทนที่จะสมมติบทบาทใหม่ เช่น DPO/IT security ที่
   ไม่มีอยู่ใน spec เพราะ spec ระบุชัดว่า "เอกสารนี้ไม่ได้เพิ่มบทบาทใหม่" — ไม่ได้เพิ่มรหัส FR/NFR ใหม่
   หรือคิดค้นบทบาทเอง จึงไม่ได้รายงานเป็น NEEDS_NEW_REQUIREMENT

**ช่องว่างที่พบและการออกแบบเพิ่ม**

- NFR-03 (lawful basis/purpose limitation) ไม่มี component รองรับ → เพิ่มความรับผิดชอบให้กลุ่มงาน
  Access Control เดิมใน Backend Service (ไม่ต้องเพิ่ม component ใหม่)
- NFR-04 (encryption at rest/in transit) ไม่มีการระบุใน diagram/responsibility ใดเลย → เพิ่มเป็น
  cross-cutting property บนทุกเส้นทางสื่อสารและทุกที่เก็บข้อมูล (ไม่วาดเป็น component แยก เพราะไม่ใช่
  หน่วยประมวลผล/จัดเก็บข้อมูลในตัวเอง)
- NFR-05 (retention & deletion), NFR-07 (data subject rights) ไม่มี component รองรับ → เพิ่มกลุ่มงาน
  ใหม่ "Data Subject Rights & Retention Management" ใน Backend Service
- NFR-06 (audit log & accountability), NFR-08 (breach notification support) ไม่มี component รองรับ
  เลย และพิจารณาแล้วว่า logic เดิมของ Backend Service ไม่พอ (ต้องมีที่เก็บบันทึกที่มีคุณสมบัติ
  append-only/immutable แยกจากข้อมูลคลินิกหลัก) → เพิ่ม component ใหม่ **"ที่เก็บบันทึกการเข้าถึง
  (Audit Log Store)"** และกลุ่มงานใหม่ "Audit Logging & Accountability" ใน Backend Service (ยังคงเป็น
  logical component ไม่ระบุ tech ใดๆ — บันทึกไว้ในประเด็นรอตัดสินใจว่าเป็น component ที่ agent นี้
  เพิ่มเข้ามาเอง)

**สิ่งที่ออกแบบเพิ่ม**

*db-spec.md (entity ใหม่ 3 entity):*
- **บันทึกการเข้าถึงข้อมูล (AuditLogRecord)** — id, ผู้ใช้ (ref User), ผู้ป่วย (ref Patient),
  การดำเนินการ (enum: ค้นหา/ดูข้อมูลผู้ป่วย/แก้ไข-ลบ-สกัด-คัดค้านข้อมูลตามคำขอสิทธิ), วันที่-เวลาที่
  เข้าถึง, คำขอสิทธิที่เกี่ยวข้อง (ref DataSubjectRequest, ไม่บังคับ) — หมายเหตุ append-only/immutable
  ตาม NFR-06 (ไม่มี operation ใดแก้ไข/ลบระเบียนรายตัว)
- **คำขอใช้สิทธิของเจ้าของข้อมูล (DataSubjectRequest)** — id, ผู้ป่วย, เจ้าหน้าที่ผู้ดำเนินการ,
  ประเภทคำขอ (เข้าถึง/สำเนา/แก้ไข/ลบ/คัดค้าน), รายละเอียดคำขอ, วันที่ยื่นคำขอ, สถานะคำขอ, วันที่
  ดำเนินการเสร็จสิ้น (NFR-07)
- **นโยบายเก็บรักษาและลบข้อมูล (RetentionPolicy)** — id, ประเภทข้อมูลที่บังคับใช้ (Primary Data
  Store/Audit Log Store แยกกัน), ระยะเวลาเก็บรักษา (จำนวนวัน — ค่าจริงยังไม่กำหนด), เงื่อนไขเริ่มนับ
  ระยะเวลา (NFR-05)
- เพิ่มความสัมพันธ์ 5 เส้นทางใหม่ใน ER diagram/ตาราง Relationships (User/Patient → AuditLogRecord,
  Patient/User → DataSubjectRequest, DataSubjectRequest → AuditLogRecord)
- เพิ่มหัวข้อ "คุณสมบัติร่วม (Cross-cutting Property) — การเข้ารหัสข้อมูล (NFR-04)" ระบุว่าไม่เพิ่ม
  attribute "เข้ารหัสหรือไม่" รายตัว แต่ระบุเป็นข้อกำหนดร่วมกับทุก entity ที่มีข้อมูลส่วนบุคคล (ตรงกับที่
  architecture ออกแบบไว้ว่า encryption เป็น property ไม่ใช่ field/component แยก)

*api-spec.md (operation ใหม่ 3 operation + operation ร่วมใหม่ 1 + แก้ไข operation ร่วมเดิม 1):*
- แก้ไข Operation ร่วม "ตรวจสอบสิทธิ์การเข้าถึงข้อมูลผู้ป่วย" เพิ่มข้อ 3 บังคับ purpose limitation
  (NFR-03) และเพิ่มกฎว่าต้องเรียก Audit Logging ก่อนดำเนินการต่อ
- เพิ่ม **Operation ร่วม — บันทึกร่องรอยการเข้าถึงข้อมูลผู้ป่วย (Audit Logging)** (internal, NFR-06/08)
  เรียกอัตโนมัติหลังผ่าน patient-level check ก่อนดึงข้อมูลจริงเสมอ พร้อม fail-safe (บันทึกไม่สำเร็จ →
  ยกเลิก operation ที่เรียกใช้)
- เพิ่ม **Operation 4 — ยื่นและดำเนินการคำขอใช้สิทธิของเจ้าของข้อมูล** (NFR-07) ใช้ Operation 0 ค้นหา
  ผู้ป่วยก่อน แล้วสร้าง/อัปเดต DataSubjectRequest พร้อมดำเนินการตามประเภทคำขอ
- เพิ่ม **Operation 5 — สืบค้นบันทึกการเข้าถึงข้อมูล (Audit Trail Retrieval)** (NFR-08) สืบค้น
  AuditLogRecord ตามเงื่อนไข พร้อม self-logging
- เพิ่ม **Operation 6 — บังคับใช้นโยบายเก็บรักษาและลบข้อมูลที่พ้นระยะเวลา (Retention Enforcement)**
  (NFR-05, internal/automated — กลไก trigger จริงยังไม่ตัดสินใจ)
- อัปเดตตาราง "กรณี Error ทั่วไป" เพิ่มแถว purpose limitation และ "บันทึก Audit Log ไม่สำเร็จ"
- อัปเดต intro, บทบาทผู้เรียกใช้, ประเด็นรอตัดสินใจ, เอกสารที่เกี่ยวข้อง ให้ครอบคลุมฟีเจอร์ที่ 4/
  ทั้งสอง journey/spec PDPA

  เฉพาะของ HN ช่วยลดความเสี่ยงที่จะทำให้การอ้างอิงข้ามเอกสารเดิมคลาดเคลื่อน อีกทั้งเงื่อนไข validation/
  retry เป็น business rule ที่ทดสอบแยกเป็นอิสระได้ (ควร map เข้า acceptance-criteria.md เป็นรายการของ
  ตัวเอง) จึงคุ้มค่าที่จะมีรหัสเฉพาะ
- ไม่เลือกแนวทางแทนที่เอกสารเดิม เพราะเนื้อหาเดิมยังใช้งานได้ ไม่ได้ล้าสมัย/เปลี่ยนทิศทาง

**หมายเหตุสำคัญ: ไม่มีเครื่องมือ AskUserQuestion ในชุดเครื่องมือของงานนี้**

Sub-agent นี้ไม่มี AskUserQuestion อยู่ในชุดเครื่องมือที่ได้รับ (มีเฉพาะ Read/Write/Edit/Glob/Grep/Bash)
แม้ prompt งานจะระบุว่าเป็น session สนทนากับผู้ใช้จริงและควรถามเมื่อกำกวมก็ตาม จึงยึด Auto Mode
ตัดสินใจแทนโดย BA และบันทึกทุกข้อสมมติฐานไว้ในหัวข้อ "หมายเหตุเพิ่มเติมสำหรับ FR-06" ของเอกสาร spec
แทน (รูปแบบเดียวกับที่ agent อื่นเคยทำไว้ในงานก่อนหน้าในวันเดียวกัน) ประเด็นที่ยังไม่ได้ยืนยันจากผู้ใช้
จริงมีดังนี้ (ต้องขอให้ผู้ใช้ยืนยัน/แก้ไขภายหลัง):

1. **ความสัมพันธ์กับการค้นหาด้วยชื่อใน FR-05** — ตีความว่าการค้นหาด้วยชื่อและการเรียกดูรายชื่อทั้งหมดตาม
   FR-05 เดิมยังคงใช้งานได้คู่ขนานกับ FR-06 (raw requirement ไม่ได้ระบุให้ยกเลิกการค้นหาด้วยชื่อ)
2. **ลักษณะการ validation** — ตีความว่า "ไม่ครบ 7 หลัก" คือ client-side validation แบบ real-time
   ก่อนส่งค้นหา ไม่ใช่ปล่อยให้กดค้นหาก่อนแล้วค่อยแจ้ง error
3. **รูปแบบ HN** — ตีความว่าเป็นตัวเลขล้วน (numeric) 7 หลัก ไม่รวมตัวอักษร
4. **ระดับความสำคัญ FR-06 = สูง** — ตีความว่าเป็นเงื่อนไขบังคับของขั้นตอนแรกสุด (ค้นหาผู้ป่วยก่อนเข้าถึง
   ข้อมูลใดๆ) จึงต้องมีใน MVP เช่นเดียวกับ FR-05

## แก้ไข FR-05/FR-06 ตามผลยืนยันจริงจากผู้ใช้ผ่าน AskUserQuestion (แก้สมมติฐานเดิม)

**บริบท**: entry ก่อนหน้า (เพิ่มเงื่อนไขการค้นหาผู้ป่วยด้วย HN 7 หลัก) ตั้งสมมติฐานไว้ 3 ข้อในหัวข้อ
"หมายเหตุเพิ่มเติมสำหรับ FR-06" ของ [[20260917-01-patient-ncd-history-lab-complication-risk]] เพราะรอบ
นั้นไม่มีเครื่องมือ AskUserQuestion ตอนนี้ผู้ใช้ยืนยัน/แก้ไขสมมติฐานเหล่านั้นจริงผ่าน AskUserQuestion ใน
เทรดหลักแล้ว จึงกลับมาแก้เนื้อหาเอกสารให้ตรงกับผลยืนยันจริง (ไม่ใช่การเพิ่ม requirement ใหม่ — คงรหัส
FR-05/FR-06 เดิม)

**ผลการยืนยัน/แก้ไขจากผู้ใช้**

| ประเด็นเดิม (สมมติฐาน) | ผลยืนยันจริง |
| --- | --- |
| 1. ค้นหาด้วยชื่อ (FR-05 เดิม) ใช้คู่ขนานกับค้นหาด้วย HN (FR-06) ได้ | **เปลี่ยน** — บังคับค้นหาด้วย HN เท่านั้น ตัดช่องทางค้นหาด้วยชื่อออก (การเรียกดูรายชื่อทั้งหมดที่อยู่ในความดูแลโดยไม่ค้นหายังคงใช้งานได้ตามเดิม) |
| 2. validation "ไม่ครบ 7 หลัก" เป็นแบบ real-time ระหว่างพิมพ์ | **เปลี่ยน** — validation เกิดขึ้นหลังผู้ใช้กดค้นหาแล้วเท่านั้น |
| 3. รูปแบบ HN เป็นตัวเลขล้วน 7 หลัก | **ยืนยันตรงตามเดิม** — ไม่ต้องแก้ไข |

**การแก้ไขเอกสาร spec**

แก้ไข [[20260917-01-patient-ncd-history-lab-complication-risk]] (ไม่สร้างไฟล์ใหม่ ไม่เปลี่ยนรหัส FR):

- **FR-05** (ตาราง Functional Requirements): แก้รายละเอียดจาก "ค้นหาและ/หรือเรียกดูรายชื่อ...
  เงื่อนไขการค้นหาด้วยเลขประจำตัวผู้ป่วย (HN) โดยเฉพาะดูรายละเอียดเพิ่มเติมที่ FR-06" เป็น "เรียกดูรายชื่อ
  ผู้ป่วยทั้งหมดที่อยู่ในความดูแล และ/หรือค้นหาผู้ป่วยเฉพาะรายด้วย HN เท่านั้น (ไม่รองรับการค้นหาด้วยชื่อ
  — ยืนยันแล้ว ดูหมายเหตุ FR-06)" ส่วนโครงสร้างที่เหลือ (การเป็นขั้นตอนแรกสุดของ journey, ข้อจำกัดตาม
  assignment/NFR-02) คงเดิม เพราะยังใช้ได้ ไม่กระทบจากการตัดช่องทางค้นหาด้วยชื่อ
- **FR-06** (ตาราง Functional Requirements): เพิ่มข้อความยืนยันรูปแบบ HN, ระบุว่าเป็นช่องทางค้นหาเดียวที่
  ใช้งานได้ (ไม่มีค้นหาด้วยชื่ออีกต่อไป), เปลี่ยนจุดเวลาของ validation เป็น "หลังผู้ใช้กดค้นหาแล้ว
  เท่านั้น" และแก้ประโยคสุดท้ายจาก "ไม่บล็อกการใช้งานช่องทางค้นหาอื่น (เช่น ค้นหาด้วยชื่อ...)" เป็น
  "ไม่บล็อกการเรียกดูรายชื่อทั้งหมดตาม FR-05" (เพราะช่องทางค้นหาด้วยชื่อถูกตัดออกแล้ว เหลือแค่การเรียกดู
  รายชื่อทั้งหมดเป็นทางเลือกคู่ขนานที่ยังใช้ได้จริง)
- **หัวข้อสมมติฐาน (Assumptions)**: แก้ "หมายเหตุเพิ่มเติมสำหรับ FR-05" — แยกส่วน "เกณฑ์การค้นหา" ออกจาก
  ส่วน "อยู่ในความดูแล" (assignment) อย่างชัดเจน ส่วนเกณฑ์การค้นหาเปลี่ยนสถานะเป็น **"ยืนยันแล้ว
  2026-09-21 ผ่าน AskUserQuestion"** ระบุบังคับ HN เท่านั้น ส่วน assignment ("อยู่ในความดูแล") ยังคง
  เป็นสมมติฐานที่รอการยืนยัน (ไม่ได้อยู่ใน 3 ประเด็นที่ผู้ใช้เพิ่งยืนยันรอบนี้ จึงไม่แตะต้อง) — แก้
  "หมายเหตุเพิ่มเติมสำหรับ FR-06" ทั้ง 3 ข้อ เปลี่ยนป้ายกำกับเป็น "(ยืนยันแล้ว)" ทุกข้อ พร้อมเนื้อหาที่
  ปรับตามผลยืนยันจริง (ข้อ 1 และ 2 เปลี่ยนเนื้อหา, ข้อ 3 คงเดิมแต่เปลี่ยนสถานะเป็นยืนยันแล้ว)

**ตรวจสอบ backlog.md**: อ่าน [[backlog]] แล้ว — คอลัมน์ "หัวข้อ" ของ FR-05 ("ค้นหา/แสดงรายชื่อผู้ป่วย NCD
ที่อยู่ในความดูแล") และ FR-06 ("ค้นหาผู้ป่วยด้วยเลข HN แบบ 7 หลัก พร้อม validation") เป็นชื่อหัวข้อสั้นๆ
ที่ยังตรงกับเนื้อหาที่แก้ไขแล้ว ไม่ต้องแก้ไข **ไม่มีการเปลี่ยนแปลง backlog.md ในรอบนี้**

**เหตุผลที่แก้เอกสารเดิมแทนสร้างใหม่**: นี่คือการแก้ไขเนื้อหาให้ถูกต้องตามที่ผู้ใช้ยืนยันจริง ไม่ใช่การ
เพิ่ม requirement ใหม่ รหัส FR-05/FR-06 เดิมยังใช้อ้างอิงในเอกสารอื่น
([[20260921-01-pdpa-data-protection-compliance]] อ้าง FR-05) การแก้ไขในที่เดิมโดยคงรหัสเดิมจึงถูกต้อง
ที่สุด ไม่กระทบ wikilink/การอ้างอิงข้ามเอกสารที่มีอยู่แล้ว

   รายชื่อทั้งหมด) เส้นทางกรอก HN แสดงลำดับ Client ส่งค่าไปยัง Backend ก่อน (ไม่ตรวจสอบฝั่ง Client) →
   Backend ตรวจสอบรูปแบบ 7 หลักตัวเลขล้วน → ถ้าไม่ผ่านหยุดทันทีไม่อ่าน PatientAssignment/Patient → ถ้า
   ผ่านจึงอ่าน PatientAssignment แล้วค้นหา Patient แบบ exact match เฉพาะในขอบเขตนั้น → แจ้งเตือนแยกกัน
   ระหว่าง "HN ไม่ครบ 7 หลัก" กับ "ไม่พบผู้ป่วย"
3. แก้ตาราง Operation↔Entity: เพิ่มแถวใหม่สำหรับขั้นตอนตรวจสอบรูปแบบ HN (ไม่กระทบ entity ใด) และแก้
   คำอธิบายแถว Patient จาก "กรองด้วยคำค้นบางส่วน" เป็น "exact match เฉพาะในขอบเขต PatientAssignment"
4. เพิ่ม State Diagram ใหม่แยกต่างหาก "สถานะขั้นตอนค้นหาด้วยเลข HN" แสดง retry loop ของทั้งสองกรณี error
   (ไม่ครบ 7 หลัก / ไม่พบผู้ป่วย) ตาม [[user-journey]] ขั้นตอนที่ 4–6 — คงเดิม State Diagram สิทธิ์
   role-level/patient-level ไว้ (ไม่มีการเปลี่ยนแปลงในส่วนนี้)
5. แก้ตาราง Edge Case: แยก "ค้นหาแล้วไม่พบผู้ป่วยที่ตรงคำค้น" เดิมออกเป็น 2 แถวใหม่ตาม 2 กรณี error ของ
   Operation 0 ใน api-spec ("HN ไม่ครบ 7 หลัก" และ "ค้นหาด้วย HN ครบ 7 หลักแล้วไม่พบ") พร้อมระบุว่าทั้งสอง
   กรณีต้องใช้ข้อความแจ้งเตือนคนละแบบ และกรณีไม่พบต้องไม่เปิดเผยว่า HN มีอยู่จริงแต่อยู่นอกความดูแล

## ปิดช่องว่าง NFR-02 (Client ต้องไม่แสดง/cache ข้อมูลผู้ป่วยที่ละเอียดอ่อนเกินความจำเป็น) — เรียกผ่าน `detailed-design-writer`

  "Client ต้องไม่แสดงหรือ cache ข้อมูลผู้ป่วยที่ละเอียดอ่อนไว้เกินความจำเป็นบนฝั่งผู้ใช้" (ส่วนหนึ่งของ
  NFR-02 ในตาราง Mapping NFR และหัวข้อขอบเขตความรับผิดชอบของ Client) ยังไม่เคยถูกส่งต่อไปยังไฟล์ใดใน

   nfr-reviewer แนะนำ): เพิ่มหัวข้อหลักอธิบายหลักการครบ 4 ข้อ (แสดงเฉพาะเท่าที่จำเป็นในหน้าจอปัจจุบัน,
   ล้างเมื่อออกจากหน้าจอ/เลือกผู้ป่วยใหม่/logout, ขอบเขตเฉพาะรายชื่อ/ผลค้นหาของฟีเจอร์นี้ ส่วนฟีเจอร์อื่น
   อ้างอิงไปที่ไฟล์นั้นๆ, กลไกจริงรอ `technology-stack.md`) พร้อมเพิ่ม 3 แถวใน Edge Case (ออกจากหน้าจอ
   โดยไม่เลือกผู้ป่วย, ค้นหา/เลือกผู้ป่วยรายใหม่แทนที่ชุดเดิม, logout/session สิ้นสุด)

   เพิ่ม 1 แถว Edge Case
