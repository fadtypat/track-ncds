# Log — 2026-09-26

## AI ช่วยอธิบายผลการค้นหาผู้ป่วยด้วย HN (FR-17) + จำกัดข้อมูลที่ส่งให้บริการ AI ภายนอก (NFR-21)

**requirement ดิบ:** "ผมอยากให้ AI ช่วย track-ncds ในหน้า ค้นหาด้วยเลข HN พิมพ์ในช่องค้นหา พอหยุดพิมพ์
หรือกดค้นหา ให้ AI เอาคำตอบมาแสดง"

### คำถามที่ถามผู้ใช้และคำตอบ (ยืนยันแล้วผ่านการสนทนาจริงก่อนเรียก agent นี้)

1. AI ทำหน้าที่ "อธิบายผลการค้นหาเป็นภาษาคน" (พบผู้ป่วย/ไม่พบผู้ป่วย/HN ไม่ครบ 7 หลัก) เท่านั้น —
   ไม่ใช่แชตตอบคำถามอิสระ และไม่ใช่การแนะนำขั้นตอนทางคลินิก
2. ห้ามส่งชื่อผู้ป่วยหรือข้อมูลระบุตัวตนใดๆ ให้บริการ AI — ส่งได้เฉพาะ HN ที่พิมพ์ และผลการค้นหาแบบไม่
   ระบุตัวตน (สถานะ/จำนวนที่พบ)
3. AI ทำงานทั้งตอน "หยุดพิมพ์" และตอน "กดค้นหา" — ขัดกับ FR-06 เดิมที่กำหนดให้ตรวจสอบ HN หลังกดค้นหา
   เท่านั้น จึงต้องแก้ไข FR-06
4. ใช้บนเว็บจริง (production) ไม่ใช่แค่เครื่องนักพัฒนา
5. ผู้ใช้เลือกเทคโนโลยี AI แล้ว แต่ spec ต้องไม่ระบุชื่อเทคโนโลยี (บันทึกใน `technology-stack.md`
   ภายหลังผ่าน `/build-tech-stack`) — spec ระบุเพียงระดับ logical ว่าเป็น "บริการ AI ภายนอก"

### คำถามที่ถาม agent นี้ถามเพิ่มเติมผ่าน NEEDS_USER_INPUT (ตอบแล้วโดยผู้ใช้ผ่าน AskUserQuestion)

- **Q1 (ระดับความสำคัญ FR-17):** สูง/กลาง/ต่ำ? → **ผู้ใช้ตอบ: กลาง** (ฟีเจอร์เสริมต่อยอดจาก FR-05/FR-06
  ที่เป็นสูงอยู่แล้ว การค้นหายังทำงานได้สมบูรณ์แม้ไม่มี AI)
- **Q2 (ระดับความสำคัญ NFR-21):** สูง/กลาง/ต่ำ? → **ผู้ใช้ตอบ: สูง** (เป็นรั้วกั้นความปลอดภัยด้านข้อมูล
  ผู้ป่วยที่ต้องบังคับใช้ทันทีที่ FR-17 ถูกพัฒนา ไม่ผูกกับระดับความสำคัญของ FR-17 เอง)

### เหตุผลการตัดสินใจ: แก้ไขเอกสารเดิม ไม่สร้างเอกสารใหม่

FR-17 ผูกกับหน้าค้นหาผู้ป่วยด้วย HN (FR-05/FR-06) โดยตรงในเอกสารเดียวกัน และ FR-06 เองก็ต้องถูกแก้ไข
อยู่แล้วตามคำตอบข้อ 3 (จาก "ตรวจสอบหลังกดค้นหาเท่านั้น" เป็น "ตรวจสอบได้ทั้งตอนหยุดพิมพ์และกดค้นหา")
จึงเพิ่ม FR-17 ต่อท้ายในเอกสารเดียวกับ FR-05/FR-06 แทนการแยกไฟล์ใหม่ ส่วน NFR-21 (ข้อจำกัดข้อมูลที่ส่ง
ให้บริการ AI ภายนอก) เป็นประเด็น PDPA/data minimization โดยตรง จึงเพิ่มต่อท้ายในเอกสาร PDPA ที่มีอยู่แล้ว
(ขยายจากหลักการ Purpose Limitation ของ NFR-03 แต่แยกเป็นรหัสใหม่เพราะเจาะจงความเสี่ยงการส่งข้อมูลให้
ผู้ประมวลผลข้อมูลภายนอก ซึ่งเป็นคนละมิติจากการเข้าถึงข้อมูลภายในระบบ)

## `/build-tech-stack` — เพิ่ม decision area 20-22 สำหรับ FR-17/NFR-21 (2026-09-26)

โหมดการแก้ไขที่ผู้ใช้เลือก: **"เพิ่มเติมเฉพาะ component/decision area ใหม่"** (ไม่ rebuild
`technology-stack.md` ทั้งไฟล์ — decision area 1-19 เดิมไม่ถูกแตะต้อง)

### บริบทที่ผู้ใช้ให้มาล่วงหน้าในแชต (ไม่ต้องถามซ้ำผ่าน intake)

1. ใช้ **Firebase AI Logic (Gemini Developer API backend)** เรียกจาก Client ตรงผ่าน `firebase/ai` SDK
   แทน "OpenRouter ผ่าน Cloud Function" เพราะโปรเจกต์ยังไม่อยู่แพ็กเกจ Blaze
2. โมเดล **`gemini-2.5-flash-lite`** — ยอมรับความเสี่ยงถูกปิดให้บริการเร็วสุด 2026-10-16 (เอกสาร
   Firebase แนะนำ `gemini-3.5-flash-lite` แทน) และต้องกำหนดชื่อโมเดลไว้จุดเดียวในโค้ด
3. Firebase บังคับเปิด **App Check** ให้ AI Logic อัตโนมัติตั้งแต่ ก.ค. 2026
4. ใช้บนเว็บจริง (production)
5. หน้าทดสอบ `/dev/ai-test` ที่เรียก OpenRouter ตรงเป็น dev-only ไม่ใช่ส่วนหนึ่งของ stack จริง

### คำถามที่ถามผู้ใช้ผ่าน `NEEDS_USER_INPUT`/`AskUserQuestion` และคำตอบ

- **Q1 (App Check provider):** reCAPTCHA v3 / reCAPTCHA Enterprise / Custom provider? → **ผู้ใช้ตอบ:
  reCAPTCHA v3 (production) + Debug Provider (local dev)** — ใช้งานได้บนแพ็กเกจ Spark โดยไม่ต้องเปิด
  billing ของ Google Cloud
- **Q2 (จังหวะเรียก AI):** Timer เดียวร่วมกับ debounce ค้นหา / Timer แยกช้ากว่า / เรียกเฉพาะตอนกดค้นหา
  เท่านั้น? → **ผู้ใช้ตอบ: เรียก AI เฉพาะตอนกดค้นหาเท่านั้น** — เลือกโดยรู้ตัวว่าขัดกับข้อความปัจจุบันของ
  FR-17 (ที่ยืนยันให้ทำงานทั้งตอนหยุดพิมพ์และกดค้นหา) ผู้ใช้ยืนยันจะสั่งแก้ไข FR-17 ผ่าน
  `/capture-requirement` แยกต่างหากในภายหลัง (บันทึกไว้ใน `technology-stack.md` หัวข้อ "ประเด็นรอ
  ตัดสินใจ" และหัวข้อความเสี่ยงเพิ่มเติมแล้ว) — FR-06 (debounce ตรวจสอบรูปแบบ HN/ค้นหาปกติ) ไม่ได้รับ
  ผลกระทบ ยังทำงานทั้ง 2 จังหวะตามเดิม
- **Q3 (จุดกำหนดชื่อโมเดล):** Constant เดียวในโค้ด / Environment variable ผ่าน Vite / Firebase Remote
  Config? → **ผู้ใช้ตอบ: Constant เดียวใน `web/src/ai/config.ts`**
  (`GEMINI_MODEL_NAME = "gemini-2.5-flash-lite"`) — ง่ายที่สุด แลกกับการต้อง build+deploy ใหม่ทุกครั้งที่
  เปลี่ยนโมเดล (ไม่เปลี่ยนแบบ runtime ได้)

### การตัดสินใจที่บันทึกใน `technology-stack.md`

- **decision area 20** — AI ช่วยอธิบายผลการค้นหาผู้ป่วยด้วย HN: Firebase AI Logic (Gemini Developer
  API) เรียกตรงจาก Client ไม่มี Cloud Function ตัวกลาง → บังคับ NFR-21 ได้แค่ฝั่ง Client, ไม่มี audit log
  ฝั่งเซิร์ฟเวอร์สำหรับ path นี้จนกว่าจะอยู่ Blaze, ถ้า AI ล้มเหลวการค้นหาปกติต้องยังทำงานได้
  (non-blocking)
- **decision area 21** — App Check: reCAPTCHA v3 (production) + Debug Provider (local dev)
- **decision area 22** — จุดกำหนดชื่อโมเดล: constant เดียวใน `web/src/ai/config.ts`
- เพิ่มแถวใหม่ 4 แถวในตารางสรุป Component → เทคโนโลยี, ปรับปรุง Deployment Diagram (เพิ่ม node
  `AppCheck`, `AILogic`, `GeminiAPI`), เพิ่มหัวข้อความเสี่ยง "กลไก AI เรียกเฉพาะตอนกดค้นหา ขัดกับข้อความ
  ปัจจุบันของ FR-17", เพิ่มรายการใน "ประเด็นรอตัดสินใจ" (แก้ไข FR-17, ย้ายไปใช้ Cloud Function ตัวกลาง
  เมื่ออยู่ Blaze, Remote Config สำหรับชื่อโมเดล, reCAPTCHA Enterprise เมื่ออยู่ Blaze)

## `/build-tech-stack` — แก้ไขโมเดล AI จาก gemini-2.5-flash-lite เป็น gemini-3.5-flash-lite (2026-09-26)

### เหตุการณ์

ผู้ใช้ทดสอบเรียก Firebase AI Logic จริงจากเว็บแอป (`web/`) แล้วได้รับ **HTTP 404** พร้อมข้อความ:

> "This model models/gemini-2.5-flash-lite is no longer available to new users. Please update your
> code to use models/gemini-3.5-flash-lite"

แสดงว่า `gemini-2.5-flash-lite` หยุดรองรับผู้ใช้ใหม่**เร็วกว่ากำหนดการที่เคยประเมินไว้ (2026-10-16)**
ที่บันทึกไว้ใน decision area 22 เดิม ผู้ใช้ยืนยันเปลี่ยนไปใช้ **`gemini-3.5-flash-lite`** ตามที่ error
message แนะนำ และได้ทดสอบเรียกจริงสำเร็จแล้วบน Gemini Developer API (ไม่ต้องอัปเกรดเป็น Blaze) พร้อม
App Check Debug Provider — โค้ดถูกแก้ไขแล้วที่ `web/src/ai/config.ts`
(`GEMINI_MODEL_NAME = "gemini-3.5-flash-lite"`) ก่อนแจ้งมาให้ปรับปรุงเอกสาร

### สิ่งที่แก้ไขใน `technology-stack.md`

- **decision area 20** — อัปเดตชื่อโมเดลเป็น `gemini-3.5-flash-lite` และเพิ่มหมายเหตุว่า FR-17 ถูกแก้ไข
  ผ่าน `/capture-requirement` ให้ตรงกับกลไก "เรียก AI เฉพาะตอนกดค้นหา" แล้ว — ความเสี่ยงที่เคยบันทึกไว้
  (spec ขัดกับ technology-stack) **คลี่คลายสมบูรณ์แล้ว**
- **decision area 22** — บันทึกเหตุการณ์ 404 แบบเต็ม (ข้อความ error จริง, การทดสอบสำเร็จกับ App Check
  Debug Provider), ปรับเหตุผลว่าการเลือก constant เดียวใน `web/src/ai/config.ts` **พิสูจน์คุณค่าจริงแล้ว**
  ในเหตุการณ์นี้ (แก้ค่าเดียวจบ ไม่ต้องไล่หาทั่วโค้ด), ระบุชัดว่า **ความเสี่ยงเรื่องกำหนดปิดบริการ
  2026-10-16 ของ `gemini-2.5-flash-lite` ไม่มีผลอีกต่อไป** (เปลี่ยนโมเดลไปแล้วจริง) แต่ยังคงความเสี่ยงทั่วไป
  ไว้ว่าโมเดลรุ่นถัดไปอาจถูกปิดกะทันหันแบบไม่มีสัญญาณเตือนที่แน่นอนอีกในอนาคต — คง "ทางเลือกอื่นที่ไม่เลือก"
  (env var, Remote Config) ไว้เหมือนเดิมแต่เพิ่มบริบทว่า Remote Config มีประโยชน์มากขึ้นถ้าเหตุการณ์แบบนี้
  เกิดซ้ำ
- อัปเดตแถวตารางสรุป Component → เทคโนโลยี 3 แถว (AI-Powered Search Result Explanation, App Check,
  จุดกำหนดชื่อโมเดล) ให้ตรงกับโมเดลใหม่และบริบทเหตุการณ์นี้
- อัปเดต Deployment Diagram (node `AILogic`) ให้แสดง `gemini-3.5-flash-lite`
- อัปเดตหัวข้อความเสี่ยง "กลไก AI เรียกเฉพาะตอนกดค้นหา ขัดกับข้อความปัจจุบันของ FR-17" เป็น **แก้ไขแล้ว**
  (FR-17 ถูกแก้ไขให้ตรงกับกลไกนี้แล้วผ่าน `/capture-requirement`)
- อัปเดต "ประเด็นรอตัดสินใจ": ขีดฆ่ารายการ "แก้ไข FR-17" (เสร็จแล้ว), ปรับรายการ Remote Config ให้สะท้อน
  บทเรียนจากเหตุการณ์นี้ (โมเดลถูกปิดกะทันหันเร็วกว่าประกาศ)

## `/capture-requirement` — แก้ FR-17 ให้ AI ทำงานเฉพาะตอนกดค้นหา สอดคล้องกับ decision area 20 (2026-09-26)

**requirement ดิบ:** ยืนยันคำตอบเดิมที่ผู้ใช้เลือกไว้ระหว่าง `/build-tech-stack` วันนี้ ("AI เฉพาะตอนกด
ค้นหา" — ประหยัด quota สูงสุด แต่ขัดกับ FR-17 เดิมที่ยืนยันให้ทำงานทั้ง 2 จังหวะ) มาแก้ spec ให้ตรงกับ
กลไกจริงที่บันทึกไว้ใน `technology-stack.md` decision area 20

### วิเคราะห์ว่าควรสร้างเอกสารใหม่หรือแก้เอกสารเดิม

เลือก **แก้เอกสารเดิม** ([[20260917-01-patient-ncd-history-lab-complication-risk]]) — FR-17 อยู่ในเอกสาร
นี้อยู่แล้ว (เพิ่มไปเมื่อช่วงเช้าวันเดียวกัน) การเปลี่ยนแปลงนี้เป็นการแก้ไขจังหวะการเรียก AI ของ FR-17
เดิม ไม่ใช่ requirement ใหม่ และไม่กระทบขอบเขต/รหัสอื่นนอกจากหมายเหตุประกอบที่ผูกกับ FR-06 อยู่แล้ว
จึงไม่มีเหตุผลให้แยกไฟล์ใหม่หรือ archive ของเดิม (ไม่ต้องออก NEEDS_USER_INPUT เพราะทิศทางชัดเจนจาก
requirement ดิบและขอบเขตงานที่ได้รับมา)

### เอกสารที่แก้ไข

- [[20260917-01-patient-ncd-history-lab-complication-risk]]
  - แก้หมายเหตุ FR-06 ข้อ 2 (หัวข้อสมมติฐาน) — เพิ่มส่วน "แก้ไขเพิ่มเติม 2026-09-26 รอบสอง" ระบุว่าการ
    เรียก AI **ไม่ได้**ทำงานทั้ง 2 จังหวะอีกต่อไป ทำงานเฉพาะตอนกดปุ่มค้นหาเพื่อประหยัด quota ส่วนการ
    ตรวจสอบรูปแบบ HN/ค้นหาผู้ป่วยตาม FR-06 เองยังคงทำงานทั้ง 2 จังหวะเหมือนเดิม ไม่เปลี่ยนแปลง
  - แก้หมายเหตุ FR-17 ข้อ 3 "จังหวะการทำงาน" — เปลี่ยนจาก "ทำงานทั้งตอนหยุดพิมพ์และกดค้นหา" เป็น
    "ทำงานเฉพาะตอนกดปุ่มค้นหาเท่านั้น" พร้อมเหตุผล (ประหยัด quota) และย้ำว่า FR-06 ไม่เปลี่ยน
  - แก้ข้อความรายละเอียดของ **FR-17** ในตาราง Functional Requirements ให้ตรงกับจังหวะใหม่ (เฉพาะกด
    ค้นหา) พร้อมหมายเหตุแทนที่ข้อความเดิม — **ระดับความสำคัญยังคงเป็น "กลาง" เหมือนเดิม ไม่เปลี่ยน**
  - **FR-06 ไม่เปลี่ยนแปลง** (ทั้งข้อความในตารางและเจตนา) — การตรวจสอบรูปแบบ HN/ค้นหาผู้ป่วยยังทำงานได้
    ทั้งตอนหยุดพิมพ์และกดค้นหาตามเดิม มีเพียงการเรียก AI เท่านั้นที่ถูกจำกัดจังหวะ
- [[backlog]] — ตรวจสอบแล้ว แถว FR-17 ปัจจุบันอ้างอิงผ่าน wikilink ไปยังหัวข้อ FR-17 ในเอกสาร spec
  โดยไม่มีข้อความอธิบายจังหวะการทำงานซ้ำในตัวเอง จึงไม่ต้องแก้ไขเพิ่มเติม (คำอธิบายที่ถูกต้องอยู่ใน
  spec ต้นทางที่ backlog ลิงก์ไปแล้ว)

### รหัส FR/NFR ที่เพิ่ม/แก้ไข

- **FR-17** — แก้ไขเนื้อหา (จังหวะการเรียก AI: เฉพาะกดค้นหา) ระดับความสำคัญคงเดิม **กลาง** — ไม่ใช่รหัส
  ใหม่ ไม่มีรหัสใหม่เพิ่มเข้ามาในรอบนี้
- **FR-06** — ไม่เปลี่ยนแปลง (ตรวจสอบแล้วว่าไม่ต้องแก้)
- **NFR-21** — ไม่เปลี่ยนแปลง (อยู่นอกขอบเขตงานนี้)

### สรุปคำถาม-คำตอบ

ไม่มีการออก `NEEDS_USER_INPUT` เพิ่มเติมในรอบนี้ — คำตอบที่ต้องใช้ยืนยันมาจากการสนทนาจริงระหว่าง
`/build-tech-stack` ก่อนหน้า (บันทึกไว้แล้วในหัวข้อด้านบนของ log วันนี้: Q2 จังหวะเรียก AI) และคำสั่งงาน
ที่ระบุขอบเขตชัดเจนแล้ว (FR-06 ไม่เปลี่ยน, ระดับความสำคัญ FR-17/NFR-21 ไม่เปลี่ยน)

### ความสอดคล้องกับ `technology-stack.md`

ยืนยันว่า spec (FR-17) สอดคล้องกับ decision area 20 ของ `technology-stack.md` แล้ว (กลไกเรียก AI

พิจารณาปิด/ปรับปรุงข้อความในรอบถัดไปที่มีการแก้ `technology-stack.md` โดยตรง

### สถานะการอัปเดต backlog.md

แล้วผ่าน wikilink ไม่ได้ทำซ้ำคำอธิบายจังหวะการทำงานในตัวเอง

## `/audit-backlog` — ตรวจสอบความสอดคล้องระหว่าง backlog.md กับ 01-spec/ ทั้งหมด (2026-09-26)

  อยู่ในตารางกลุ่ม "กลาง" แยกจากกลุ่ม MVP สูง — ตรงกับ spec) และ NFR-21 (หัวข้อ "PDPA / จำกัดข้อมูลที่ส่ง
  ให้บริการ AI ภายนอก (Data Minimization for External AI Service)", ระดับ **สูง** — ตรงกับ spec) รวมถึง
  รหัสอื่นทั้งหมด (FR-01–FR-05, FR-07–FR-16, NFR-01–NFR-20) เทียบหัวข้อ/ระดับความสำคัญ/เอกสารอ้างอิงแล้ว

## `/sync-feature-journey` — sync FR-17/NFR-21/FR-06 เข้า feature-list.md และ user-journey.md (2026-09-26)

### สถานะก่อนเริ่มงาน

`feature-list.md` และ `user-journey.md` **ยังไม่ up to date** กับ backlog ล่าสุด — ขาดรหัส FR-17

(ตรวจสอบรูปแบบ HN ทำงานได้ทั้งตอนหยุดพิมพ์และกดค้นหา แทนที่ "หลังกดค้นหาเท่านั้น") ตารางสรุป MoSCoW

พิจารณาแล้วว่า FR-17 ควรอยู่ในฟีเจอร์ที่ 3 "ค้นหา/เลือกผู้ป่วย" (เป็นส่วนขยายโดยตรงของขั้นตอนค้นหาด้วย
HN/FR-06 ไม่ใช่สถานการณ์ใหม่) และ NFR-21 ควรอยู่ในฟีเจอร์ที่ 4 "คุ้มครองข้อมูลส่วนบุคคลของผู้ป่วยตาม
PDPA" (เป็นข้อกำหนด data minimization เช่นเดียวกับรหัส PDPA อื่นในฟีเจอร์นั้น) ไม่กำกวม จึงไม่ต้องออก
`NEEDS_USER_INPUT` ถามเรื่องการจัดกลุ่ม

  โค้ดจริง `web/src/pages/PatientListPage.tsx`/`searchPatientByHn` เป็นหลักฐาน
- **ย่อหน้าอธิบาย Data Flow Diagram — Journey หลัก:** แก้ให้ระบุว่าทั้งสองจังหวะยิง query จริงเหมือนกัน
