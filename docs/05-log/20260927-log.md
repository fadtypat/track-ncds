- [[ACL]] — แหล่งความจริงหลักของสิทธิ์: ทุกบทบาท (แพทย์/พยาบาล/admin) เห็นผู้ป่วยทุกรายในระบบเหมือนกัน
  หลังผ่านเงื่อนไข role/isActive/email_verified ระดับบัญชีเท่านั้น ไม่มีการกรองระดับรายผู้ป่วยอีกต่อไป
- [[api-spec]] — หัวข้อ "Operation 14, 15 — ยกเลิกแล้ว (2026-09-25)"; Operation 0 อ่าน collection
  `patients` โดยตรงด้วย equality query บน `hn` (หรืออ่านทั้ง collection เมื่อไม่ระบุ HN) ไม่ต้องมี

2. **Decision area 3** (สถาปัตยกรรม Backend Service) — แก้ข้อความ "แสดงรายชื่อผู้ป่วยในความดูแล"/

   เพียง role/isActive/email_verified ระดับบัญชีเท่านั้น"
3. **Decision area 4** (Database Engine) — เขียนหมายเหตุแก้ไขและขีดฆ่าย่อหน้า/bullet ที่อธิบาย
   PatientAssignment เป็นความสัมพันธ์ N:M ที่ต้อง denormalize เป็น collection `patientAssignments`

   `patientAssignments` เป็น `patients`; แก้ตัวอย่าง test case ของ NFR-14 ที่เคยเขียนว่า "role/isActive/

6. **หัวข้อ "ความเสี่ยงที่ต้องพิจารณาเพิ่มเติม"** (ความเสี่ยงของ Firestore Security Rules ตรวจสอบ 2

   check) ไม่มีผลอีกต่อไป, ปรับรายการ automated test ที่แนะนำให้ตรงกับเงื่อนไขปัจจุบัน (บทบาท/isActive/

## `/build-tech-stack` — เพิ่ม decision area 23 สำหรับ FR-18 (สรุปจำนวนครั้งตรวจ HbA1c/ระยะห่างระหว่างการตรวจในปีงบประมาณ) (2026-09-27)

area 1-22 เดิม

### FR-18/NFR-21 (ขยาย) ที่เพิ่งบันทึกในสายเอกสาร spec/backlog

- **FR-18** (ระดับ **กลาง**) — [[20260917-01-patient-ncd-history-lab-complication-risk]]: ปุ่มบนการ์ด
  ผู้ป่วยแต่ละรายในหน้ารายชื่อ (FR-05) คำนวณวันที่ตรวจ HbA1c/จำนวน visit/ระยะห่างเป็นวันในปีงบประมาณไทย
  (1 ต.ค.–30 ก.ย.) แล้วให้ AI เขียนสรุปเป็นภาษาไทย บันทึกผลลง Firestore
- **NFR-21** (ขยายเพิ่ม 2026-09-27) — [[20260921-01-pdpa-data-protection-compliance]]: ข้อมูลที่ส่งให้
  AI จำกัดเฉพาะตัวเลขสรุปที่คำนวณแล้ว (จำนวน visit, ระยะห่างเป็นวัน) ห้ามส่ง HN/ชื่อ/วันที่ตรวจจริง/
  ค่าผล HbA1c เด็ดขาด

### บริบทที่ผู้ใช้ตัดสินใจแล้วในแชต (ไม่ต้องถามซ้ำ — ตามที่ coordinator ส่งมาพร้อมงาน)

1. ขั้นที่ 1-2 (วันที่ตรวจ, จำนวน visit, ระยะห่างเป็นวัน) คำนวณในโค้ด ไม่ใช่ AI — AI เขียนแค่ประโยคสรุป
   จากตัวเลขที่คำนวณแล้ว
2. ส่งเฉพาะตัวเลขสรุปให้ AI (จำนวน visit, ระยะห่างเป็นวัน, min/avg/max) ไม่ส่ง HN/ชื่อ/วันที่ตรวจ/ค่า
   HbA1c (NFR-21 ขยาย)
3. บันทึกผลลง collection ใหม่ที่ผู้ใช้อนุมัติ: `hba1cVisitSummaries/{patientId}_{fiscalYear}` พร้อม
   ตัวเลขที่คำนวณแล้ว, ข้อความ AI, ชื่อโมเดล, เวลาที่สร้าง — กดซ้ำ = เขียนทับเอกสารเดิม ไม่เก็บประวัติ
4. แพทย์/พยาบาล/admin ทุกคนกดได้ (ผู้ใช้ถือว่าเป็นการสรุปสถิติ ไม่ใช่การตัดสินใจทางคลินิก)
5. ไม่มีผลตรวจ HbA1c ในปีงบประมาณ → ยังบันทึก visitCount=0; ตรวจครั้งเดียว → visitCount=1 ไม่มีระยะห่าง
6. ข้อมูลเป็น mock เท่านั้น: อ่าน `labResults` กรองด้วย `dataSource == "ข้อมูลจำลอง"` และ
   `testType == "HbA1c"` (ชื่อ field ตาม db-spec LabResult)

### ข้อจำกัดที่บันทึกไว้อย่างตรงไปตรงมา

ไม่มี Blaze → ไม่มี Cloud Function → การอ่าน `labResults` และเขียน `hba1cVisitSummaries` เกิดขึ้นจาก
Client ภายใต้ Firestore rules แบบเปิดกว้างปัจจุบัน — **ขัดกับเส้นทางที่ออกแบบไว้** (ข้อมูลทางคลินิกต้อง
ผ่าน callable Cloud Functions พร้อม audit log แบบ fail-safe ตาม NFR-06 และ Security Rules
`labResults` ที่ตั้งใจไว้ต้อง `allow read, write: if false`) บันทึกเป็น temporary stand-in เหมือน
`clientAuthFlows.ts`/`accountApproval.ts` พร้อม target design (callable function + audit log) สำหรับ
ตอนอยู่ Blaze — เรื่องนี้ยังพลิกกลับหมายเหตุเดิมของ decision area 20 ที่ว่า "AI ไม่เคยถูกบันทึกผลลง
Firestore" ด้วย เพราะ FR-18 เป็นข้อยกเว้น (บันทึกผล AI ลง `hba1cVisitSummaries` จริง)

### การตัดสินใจสร้างเอกสารใหม่ vs แก้เอกสารเดิม

เลือก**เพิ่มต่อท้ายในเอกสารเดิม** ไม่สร้างไฟล์ spec ใหม่ เพราะเนื้อหาต่อยอดโดยตรงจาก FR-02 (แสดงผลตรวจ lab
รวม HbA1c) ในไฟล์เดียวกัน จึงเพิ่ม **FR-18** ต่อท้ายตาราง FR ใน
[[../01-requirements/01-spec/20260917-01-patient-ncd-history-lab-complication-risk|20260917-01]] และขยาย
**NFR-21** (ไม่สร้างรหัสใหม่ — ตามที่ผู้ใช้ยืนยันในแชทว่า "ต้องขยาย NFR-21") ใน
[[../01-requirements/01-spec/20260921-01-pdpa-data-protection-compliance|20260921-01]] แทนการสร้างไฟล์ใหม่
หรือย้ายเนื้อหาเดิมไป archived

### คำถามที่ถามผู้ใช้ผ่าน NEEDS_USER_INPUT และคำตอบที่ได้ (ยืนยันผ่าน AskUserQuestion ในเทรดหลัก)

1. **ระดับความสำคัญของ FR-18** → **กลาง** (เหตุผลผู้ใช้: เป็นฟีเจอร์เสริม ไม่ใช่ MVP หลัก สอดคล้องกับ
   FR-17)
2. **สิทธิ์กดปุ่ม/เขียนผลลงฐาน** → **แพทย์/พยาบาล/admin ทุกคน** (ผู้ใช้ให้เหตุผลว่าผลสรุปนี้เป็นการคำนวณ
   สถิติ ไม่ใช่การตัดสินใจทางคลินิก จึงไม่เข้าข่ายข้อจำกัดของ FR-16 ที่จำกัดเฉพาะแพทย์/พยาบาล — ระบุไว้
   ชัดเจนในสมมติฐาน FR-18 ข้อ 5 ว่าเป็นข้อยกเว้นที่แตกต่างจาก FR-16 โดยเจตนา; admin ยังคง read-only สำหรับ
   ข้อมูลทางคลินิกอื่นตาม FR-15 เหมือนเดิม)
3. **กรณีไม่มีผลตรวจ HbA1c ในปีงบประมาณที่เลือก** → ปุ่มยังกดได้ ระบบบันทึกผลสรุปว่าจำนวน visit = 0
   ("ไม่มีข้อมูล") ลงฐานเป็นหลักฐานว่าเคยตรวจสอบแล้ว (ไม่ปิด/ไม่ซ่อนปุ่ม)
4. **กรณีตรวจ HbA1c เพียงครั้งเดียวในปีงบประมาณ** → สรุปจำนวน visit = 1 โดยไม่มีค่าระยะห่าง และให้ AI ระบุ
   ว่ายังไม่มีข้อมูลเพียงพอสำหรับประเมินความสม่ำเสมอ

### รหัส FR/NFR ที่เพิ่ม/แก้ไข

- **FR-18 (ใหม่)** — เพิ่มในตาราง FR ของ
  [[../01-requirements/01-spec/20260917-01-patient-ncd-history-lab-complication-risk|20260917-01]] พร้อม
  หมายเหตุสมมติฐาน 12 ข้อ (นิยามปีงบประมาณ, ตำแหน่งปุ่ม, ระดับความสำคัญ, ขอบเขตคำนวณระบบ vs AI, สิทธิ์
  กดปุ่ม, กรณีไม่มีข้อมูล, กรณีตรวจครั้งเดียว, การเขียนทับผลลงฐาน, ข้อมูลที่ส่งให้ AI, ป้ายกำกับ/ความทนทาน
  ต่อความล้มเหลว, audit log, ชื่อเทคโนโลยี AI) และอัปเดตหัวข้อ "เอกสารที่เกี่ยวข้อง" ให้พาดพิง FR-18
- **NFR-21 (ขยาย)** — เพิ่มขอบเขตในหัวข้อ "ข้อมูลที่อยู่ในขอบเขตของเอกสารนี้", เพิ่มหมายเหตุขยาย
  2026-09-27 ในหัวข้อสมมติฐาน, แก้ข้อความในตาราง NFR-21 และหัวข้อ "เอกสารที่เกี่ยวข้อง" ของ
  [[../01-requirements/01-spec/20260921-01-pdpa-data-protection-compliance|20260921-01]] ให้ครอบคลุม
  ข้อมูลที่ส่งให้ AI จาก FR-18 (จำกัดเฉพาะจำนวนครั้ง/ระยะห่างวัน ห้ามส่ง HN/ชื่อ/วันที่ตรวจ/ค่า HbA1c)
