- **Q1 PasswordPolicy (NFR-17):** เลือก **Hybrid** — regex ในโค้ด Cloud Function `signUpUser`
  (Operation 8) + เปิด Google Cloud Identity Platform password policy เป็น backstop ฝั่งเซิร์ฟเวอร์

  อัปเกรดเป็น Identity Platform บางส่วน ต้องติดตาม billing/quota แยกจาก Firebase Auth เปล่า
- **Q2 EnumPrevent (NFR-18):** เลือก **Firebase "Email Enumeration Protection" เท่านั้น** (ไม่เพิ่ม
  fixed minimum delay/normalize เวลาตอบสนอง) — บันทึกความเสี่ยง timing side-channel ที่ยังไม่ปิดไว้
  อย่างเด่นชัดในหัวข้อ "ความเสี่ยงที่ต้องพิจารณาเพิ่มเติม" ผู้ใช้รับทราบและยืนยันให้ดำเนินการต่อแล้ว
- **Q3 EmailTemplate (FR-09/FR-10):** เลือก template เริ่มต้นของ Firebase Authentication + ปรับ
  ภาษาไทย/ชื่อผู้ส่งผ่าน Console เท่านั้น (ไม่ custom domain) — ทบทวนเมื่อเข้า production จริง

  ระบุว่าเก็บบทบาทใน custom claims) ให้ตรงกับการตัดสินใจนี้
- **Q7 EmailVerifiedCheck (FR-09):** เลือกตรวจทั้ง Cloud Functions (Op.1-6, `decodedToken.email_verified`)
  และ Firestore Security Rules (Op.0, `request.auth.token.email_verified`) — ปิดช่องว่างที่

### คำถามที่ถามผู้ใช้ (NEEDS_USER_INPUT) และคำตอบที่ได้รับ

**รอบที่ 1 (6 ข้อ, เลือกตัวเลือกแนะนำทั้งหมด):**
- **Q1 แนวทางไฟล์:** สร้าง spec ใหม่แยก (`20260924-01-admin-role-account-management.md`) ลิงก์กลับ
  เอกสาร auth เดิม และแก้เฉพาะย่อหน้า assumption/out-of-scope ในเอกสารเดิมว่าถูกแทนที่บางส่วน
- **Q2 นิยามบทบาท:** "2 บทบาท" = 2 กลุ่มเชิงหน้าที่ (ผู้ใช้งานทางคลินิก = แพทย์+พยาบาล / admin) แต่คง
  3 role ย่อยในระบบ (แพทย์/พยาบาล/admin)
- **Q3 ขอบเขตแก้ไข:** ครบวงจร — อนุมัติบัญชีใหม่ (กำหนด role+isActive) + เปลี่ยน role + ระงับ/เปิดใช้งาน
  บัญชี + จัดการ PatientAssignment
- **Q4 admin ดูประวัติ:** ทุกผู้ป่วยโดยไม่ต้องมี PatientAssignment แต่ต้องบันทึก audit log แบบ
  fail-safe ทุกครั้ง
- **Q5 ช่องทาง:** สร้างหน้าจอจัดการผู้ใช้ในระบบสำหรับ admin (ไม่ใช้ Firebase Console อีกต่อไปสำหรับงาน
  routine เหล่านี้)
