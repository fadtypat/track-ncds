- **Q1 PasswordPolicy (NFR-17):** เลือก **Hybrid** — regex ในโค้ด Cloud Function `signUpUser`
  (Operation 8) + เปิด Google Cloud Identity Platform password policy เป็น backstop ฝั่งเซิร์ฟเวอร์

  อัปเกรดเป็น Identity Platform บางส่วน ต้องติดตาม billing/quota แยกจาก Firebase Auth เปล่า
- **Q2 EnumPrevent (NFR-18):** เลือก **Firebase "Email Enumeration Protection" เท่านั้น** (ไม่เพิ่ม
  fixed minimum delay/normalize เวลาตอบสนอง) — บันทึกความเสี่ยง timing side-channel ที่ยังไม่ปิดไว้
  อย่างเด่นชัดในหัวข้อ "ความเสี่ยงที่ต้องพิจารณาเพิ่มเติม" ผู้ใช้รับทราบและยืนยันให้ดำเนินการต่อแล้ว
- **Q3 EmailTemplate (FR-09/FR-10):** เลือก template เริ่มต้นของ Firebase Authentication + ปรับ
  ภาษาไทย/ชื่อผู้ส่งผ่าน Console เท่านั้น (ไม่ custom domain) — ทบทวนเมื่อเข้า production จริง

  ระบุว่าเก็บบทบาทใน custom claims) ให้ตรงกับการตัดสินใจนี้
- **Q7 EmailVerifiedCheck (FR-09):** เลือกตรวจทั้ง Cloud Functions (Op.1-6, `decodedToken.email_verified`)
  และ Firestore Security Rules (Op.0, `request.auth.token.email_verified`) — ปิดช่องว่างที่

### คำถามที่ถามผู้ใช้ (NEEDS_USER_INPUT) และคำตอบที่ได้รับ

**รอบที่ 1 (6 ข้อ, เลือกตัวเลือกแนะนำทั้งหมด):**
- **Q1 แนวทางไฟล์:** สร้าง spec ใหม่แยก (`20260924-01-admin-role-account-management.md`) ลิงก์กลับ
  เอกสาร auth เดิม และแก้เฉพาะย่อหน้า assumption/out-of-scope ในเอกสารเดิมว่าถูกแทนที่บางส่วน
- **Q2 นิยามบทบาท:** "2 บทบาท" = 2 กลุ่มเชิงหน้าที่ (ผู้ใช้งานทางคลินิก = แพทย์+พยาบาล / admin) แต่คง
  3 role ย่อยในระบบ (แพทย์/พยาบาล/admin)
- **Q3 ขอบเขตแก้ไข:** ครบวงจร — อนุมัติบัญชีใหม่ (กำหนด role+isActive) + เปลี่ยน role + ระงับ/เปิดใช้งาน

- **Q4 admin ดูประวัติ:** ทุกผู้ป่วยโดยไม่ต้องมี PatientAssignment แต่ต้องบันทึก audit log แบบ
  fail-safe ทุกครั้ง
- **Q5 ช่องทาง:** สร้างหน้าจอจัดการผู้ใช้ในระบบสำหรับ admin (ไม่ใช้ Firebase Console อีกต่อไปสำหรับงาน
  routine เหล่านี้)
- **Q6 admin คนแรก:** สร้าง/กำหนดผ่าน Firebase Console/Firestore โดยตรง (bootstrap เท่านั้น)

**รอบที่ 2 (2 ข้อ ต่อ requirement ดิบเพิ่มเติมเรื่อง "แพทย์/พยาบาล...แก้ไข การวิเคราะห์โรคได้" —

- **Q1 ขอบเขตแก้ไข:** "แก้ไข" = แก้ไข/บันทึกผลการประเมินความเสี่ยงโรคแทรกซ้อน (FR-03/FR-04) เท่านั้น —
  แพทย์/พยาบาลยืนยัน/override flag อัตโนมัติ **ไม่แก้ไขข้อมูลต้นทางจาก HOSxP** (ประวัติวินิจฉัย/lab
  ยังคง read-only ตาม NFR-01 เหมือนเดิม)
- **Q2 การวิเคราะห์โรค:** หมายถึงการใช้งาน FR-03/FR-04 ที่มีอยู่แล้ว ไม่ใช่ฟีเจอร์วิเคราะห์โรคใหม่ —

**หมายเหตุทางเทคนิคที่ผู้ใช้แจ้งเพิ่มระหว่างทาง:** ระบบไม่ใช้ Firebase Custom Claims เก็บบทบาทแล้ว —

## build-prototype (prototype-writer): แก้บั๊ก 2 จุดใน admin-user-directory.html และ admin-patient-detail-readonly.html

**ผู้ดำเนินการ:** prototype-writer agent (เรียกผ่าน orchestrator สกิล `build-prototype`)

**ขอบเขตงาน:** แก้ไขเฉพาะ 3 ไฟล์ตามที่ผู้ใช้ยืนยัน scope ผ่าน AskUserQuestion ในเทรดหลัก:
`admin-user-directory.html`, `admin-patient-detail-readonly.html`, `prototype.md` — ทั้งหมดอยู่ใน
`docs/02-design/01-prototypes/20260918-01-v1/` (เวอร์ชันเดิม แก้ในที่เดิม) ไม่แตะไฟล์อื่นใด ไม่ใช้สี/
สไตล์ใหม่นอก DESIGN.md

**บั๊กที่ 1 — `admin-user-directory.html` (อ้างอิง api-spec Operation 12/13):**
- เพิ่มแถวของ Admin ที่เข้าสู่ระบบอยู่ (กานดา ตรวจตรา, `role=admin`, `data-self="true"`) ไว้บนสุดของ
  ตาราง — select เปลี่ยน role และปุ่มเปลี่ยน role/ระงับการใช้งานของแถวนี้ใส่ `disabled` ทั้งหมด พร้อม
  ข้อความกำกับ "ไม่สามารถแก้ไขสิทธิ์ของตนเองได้ (Op.12/Op.13)" ต่อท้าย (ข้อความกำกับคู่กับสถานะเสมอ ไม่ใช้
  สีเป็นสัญญาณเดียวตาม NFR-13) และแก้ JS ให้ข้ามการผูก event ให้แถวนี้ด้วยเงื่อนไข `data-self==="true"`
- เพิ่มตัวเลือก `admin` ในทุก `<select class="role-select">` ของผู้ใช้อื่น (4 แถวเดิม u1–u4) และเพิ่มค่า
  `admin` ใน object `roleLabel`/`roleChipClass` ของ JS (ใช้ `.chip.chip-neutral` ซ้ำกับที่ใช้แสดงบทบาท
  Admin ในหน้าจอ Admin อื่นอยู่แล้ว — ไม่มี class/สีใหม่)

**บั๊กที่ 2 — `admin-patient-detail-readonly.html` (root cause: CSS cascade):**
- พบว่า `#access-check` (`class="callout tip"`) และ `#denied-panel` (`class="denied-shell"`) เดิมใส่
  attribute `hidden` ไว้บน element เดียวกับ class ที่กำหนด `display:flex` ตรงๆ ใน `style.css` — ตามกฎ
  cascade ของ CSS, author rule (class ใน stylesheet ของเว็บไซต์) ชนะ user-agent rule
  `[hidden]{display:none}` เสมอไม่ว่าค่า specificity จะเท่ากัน ทำให้ `element.hidden = true` ทาง JS ไม่
  ซ่อน element จริง เป็นสาเหตุที่กล่อง "บันทึก audit log สำเร็จ" ค้างแสดงคู่กับหน้าปฏิเสธหลังกด "จำลอง:
  บันทึก audit log ไม่สำเร็จ"
- แก้โดยห่อเนื้อหาเดิมของทั้งสอง block ด้วย wrapper `<div>` เปล่า (ไม่มี class ที่กำหนด display ใดๆ)
  แล้วย้าย `id="access-check"`/`id="denied-panel"` และ `hidden` ไปไว้ที่ wrapper แทน ส่วน class เดิม
  (`.callout tip`, `.denied-shell`/`.denied-card`) ยังอยู่ที่ inner `<div>` เหมือนเดิมทุกประการ ไม่มีการ
  แก้ `style.css` หรือเพิ่มสี/สไตล์ใหม่ใดๆ — ไม่แก้ `<script>` (ตัว JS เดิม toggle `hidden` ที่ id เดิม
  ทำงานถูกต้องอยู่แล้ว ปัญหาอยู่ที่ HTML/CSS structure เท่านั้น) ปุ่ม "ลองบันทึก audit log อีกครั้ง" กลับ
  สถานะเดิมได้ถูกต้องด้วยเหตุผลเดียวกัน

**`prototype.md`:** เพิ่มบรรทัด "อัปเดตล่าสุด (รอบที่ 3 — แก้บั๊ก)" ที่ต้นเอกสาร และเพิ่มหมายเหตุ
simplification 2 ข้อ (รายละเอียดบั๊กที่ 1/2 ข้างต้น) ในส่วน "หมายเหตุการตีความ/simplification"

**คำถามที่ถามผู้ใช้ (NEEDS_USER_INPUT):** ไม่มี — ผู้ใช้ยืนยัน scope ครบถ้วนมาก่อนแล้วผ่าน
AskUserQuestion ในเทรดหลัก ไม่มีจุดคลุมเครือที่ต้องถามเพิ่มระหว่างแก้

**ตรวจสอบตัวเอง:** อ่านทั้ง 2 ไฟล์ HTML กลับมาตรวจแล้วทั้งไฟล์ — แท็กเปิด/ปิดครบ, `disabled`/`data-self`
attribute ถูกต้อง, `<script>` อ้าง id ที่มีอยู่จริงและ logic การข้าม event ของแถว self ถูกต้อง, โครงสร้าง
wrapper div ใหม่ใน `admin-patient-detail-readonly.html` ไม่กระทบ layout เดิมของ `.callout`/`.denied-shell`
ภายใน (ยังอยู่ใน DOM tree เดียวกัน เพียงมี wrapper เพิ่มชั้นเดียว) — **ยังไม่ได้ตรวจด้วยเบราว์เซอร์จริง**
แนะนำให้เปิดไฟล์จริงทดสอบปุ่ม "จำลอง: บันทึก audit log ไม่สำเร็จ" → "ลองบันทึก audit log อีกครั้ง" และ
ตรวจว่าแถว Admin ของตนเองใน `admin-user-directory.html` กดปุ่ม/select ไม่ได้จริง เป็น follow-up ในเทรดหลัก
