# Build Tech Stack

Skill นี้เป็น workflow มาตรฐานสำหรับสร้าง/ปรับปรุง `docs/02-design/02-technical/
technology-stack.md` โดยถามผู้ใช้งานอย่างละเอียดเกี่ยวกับบริบททีม/องค์กร/ข้อจำกัด เพื่อแนะนำและ
ตัดสินใจเทคโนโลยี stack ที่เหมาะสมกับระบบตามเอกสารเชิงเทคนิคที่ออกแบบไว้แล้ว (`architecture.md`/
`api-spec.md`/`db-spec.md`/`nfr-review.md`) ตามกฎใน `CLAUDE.md` — **ต่างจาก skill สาย `sync-*`
อื่นๆ ตรงที่นี่คือกระบวนการตัดสินใจ (decision process) ไม่ใช่การ sync เอกสารชั้นล่างให้ตรงกับชั้นบน
แบบ 1:1**

**ข้อจำกัดสำคัญของสภาพแวดล้อม:** `AskUserQuestion` ใช้งานไม่ได้จากภายใน subagent (error ทันทีถ้า
subagent พยายามเรียก) ดังนั้น subagent `tech-stack-writer` **ไม่มี** เครื่องมือนี้และจะไม่เรียกมันเลย
— แทนที่ subagent จะหยุดทำงานแล้วส่งคำถามกลับมาในรูปแบบหัวข้อ `## NEEDS_USER_INPUT`
(คำถาม + ตัวเลือก + ข้อดีข้อเสีย) **คุณ (ผู้ดำเนินการ skill นี้ ซึ่งรันอยู่ในเทรดหลัก) คือคนที่ต้อง
ใช้ `AskUserQuestion` ถามผู้ใช้จริงแทน subagent เสมอ** แล้วส่งคำตอบกลับไปให้ subagent ตัวเดิมทำงาน
ต่อผ่าน `SendMessage` (ไม่ใช่เรียก Agent ใหม่ — ต้องเป็น agent ตัวเดิมเพื่อรักษาบริบทที่อ่านไปแล้ว)

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: รูปแบบ `YYYYMMDD` เพื่อส่งต่อให้ subagent — subagent ไม่มีเครื่องมือ Bash
   จึงหาวันที่เองไม่ได้ ต้องส่งมาให้ใน prompt เสมอ

2. **เรียก subagent `tech-stack-writer` ครั้งแรก**: ผ่าน Agent tool
   (`subagent_type: tech-stack-writer`, `run_in_background: false`) โดย prompt ที่ส่งต้องมี:
   - วันที่ปัจจุบัน (YYYYMMDD)
   - บริบทว่า subagent นี้ไม่มีเครื่องมือ `AskUserQuestion` — เมื่อต้องถามผู้ใช้ ให้ออกหัวข้อ
     `## NEEDS_USER_INPUT` ตามรูปแบบที่ระบุไว้ในระบบของ agent แล้วหยุดทำงานทันที
   - **ถ้าผู้ใช้ให้บริบทบางส่วนมาล่วงหน้าแล้วในคำขอ** (เช่น "อยากใช้ cloud", "ทีมถนัด Python")
     ให้สรุปส่งต่อแบบ verbatim เพื่อไม่ให้ subagent ถามซ้ำในหัวข้อนั้น
   - เก็บ `agentId` ที่ได้กลับมาไว้ใช้ต่อในข้อ 3

3. **วนรอบถาม-ตอบจนกว่างานจะเสร็จ (สูงสุด 8 รอบ เพื่อป้องกัน infinite loop)**: อ่านผลลัพธ์ที่ได้จาก
   subagent ทุกครั้ง —
   - **ถ้าพบหัวข้อ `## NEEDS_USER_INPUT`**: แปลงแต่ละคำถาม (Q1, Q2, ...) เป็นคำถามจริงผ่าน
     `AskUserQuestion` **โดยใช้ตัวเลือก/คำอธิบายข้อดี-ข้อเสียตามที่ subagent เสนอมาเป๊ะๆ ไม่ตัดทอน/
     ไม่แต่งเพิ่มเอง** (ถ้ามีมากกว่า 4 คำถามในรอบเดียว แบ่งเรียก `AskUserQuestion` หลายครั้ง) รอ
     คำตอบจากผู้ใช้จริงเสมอ ห้าม mock/เดาคำตอบแทนผู้ใช้ไม่ว่ากรณีใด จากนั้นเรียก **`SendMessage`
     ไปยัง agent ตัวเดิม** (`to: <agentId จากข้อ 2>`) พร้อมสรุปคำตอบของผู้ใช้ต่อแต่ละคำถามแบบชัดเจน
     (ระบุว่า Q ไหนตอบว่าอะไร) แล้ววนกลับมาอ่านผลลัพธ์รอบถัดไป
   - **ถ้าไม่พบหัวข้อนี้**: ถือว่า subagent ทำงานเสร็จสมบูรณ์ (เขียนไฟล์แล้ว หรือรายงานปัญหา/gate
     ที่ไม่ใช่คำถามผู้ใช้ เช่น "architecture.md ว่างเปล่า") ออกจากลูป ไปข้อ 4
   - **ถ้าครบ 8 รอบแล้วยังไม่เสร็จ**: หยุด แจ้งผู้ใช้ตรงๆ ว่าการสนทนายาวเกินคาด ให้ตรวจสอบสถานะและ
     สั่งงานต่อเองหรือเริ่มใหม่

4. **ตรวจสอบผลลัพธ์ก่อนรายงาน**: สุ่มอ่าน `technology-stack.md` จริงอย่างน้อย 1-2 จุด ตรวจว่า:
   - มีตาราง Component ↔ เทคโนโลยีที่เลือก ↔ เหตุผล (อ้างอิง NFR/บริบท) ครบตามที่รายงาน
   - ทุกการตัดสินใจมีเหตุผลอ้างอิงจากบริบท intake หรือ NFR จริง ไม่ใช่ลอยๆ
   - ไม่มี component/operation/entity ใหม่ที่ไม่มีอยู่จริงใน `architecture.md`/`api-spec.md`/
     `db-spec.md` ถูกอ้างถึง
   ห้ามเชื่อรายงานของ subagent 100% โดยไม่ตรวจเอง

5. **สรุปให้ผู้ใช้ทราบ**:
   - บริบทที่รวบรวมได้จาก intake โดยย่อ
   - การตัดสินใจ stack แต่ละ component/decision area พร้อมเหตุผลสั้น
   - จุดที่ถามผู้ใช้ระหว่างทาง (ทั้ง intake และการตัดสินใจ) และจำนวนรอบที่ใช้
   - **ถามผู้ใช้ว่าต้องการให้สั่งรัน `sync-architecture`/`sync-api-db`/`sync-detailed-design`
     ต่อทันทีเลยหรือไม่** เพื่อให้เอกสารชั้นอื่นเริ่มอ้างอิงชื่อ stack จริง (ไม่ auto-chain เอง
     เพราะกระทบเอกสารหลายไฟล์พร้อมกัน ให้ผู้ใช้เป็นคนตัดสินใจจังหวะเอง)

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้วเขียน `technology-stack.md` เองตรงๆ ในเทรดหลัก — `tech-stack-writer`
  คือแหล่งความจริงเดียวของกฎการรวบรวมบริบทและตัดสินใจ stack แม้การถามจริงจะเกิดในเทรดหลักก็ตาม
- **ห้ามข้ามขั้นตอนถาม `AskUserQuestion` จริงแทนคำถามใน `NEEDS_USER_INPUT`** และห้าม "ช่วยตอบ" หรือ
  เดาคำตอบแทนผู้ใช้เพื่อให้ลูปจบเร็วขึ้นเด็ดขาด ไม่ว่าคำถามจะดูตอบง่ายแค่ไหนก็ตาม
- **ต้องใช้ `SendMessage` กลับไปยัง agent ตัวเดิม (agentId เดิม) เสมอ** ห้ามเรียก Agent ใหม่แทน
  เพราะจะเสียบริบทเอกสารที่อ่านไปแล้วทั้งหมด ทำให้ subagent ต้องอ่านไฟล์ใหม่ทั้งหมดอีกรอบโดยไม่จำเป็น
- Subagent นี้ตั้งใจไม่มีเครื่องมือ Bash/AskUserQuestion และห้ามแตะไฟล์ใดๆ นอกจาก
  `technology-stack.md` กับไฟล์ log ของวันนั้น หากผลลัพธ์พูดถึงการแก้ไขไฟล์อื่น (โดยเฉพาะ
  `architecture.md`, `api-spec.md`, `db-spec.md`, ไฟล์ใน `detailed-design/`) ให้หยุดและแจ้งผู้ใช้ทันที
- ถ้า subagent รายงานว่า `architecture.md` ว่างเปล่า ให้แจ้งผู้ใช้ให้รัน `sync-architecture` ก่อน
  อย่าฝืนทำต่อในสถานะที่ไม่มี component ให้ map เทคโนโลยี
- ถ้า `technology-stack.md` มีเนื้อหาอยู่แล้ว subagent จะออก `NEEDS_USER_INPUT` ถามผู้ใช้ก่อนเสมอว่า
  จะ rebuild ทั้งไฟล์/แก้เฉพาะส่วน/เพิ่มเติมเฉพาะ component ใหม่ — ปฏิบัติตามข้อ 3 ตามปกติ ห้ามเขียน
  ทับเงียบๆ
