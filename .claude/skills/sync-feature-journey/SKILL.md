# Sync Feature & Journey

Skill นี้เป็น workflow มาตรฐานสำหรับตรวจสอบว่า `docs/02-design/feature-list.md` (รวมถึง
ตารางสรุปฟีเจอร์และระดับความสำคัญแบบ MoSCoW) และ `docs/02-design/user-journey.md`
สอดคล้อง ("up to date") กับ `docs/01-requirements/backlog.md` หรือไม่ ถ้าไม่สอดคล้อง ให้
สร้าง/ปรับปรุงทั้งสองไฟล์ พร้อมบันทึก log ตามกฎใน `CLAUDE.md`

**ข้อจำกัดสำคัญของสภาพแวดล้อม:** `AskUserQuestion` ใช้งานไม่ได้จากภายใน subagent ดังนั้น subagent
`feature-journey-writer` **ไม่มี** เครื่องมือนี้ — เมื่อต้องถามผู้ใช้ มันจะหยุดแล้วส่งคำถามกลับมาใน
หัวข้อ `## NEEDS_USER_INPUT` **คุณ (ผู้ดำเนินการ skill นี้ในเทรดหลัก) คือคนที่ต้องใช้
`AskUserQuestion` ถามผู้ใช้จริงแทน** แล้วส่งคำตอบกลับไปยัง subagent ตัวเดิมผ่าน `SendMessage`
เพื่อให้ทำงานต่อ

## เมื่อถูกเรียกใช้

1. **หาวันที่ปัจจุบัน**: ใช้ค่าวันที่ปัจจุบันที่มีอยู่ในบริบทของคุณ (รูปแบบ `YYYYMMDD`)
   เพื่อส่งต่อให้ subagent ใช้กับไฟล์ log ของวันนี้ — subagent ไม่มีเครื่องมือ Bash
   จึงหาวันที่เองไม่ได้ ต้องส่งมาให้ใน prompt เสมอ

2. **เรียก subagent `feature-journey-writer` ครั้งแรก**: ผ่าน Agent tool
   (`subagent_type: feature-journey-writer`, `run_in_background: false`) โดย prompt ที่ส่งต้องมี:
   - วันที่ปัจจุบัน (YYYYMMDD) สำหรับใช้กับไฟล์ log
   - บริบทว่า subagent นี้ไม่มีเครื่องมือ `AskUserQuestion` — เมื่อต้องถามผู้ใช้ ให้ออกหัวข้อ
     `## NEEDS_USER_INPUT` ตามรูปแบบที่ระบุไว้ในระบบของ agent แล้วหยุดทำงานทันที
   - เก็บ `agentId` ที่ได้กลับมาไว้ใช้ต่อในข้อ 3

3. **วนรอบถาม-ตอบจนกว่างานจะเสร็จ (สูงสุด 6 รอบ ป้องกัน infinite loop)**: อ่านผลลัพธ์จาก subagent
   ทุกครั้ง —
   - **ถ้าพบ `## NEEDS_USER_INPUT`**: แปลงแต่ละคำถามเป็นคำถามจริงผ่าน `AskUserQuestion` โดยใช้
     ตัวเลือก/ข้อดี-ข้อเสียตามที่ subagent เสนอมาเป๊ะๆ รอคำตอบผู้ใช้จริงเสมอ ห้าม mock คำตอบ จากนั้น
     เรียก `SendMessage` ไปยัง agent ตัวเดิม (`to: <agentId>`) พร้อมสรุปคำตอบต่อแต่ละคำถาม แล้ววน
     อ่านผลลัพธ์รอบถัดไป
   - **ถ้าไม่พบ**: ออกจากลูป ไปข้อ 4
   - **ถ้าครบ 6 รอบยังไม่เสร็จ**: หยุด แจ้งผู้ใช้ตรงๆ ว่าการสนทนายาวเกินคาด ให้ตรวจสอบสถานะเอง

4. **ตรวจจับสัญญาณ "ต้องการ requirement ใหม่"**: อ่านรายงานสุดท้ายที่ได้กลับมาทั้งหมด
   - **ถ้าไม่มีหัวข้อ `## NEEDS_NEW_REQUIREMENT` ในรายงาน**: ข้ามไปข้อ 6 (ตรวจสอบผลลัพธ์) ตามปกติ
   - **ถ้ามีหัวข้อนี้**: ทำตามข้อ 5 ก่อน (auto-chain ไป `requirement-writer`) แล้วค่อยไปข้อ 6

5. **Auto-chain ไป `requirement-writer` (เฉพาะเมื่อมีสัญญาณในข้อ 4)**:
   a. แจ้งผู้ใช้สั้นๆ ก่อนว่าเจอความต้องการใหม่ระหว่างทำ feature-list/user-journey กำลังส่งต่อให้
      `requirement-writer` เขียนเป็น FR/NFR ให้อัตโนมัติ (ไม่ต้องถามผู้ใช้ก่อนว่าจะส่งต่อหรือไม่
      — เป็นพฤติกรรมมาตรฐานของ skill นี้ที่ผู้ใช้ตกลงไว้แล้ว)
   b. เรียก subagent `requirement-writer` ผ่าน Agent tool (`run_in_background: false`) โดย prompt
      ต้องมี: เนื้อหาทั้งหมดใต้หัวข้อ `## NEEDS_NEW_REQUIREMENT` แบบ verbatim (ไม่สรุปย่อเอง),
      วันที่ปัจจุบัน (YYYYMMDD), บริบทว่าเนื้อหานี้ค้นพบระหว่างทำ feature-list/user-journey
      ไม่ใช่ผู้ใช้พิมพ์มาตรงๆ, และบริบทว่านี่คือ session สนทนากับผู้ใช้จริง
   c. รอผลลัพธ์ แล้วสุ่มตรวจสอบเองอย่างน้อย 1 จุด (เปิดอ่าน `backlog.md` ว่ามีรหัส FR/NFR ใหม่
      ปรากฏจริงตามที่รายงาน) ก่อนไปขั้นตอนถัดไป
   d. เรียก subagent `feature-journey-writer` **อีกรอบ** (prompt เดิมจากข้อ 2 บวกข้อความแจ้งว่า
      `backlog.md` เพิ่งมีรหัสใหม่เพิ่มเข้ามาแล้ว ให้ทำงานที่ค้างไว้ต่อให้ครบ) เพื่อให้ feature-list/
      user-journey ครอบคลุมรหัสใหม่ที่เพิ่งเกิดด้วย
   e. **ป้องกัน infinite loop**: ทำข้อ 4-5 ซ้ำได้อีกไม่เกิน 1 รอบเท่านั้น (รวมแล้วเรียก
      `feature-journey-writer` ได้สูงสุด 3 ครั้งต่อ 1 คำขอผู้ใช้) ถ้ารอบที่สองยังพบ
      `## NEEDS_NEW_REQUIREMENT` อีก ให้หยุด auto-chain แล้วรายงานผู้ใช้ตรงๆ ว่ายังมีความต้องการ
      ใหม่ค้างอยู่ ให้ผู้ใช้ตรวจสอบเองก่อนสั่งต่อ อย่าวนไม่รู้จบ

6. **ตรวจสอบผลลัพธ์ก่อนรายงาน**: หลัง subagent รายงานว่าแก้ไขอะไรไปบ้าง (รอบสุดท้าย) ให้สุ่ม
   ตรวจสอบเองอย่างน้อย 1-2 จุด (เปิดอ่าน feature-list.md และ/หรือ user-journey.md จริงว่ามีการแก้ไข
   ตรงตามที่รายงานหรือไม่ และตรวจว่าทุก journey มี mermaid block กำกับ พร้อม node ตรงกับรายการ
   ขั้นตอนแบบข้อความจริง) รวมถึงตรวจว่า feature-list.md มีตารางสรุปฟีเจอร์ต้นไฟล์ครบทุกฟีเจอร์
   และคอลัมน์ MoSCoW ของแต่ละแถวตรงกับบรรทัด "ระดับความสำคัญ (MoSCoW): ..." ใน heading
   รายละเอียดของฟีเจอร์เดียวกันจริง ก่อนสรุปให้ผู้ใช้ฟัง ห้ามเชื่อรายงานของ subagent 100% โดยไม่
   ตรวจเอง

7. **สรุปให้ผู้ใช้ทราบ**: หลัง subagent ทำงานเสร็จและตรวจสอบแล้ว ให้สรุปสั้นๆ ว่า
   - feature-list.md และ user-journey.md up to date อยู่แล้วหรือไม่ก่อนตรวจ (รวมถึงตารางสรุป
     MoSCoW ครบ/ตรงอยู่แล้วหรือไม่)
   - ไฟล์ใดถูกสร้าง/แก้ไขบ้าง (path เต็ม) และระดับ MoSCoW ที่กำหนด/เปลี่ยนของฟีเจอร์ใดบ้าง (ถ้ามี)
   - **ความต้องการใหม่ที่เจอระหว่างทำงานและถูก auto-chain ไป `requirement-writer` ให้เอง (ถ้ามี)**
     พร้อมรหัส FR/NFR ใหม่ที่ได้และเอกสาร spec ที่ถูกสร้าง/แก้ไข
   - จุดที่ถาม/รอผู้ใช้ตัดสินใจ (ถ้ามี)
   - ปัญหาเชิงโครงสร้างอื่นที่ subagent รายงาน

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้วเขียน feature-list.md/user-journey.md เองตรงๆ ในเทรดหลัก
  — subagent คือแหล่งความจริงเดียวของกฎการจัดกลุ่มฟีเจอร์/journey จาก backlog
- **ห้ามข้ามขั้นตอนถาม `AskUserQuestion` จริงแทนคำถามใน `NEEDS_USER_INPUT`** และห้ามเดา/ช่วยตอบแทน
  ผู้ใช้เพื่อให้ลูปจบเร็วขึ้น **ต้องใช้ `SendMessage` กลับไปยัง agent ตัวเดิมเสมอ** ห้ามเรียก Agent
  ใหม่แทน ยกเว้นกรณี auto-chain รอบใหม่ตามข้อ 5d ที่ต้องเริ่มใหม่จริงๆ เพราะ backlog เปลี่ยนไปแล้ว
- Subagent `feature-journey-writer` ตั้งใจไม่มีเครื่องมือ Bash/AskUserQuestion และห้ามแตะไฟล์ใดๆ นอกจาก
  `feature-list.md`, `user-journey.md`, และไฟล์ log ของวันนั้น หากผลลัพธ์พูดถึงการแก้ไขไฟล์อื่น
  นอกเหนือจากนี้ (โดยเฉพาะ `backlog.md` หรือไฟล์ใน `01-spec/`) ให้หยุดและแจ้งผู้ใช้ทันที
  อย่าดำเนินการต่อ
- การ auto-chain ไป `requirement-writer` (ข้อ 5) เป็นข้อยกเว้นเดียวที่ skill นี้เรียก subagent
  ตัวอื่นนอกเหนือจาก `feature-journey-writer` — ต้องเรียกก็ต่อเมื่อพบหัวข้อ
  `## NEEDS_NEW_REQUIREMENT` ตรงตัวในรายงานเท่านั้น ห้ามเดาเองจากเนื้อหาอื่นว่าเข้าเงื่อนไขหรือไม่
- ห้ามวน auto-chain เกิน 1 รอบเด็ดขาด (ดูข้อ 5e) เพื่อป้องกัน infinite loop ถ้ายังไม่จบใน 2 รอบ
  ให้หยุดและคืนการตัดสินใจให้ผู้ใช้
- ถ้า subagent รายงานว่าหาโฟลเดอร์ `docs/02-design/` หรือโครงสร้างที่คาดไว้ไม่เจอ อย่าให้
  subagent ลองสร้าง/ย้าย/เดาชื่อโฟลเดอร์เอง ให้ผู้ใช้เข้ามาตรวจสอบโครงสร้างจริงก่อน
