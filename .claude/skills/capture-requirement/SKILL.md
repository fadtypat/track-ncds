# Capture Requirement

Skill นี้เป็น workflow มาตรฐานสำหรับแปลงความต้องการดิบที่ผู้ใช้เล่ามา (ข้อความอิสระ,
บันทึกการประชุม, รายการ feature ที่อยากได้ ฯลฯ) ให้กลายเป็นเอกสาร Requirement
Specification ที่เป็นทางการของโปรเจกต์นี้ พร้อมอัปเดต backlog และ log ให้ครบ ตามกฎใน `CLAUDE.md`

**ข้อจำกัดสำคัญของสภาพแวดล้อม:** `AskUserQuestion` ใช้งานไม่ได้จากภายใน subagent ดังนั้น subagent
`requirement-writer` **ไม่มี** เครื่องมือนี้ (และไม่มี Bash) — เมื่อต้องถามผู้ใช้ มันจะหยุดแล้วส่ง
คำถามกลับมาในหัวข้อ `## NEEDS_USER_INPUT` **คุณ (ผู้ดำเนินการ skill นี้ในเทรดหลัก) คือคนที่ต้องใช้
`AskUserQuestion` ถามผู้ใช้จริงแทน** แล้วส่งคำตอบกลับไปยัง subagent ตัวเดิมผ่าน `SendMessage`
เพื่อให้ทำงานต่อ

## เมื่อถูกเรียกใช้

1. **รับ input**: ถ้าผู้ใช้ยังไม่ได้แนบความต้องการดิบมาพร้อม args ให้ถามผู้ใช้ตรงๆ ว่า
   ต้องการบันทึกความต้องการอะไร (รับเป็นข้อความอิสระได้เลย ไม่ต้องมีรูปแบบตายตัว)

2. **หาวันที่ปัจจุบัน**: รูปแบบ `YYYYMMDD` เพื่อส่งต่อให้ subagent — subagent ไม่มีเครื่องมือ Bash
   จึงหาวันที่เองไม่ได้ ต้องส่งมาให้ใน prompt เสมอ

3. **เรียก subagent `requirement-writer` ครั้งแรก**: ผ่าน Agent tool
   (`subagent_type: requirement-writer`, `run_in_background: false`) โดย prompt ที่ส่งต้องมี:
   - ข้อความ requirement ดิบทั้งหมดที่ผู้ใช้ให้มา (verbatim อย่าสรุปย่อเอง เดี๋ยว agent จะตีความเอง)
   - วันที่ปัจจุบัน (YYYYMMDD)
   - เอกสารหรือหัวข้อใดๆ ที่ผู้ใช้อ้างถึงในบทสนทนา (ถ้ามี) พร้อม path ถ้ารู้
   - บริบทว่า subagent นี้ไม่มีเครื่องมือ `AskUserQuestion` — เมื่อต้องถามผู้ใช้ ให้ออกหัวข้อ
     `## NEEDS_USER_INPUT` ตามรูปแบบที่ระบุไว้ในระบบของ agent แล้วหยุดทำงานทันที
   - เก็บ `agentId` ที่ได้กลับมาไว้ใช้ต่อในข้อ 4

4. **วนรอบถาม-ตอบจนกว่างานจะเสร็จ (สูงสุด 6 รอบ ป้องกัน infinite loop)**: อ่านผลลัพธ์จาก subagent
   ทุกครั้ง —
   - **ถ้าพบ `## NEEDS_USER_INPUT`**: แปลงแต่ละคำถามเป็นคำถามจริงผ่าน `AskUserQuestion` โดยใช้
     ตัวเลือก/ข้อดี-ข้อเสียตามที่ subagent เสนอมาเป๊ะๆ (รวมถึงตัวเลือกที่แนะนำ) ไม่ตัดทอน/แต่งเพิ่มเอง
     รอคำตอบผู้ใช้จริงเสมอ ห้าม mock คำตอบ จากนั้นเรียก `SendMessage` ไปยัง agent ตัวเดิม
     (`to: <agentId>`) พร้อมสรุปคำตอบต่อแต่ละคำถาม แล้ววนอ่านผลลัพธ์รอบถัดไป
   - **ถ้าไม่พบ**: ออกจากลูป ไปข้อ 5
   - **ถ้าครบ 6 รอบยังไม่เสร็จ**: หยุด แจ้งผู้ใช้ตรงๆ ว่าการสนทนายาวเกินคาด ให้ตรวจสอบสถานะเอง

5. **สรุปให้ผู้ใช้ทราบ**: หลัง subagent ทำงานเสร็จ ให้สรุปสั้นๆ ว่า
   - สร้าง/แก้ไขเอกสารอะไรที่ path ไหน
   - เพิ่มรหัส FR-xx/NFR-xx อะไรบ้าง
   - อัปเดต backlog.md และ log แล้ว
   - จุดที่ถามผู้ใช้ระหว่างทางและจำนวนรอบที่ใช้ (ถ้ามี)

## ข้อควรระวัง

- ห้ามข้ามการเรียก subagent แล้วเขียนเอกสารเองตรงๆ ในเทรดหลัก — subagent คือแหล่งความจริง
  เดียวของกฎการตั้งชื่อไฟล์ เลขรัน และการจัดรหัส FR/NFR ไม่ให้ชนกัน การเขียนเองเสี่ยงข้อมูล
  ไม่สอดคล้องกับเอกสารที่มีอยู่แล้ว
- **ห้ามข้ามขั้นตอนถาม `AskUserQuestion` จริงแทนคำถามใน `NEEDS_USER_INPUT`** และห้ามเดา/ช่วยตอบแทน
  ผู้ใช้เพื่อให้ลูปจบเร็วขึ้น
- **ต้องใช้ `SendMessage` กลับไปยัง agent ตัวเดิมเสมอ** ห้ามเรียก Agent ใหม่แทน (จะเสียบริบทที่อ่าน
  ไปแล้ว)
- ถ้าผู้ใช้ส่ง requirement ดิบมาหลายเรื่องไม่เกี่ยวข้องกันในคำขอเดียว ให้ใช้ `AskUserQuestion` ถามก่อน
  เรียก subagent เลย (เป็นการตัดสินใจ scope ของงาน ไม่ใช่สิ่งที่ subagent ต้องเป็นคนถาม) โดยเสนอ
  อย่างน้อย 3 ตัวเลือก: (1) แยกเป็นหลายเอกสาร เอกสารละเรื่อง (แนะนำ — ทำให้แต่ละเอกสารยังคุมรหัส
  FR/NFR และประวัติแก้ไขของตัวเองได้ชัดเจน), (2) รวมเป็นเอกสารเดียว, หรือ (3) แยกเป็นหลายเอกสารแต่
  เชื่อมโยงกันด้วย `[[wikilink]]` เพราะเกี่ยวข้องกันบางส่วน — แล้วส่งให้ subagent ทีละเรื่องหรือรวม
  กันตามที่ผู้ใช้เลือก
